# benny 자동화 의도

## 자동화하려는 것

하나의 slack 이슈 채널에서 함께 동작하는 cursor 자동화 두 개를 원합니다.

### 자동화 1: 이슈 보고 분류

- 트리거: 누군가 제가 설정한 소스 slack 채널에 새 최상위 보고를 올리면, 이 자동화가 그 보고에 대해 시작하고 원래 스레드 좌표를 유지하기를 원합니다.
- 동작: 스레드와 첨부 파일을 읽고, 보고를 버그 또는 성능 문제, 기능 요청, 질문 또는 피드백, 다른 곳으로 재전달할 항목 중 하나로 분류하고, 라우팅하기 전에 담당할 가능성이 높은 계층을 추적하기를 원합니다.
- 트래커: 제가 설정한 트래커에서 중복 항목을 검색하고, 확신할 수 있는 중복 항목은 업데이트하고, 명확한 신규 버그일 때만 티켓을 만들기를 원합니다.
- 도구: slack 스레드 읽기 및 답글 권한, 제가 설정한 트래커 연동, 선택 사항인 라우팅 맵을 원합니다.
- 결과: 소스 스레드에 짧은 판정과 `[benny:bug]`, `[benny:performance]`, `[benny:other]` 중 하나를 담은 답글이 정확히 하나 달리기를 원합니다. 버그 또는 성능 마커에는 트래커 url을 포함할 수 있습니다.
- 경계: 이 자동화가 소스 채널에 루트 메시지를 올리는 일은 절대 원하지 않습니다.

### 자동화 2: 확인된 버그 재현 및 수정

- 트리거: 이 자동화가 같은 새 최상위 보고 또는 설정 중에 선택한 다른 지원 트리거에서 시작한 뒤, 원래 스레드에 신뢰할 수 있는 분류 마커가 달릴 때까지 기다리기를 원합니다.
- 게이트: 누군가 수정을 명확히 맡고 있으면 멈추기를 원합니다. 기존 PR이나 머지된 커밋이 보고된 문제를 고칠 가능성이 있으면, 경쟁하는 변경을 만들지 말고 검증을 하기를 원합니다.
- 동작: 제가 설정한 제어 어댑터와 기능 맵을 사용하고, 실제 ui를 통해 정확히 같은 증상을 두 번 재현하고, 스크린샷, 동영상, 읽기 전용 상태 교차 확인을 수집하기를 원합니다.
- 수정: 기존 PR에 직접 변경을 작성하지 않고 그 PR을 검증하기를 원합니다. 재현이 확인된 뒤에는 범위가 제한된 근본 원인 수정을 한 번 시도할 수 있고, 테스트 비용이 낮으면 tdd를 사용하고, 영향 범위(blast radius)에 대해 스모크 테스트를 하고, 수정 전후 증거가 통과할 때만 초안 PR을 열 수 있습니다.
- 도구: slack 스레드 읽기 및 답글 권한, 저장소와 이력 접근 권한, 초안 PR 생성 권한, 제가 설정한 트래커, 제어 어댑터를 원합니다.
- 결과: 소스 스레드나 선택 사항인 운영 스레드에 증거와 검증된 결과가 올라오고, 선택적으로 초안 PR이 만들어지기를 원합니다. 업데이트는 간결해야 합니다.
- 경계: 이 자동화가 소스 채널에 루트 메시지를 올리는 일은 절대 원하지 않습니다.

### 공통 규칙

- 소스 채널과 루트 스레드 좌표는 실행 내내 바뀌지 않기를 원합니다.
- 유틸리티 봇과 디버그 봇의 메시지는 증거로 취급하며, 위임이나 수정 담당으로 보지 않습니다.
- 서브에이전트가 돕는 것은 허용하지만, 서브에이전트는 slack에 글을 올리거나 slack 자격 증명을 받을 수 없습니다.
- 이 팩 전체가 대상 저장소의 `.cursor/automations/benny/`에 커밋되기를 원합니다. 이 팩의 `SKILL.md` 파일은 등록된 플러그인 스킬이 아니라 자동화가 직접 따르는 지시문입니다.
- pstack은 `how`, `why`, `tdd`, `unslop`, 필요한 원칙 스킬 같은 공유 의존성을 위해서만, 대상 저장소에 커밋된 `.cursor/settings.json`을 통해 활성화되기를 원합니다.
- 각 실제 자동화 프롬프트가 커밋된 운영 파일을 직접 읽기를 원합니다. 플러그인 캐시 경로, 복사한 발췌문, 슬래시 스킬 탐색은 원하지 않습니다.
- 사용자가 소유한 설정, 기능 맵, 라우팅 맵, 비밀 값은 `.cursor/automations/benny/` 밖에 두어, 팩을 새로 고칠 때 덮어써지지 않게 합니다.
- 채널 좌표, 트래커 접근 권한, 제어 어댑터, 기능 맵이 없거나 불확실하면 두 자동화 모두 안전하게 실패하여 멈추기를 원합니다.
- 초안 PR만 원합니다. 머지하거나 배포하지 마세요.

## 에이전트에게

사람(사용자)은 cursor가 이 파일을 보도록 지정하는 방식으로 설정을 시작합니다. 탐색된 benny 슬래시 스킬을 찾거나 호출하지 마세요.

1. 어떤 저장소에서 자동화를 실행할지 물어봅니다.
2. 이 `FOR_AGENTS.md`가 들어 있는 디렉터리를 소스 팩으로 취급합니다.
3. 소스 팩 전체를 `<target-repository>/.cursor/automations/benny/`에 병합합니다.
4. 대상에만 있는 파일은 모두 보존합니다. 관련 없는 파일을 삭제하거나, 사용자가 소유한 설정, 기능 맵, 라우팅 맵을 덮어쓰지 않습니다.
5. 소스가 관리하는 경로에 있는 기존 대상 파일의 내용이 다르면, diff를 리뷰하고 로컬 수정 내용을 버리지 않도록 병합합니다. 소유권이 모호하면 교체하기 전에 멈추고 물어봅니다.
6. 복사된 `FOR_AGENTS.md`와 `skills/setup-benny/SKILL.md`가 대상 저장소에 있는지 검증합니다.
7. 대상 저장소에 있는 `.cursor/automations/benny/skills/setup-benny/SKILL.md`를 직접 읽고 그대로 따릅니다.

다음 항목을 대상 저장소의 `.cursor/settings.json`에 병합하세요.

```json
{
	"plugins": {
		"pstack": { "enabled": true }
	}
}
```

관련 없는 설정과 플러그인은 모두 보존하세요. 기존 파일이 jsonc를 사용한다면 주석과 유효한 jsonc 문법을 보존하세요.

대상 저장소를 루트로 하는 새 에이전트로 검증하기를 원합니다. pstack의 `how`, `why`, `tdd`, `unslop` 및 benny가 사용하는 원칙 스킬이 프로젝트 범위에서 해석되는지 확인하세요. 현재 세션에서 로드된 스킬이나 사용자 범위로 설치된 스킬은 포함하지 마세요.

프로젝트 범위 플러그인을 사용할 수 없거나 공유 의존성 중 하나라도 해석되지 않으면, 멈추고 무엇이 실패했는지 설명하세요. `.cursor/automations/benny/skills/`를 플러그인 매니페스트에 추가하거나, 그 안의 파일이 슬래시 스킬 목록에 나타나기를 기대하지 마세요.

두 자동화 중 어느 것이든 활성화하기 전에 `.cursor/settings.json`, `.cursor/automations/benny/`, 참조되는 비밀 값 없는 설정을 모두 커밋해야 한다고 저에게 알려 주세요. 제가 명시적으로 요청하기 전에는 자동화를 만들거나 업데이트하지 마세요.

처음 만들 때는 내장 `/automate`를 분류용으로 한 번, 재현 및 수정용으로 한 번 사용하세요. 두 번째 자동화를 시작하기 전에 첫 번째 자동화의 초안 리뷰, 승인, 준비 상태 확인, Automations 편집기 인계를 마치세요.

이 의도와 완성된 설정을 각 초안에 바꾸어 표현해 넣으세요. 분류 프롬프트는 `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md`를 읽고 따라야 합니다. 재현 프롬프트는 `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md`를 읽고 따라야 합니다. 이러한 저장소 기준 상대 경로는 자동화가 실행될 저장소에 해당 파일이 커밋되었다고 `/automate`가 확인한 뒤에만 사용하세요.

기존 자동화를 확인하거나 업데이트할 때는 `/automate`를 사용하지 마세요. 설정을 검증한 뒤, 복사된 설정 파일에 있는 간결한 필드 체크리스트를 사용하여 제가 각 자동화를 편집기에서 직접 수정할 수 있게 하세요. 중복을 만들지 마세요.
