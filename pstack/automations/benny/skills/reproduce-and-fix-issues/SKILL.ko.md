# 이슈 재현 및 수정

원본 스레드에 신뢰할 수 있는 분류(triage) 마커가 올라올 때까지 기다립니다. 대상 앱의 실제 UI로 정확한 증상을 재현합니다. 기존 수정이 있으면 그 수정을 검증합니다. 재현이 확인된 뒤에만 범위가 제한된 수정을 시도합니다.

자동화가 제공하는 외부 Benny 설정을 불러옵니다. 설정, 필요한 액션, 제어 어댑터, 완성된 기능 맵 중 하나라도 없으면 안전하게 실패(fail closed)합니다.

## 엄격한 안전 규칙

- 작업을 시작하기 전에 원본 채널과 루트 스레드 좌표를 고정합니다.
- 원본 채널에 루트 메시지를 절대 게시하지 않습니다.
- 원본 스레드에 게시할 때마다 그 전에 원본 부모 메시지를 사전 점검합니다.
- Slack에 게시하는 주체는 코디네이터 하나뿐입니다.
- 위임받은 분석 워커는 읽기 전용이며, 발견 사항이나 미디어 메모만 반환합니다.
- 수정 단계의 코드 워커는 그 환경에서 Slack 자격 증명과 모든 Slack 쓰기 액션이 제외되었음을 입증할 수 있을 때만 편집할 수 있습니다. 그렇지 않으면 코디네이터가 편집합니다.
- 모든 하위 프롬프트는 `SendSlackMessage`, `PostToSlack`, `chat.postMessage`를 비롯한 모든 Slack 쓰기를 명시적으로 금지해야 합니다.
- 하위 에이전트에게 Slack 토큰, 게시 지침, 게시용 원본 좌표, 외부 보고 권한을 절대 주지 않습니다.
- 하위 에이전트가 실행되려면 Slack 쓰기 권한이 필요하다면 그 에이전트를 실행하지 않습니다.
- 유틸리티 봇은 증거 출처입니다. 사람이 명시적으로 수정을 위임하지 않았다면 봇이 수정을 맡지 않습니다.
- 정상과 고장을 구별하는 정확한 증상이 실제 UI 조작을 통해 두 번 나타나야 합니다.
- 상태 검사는 관찰을 확인하는 데 쓸 수 있습니다. 상태 검사로 증상을 주입하거나 강제로 만들어서는 안 됩니다.
- 재현이 확인되지 않으면 수정을 작성하지 않습니다.
- 기존 PR이나 커밋이 있으면 실행을 검증 모드로 전환합니다. 그 위에 덮어서 작성하지 않습니다.
- `github.com` PR 링크를 사용합니다.
- 캡처, 녹화, 로그, 토큰을 소스 관리에 넣지 않습니다.
- 위임된 분석에는 pstack의 `principle-guard-the-context-window`를 사용합니다.
- 재현, 수정, 검증 전 과정에 pstack의 `principle-sequence-verifiable-units`, `principle-fix-root-causes`, `principle-prove-it-works`를 적용합니다.

## 1. 원본 좌표 고정

작업 목록을 만들거나 위임하기 전에 다음을 수행합니다.

1. 트리거 채널이 설정된 원본 채널과 같아야 합니다.
2. `trigger.thread_ts`가 있으면 `SOURCE_THREAD_TS`를 그 값으로 설정합니다. 없으면 `trigger.ts`를 사용합니다.
3. `SOURCE_THREAD_TS`가 비어 있지 않아야 합니다.
4. `SOURCE_CHANNEL_ID`와 `SOURCE_THREAD_TS`를 변경할 수 없는 값으로 저장합니다.
5. 원본 스레드를 읽고, 그 루트가 정확히 이 좌표를 갖는지 검증합니다.
6. 원본 퍼머링크를 가져옵니다.

이 값을 답글 타임스탬프, 운영 타임스탬프, 상태 메시지 타임스탬프로 절대 바꾸지 않습니다.

원본 채널에 게시할 때마다 그 전에 다음을 수행합니다.

1. 변경할 수 없는 좌표로 스레드를 읽습니다.
2. 부모 메시지가 존재하고, 삭제되지 않았으며, 여전히 원본 채널에 속해 있는지 확인합니다.
3. `channel=SOURCE_CHANNEL_ID`와 `thread_ts=SOURCE_THREAD_TS`로만 전송합니다.
4. 스레드를 다시 읽고 새 메시지가 답글인지 검증합니다.

점검 중 하나라도 실패하면 아무것도 게시하지 않습니다. 루트나 대체 채널에서 절대 재시도하지 않습니다.

## 2. 분류(triage) 계약 대기

설정된 판정 대기 시간 동안 원본 스레드를 지켜봅니다. 기다리는 동안에는 아무 말도 하지 않습니다.

다음 조건을 모두 만족할 때만 판정을 받아들입니다.

- 작성자가 `slack.triage_identity_user_id`와 일치합니다.
- `SOURCE_THREAD_TS` 아래의 답글입니다.
- 설정된 마커를 정확히 하나 포함합니다.

공개 마커 형식은 다음과 같습니다.

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

`bug` 또는 `performance`일 때만 진행합니다. 선택 사항인 트래커 URL을 기록합니다. `other`, 판정 누락, 신뢰할 수 없는 작성자, 서로 충돌하는 마커, 시간 초과의 경우에는 아무 말 없이 중단합니다.

이 마커는 비공개 봇 신원과 자유 형식 판정 매칭을 대체합니다.

## 3. 소유권 및 수정 산출물 게이트 적용

작업을 시작하기 직전에 스레드를 다시 읽습니다.

### 누군가 명시적으로 수정하고 있는 경우

사람이 수정을 맡겠다고 분명히 밝히거나, 구체적인 구현 계획을 제시하거나, 다른 에이전트에게 구현, 패치, 수정, PR 생성을 요청하면 중단합니다.

다음은 수정 소유권으로 간주하지 않습니다.

- 봇이 증거를 요약합니다.
- 도구가 로그나 티켓을 조회합니다.
- 누군가 봇에게 진단, 설명, 검사, 재현을 요청합니다.
- 봇이 구현하겠다고 동의하지 않은 채 원인 가설을 게시합니다.

봇이 있는지가 아니라 요청된 행동을 기준으로 판단합니다.

### 수정 산출물이 이미 있는 경우

열려 있는 PR이나 병합된 커밋이 이 보고를 수정했을 가능성이 있다면 `references/verify-existing-fix.md`로 전환합니다.

산출물은 스레드, 트래커 이슈, 저장소 히스토리, PR 검색에서 나올 수 있습니다. 커밋이나 PR 없이 주장만 있는 것은 수정 산출물이 아닙니다.

사람이 작업을 맡았지만 아직 산출물을 만들지 않았다면 중단합니다. 그 사람과 경쟁하지 않습니다.

## 4. 선택 사항인 운영 스레드 열기

`slack.operations_channel_id`가 설정되어 있으면 코디네이터는 그 채널에 루트 상태 메시지를 하나 만들 수 있습니다. 이것이 재현 워크플로에서 허용되는 유일한 루트 게시입니다.

그 좌표를 `OPERATIONS_CHANNEL_ID`와 `OPERATIONS_THREAD_TS`로 저장합니다. 이 값을 원본 좌표와 절대 혼동하지 않습니다.

설정된 일반 유니코드 상태 문자열을 사용합니다. 상태 텍스트는 짧게 유지합니다.

- Reproducing
- Could not reproduce
- Blocked
- Reproduced
- Verifying existing fix
- Attempting bounded fix
- Draft pull request opened
- Fix did not land

설정된 Cursor Slack 액션을 우선 사용합니다. `BENNY_SLACK_BOT_TOKEN`은 사용자가 이 상태 메시지 하나를 편집하는 것처럼 좁은 범위의 누락된 기능을 위해 설정해 둔 경우에만 사용합니다. 토큰을 워커에게 절대 노출하지 않습니다.

운영 채널이 설정되어 있지 않으면 자세한 상태는 자동화 실행 출력에 남깁니다. 원본 채널 루트 메시지로 대신하지 않습니다.

## 5. 제어 어댑터 불러오기 및 점검

`references/control-adapter.md`와 `control.feature_map_path`에 있는 완성된 맵을 읽은 다음, `control.skill_name`이 가리키는 스킬을 호출합니다.

보고된 사용자 경로와 일치하는 기능 맵 섹션을 찾습니다. 앱을 조작하기 전에 그 섹션을 읽습니다. 해당 기능을 다루는 섹션이 없으면 경로나 선택자를 지어내지 말고 실행을 blocked로 표시합니다.

다음 일곱 가지 기능이 모두 필요합니다.

1. 설정된 대상 앱과 테스트 환경을 띄웁니다.
2. 매핑된 기능으로 이동하고 문서화된 상태들을 실행해 봅니다.
3. 클릭, 입력, 키, 스크롤, 드래그, 크기 조절, 이동으로 실제 UI를 조작합니다.
4. 상태를 변경하지 않고 검사합니다.
5. 스크린샷을 캡처합니다.
6. 화면 녹화를 시작하고 중지합니다.
7. 프로세스, 세션, 프로필, 임시 데이터를 정리합니다.

어댑터가 없거나 필요한 기능이 하나라도 빠져 있으면 운영 상태를 blocked로 표시하고 중단합니다. 스크린샷, 단위 테스트, 상태 변경, 소스 읽기를 UI 재현인 것처럼 꾸미지 않습니다.

## 6. 보고 내용 파악

원본 스레드 전체와, 있다면 트래커 이슈를 읽습니다.

다음을 수집합니다.

- 정확한 동작 경로
- 기대 동작
- 관찰된 동작
- 두 동작이 갈라지는 구별 상태
- 발생 빈도
- 버전, 환경, 플랫폼
- 첨부 파일과 오류 시그니처
- 후보 코드 영역

스크린샷과 영상을 살펴봅니다. 유용하다면 코드 히스토리, 테스트 아이디어, 영향 범위(blast radius) 매핑, 미디어 리뷰에 읽기 전용 병렬 워커를 사용합니다. 각 워커에게는 좁은 범위의 질문과 Slack 쓰기 금지 규칙을 함께 줍니다.

pstack의 `how` 스킬로 저장소 안에서 동작을 트레이스합니다. 회귀 히스토리와 방어적 코드에는 `why`를 사용합니다. 서로 경쟁하는 원인 가설을 세우고, 그 가설들을 구별해 줄 증거를 찾습니다.

## 7. 재현

제어 어댑터로 대상 앱을 띄웁니다.

동작하기 전에 앱, 워크스페이스, 계정, 데이터 세트, 기능 상태가 올바른지 확인합니다. 안정적인 앱 표식을 사용합니다. 창 순서나 익숙한 제목만으로 판단하지 않습니다.

보고된 경로를 실제 UI 동작으로 따라갑니다.

재현되었다고 판단하기 전에 다음을 수행합니다.

1. 올바른 최종 상태를 명시합니다.
2. 깨진 최종 상태를 명시합니다.
3. 두 상태가 갈라지는 지점에 도달합니다.
4. 깨진 상태를 관찰합니다.
5. 두 번째 시도가 독립적이도록 충분한 상태를 초기화합니다.
6. 같은 경로를 반복하여 같은 깨진 상태를 다시 관찰합니다.
7. 가능하면 실제 상태 값을 교차 확인합니다.

예상된 대화 상자, 로딩 상태, 설정 단계는 버그가 아닙니다. 올바른 동작과 깨진 동작을 구별하는 최종 상태를 캡처합니다.

설정된 재현 예산을 사용합니다. 그 안에서 증상이 재현되지 않으면 깔끔하게 `Could not reproduce` 결과를 보고합니다. 환경이 필요한 기능을 제공하지 못하면 `Blocked`를 보고하고 무엇이 빠졌는지 밝힙니다.

## 8. 증거 캡처 및 리뷰

재현에 성공하면 다음을 수행합니다.

- 증상에 이르는 전체 경로를 녹화합니다.
- 깨진 최종 상태의 스크린샷을 캡처합니다.
- 정확한 단계와 관찰된 상태를 담은 짧은 메모를 저장합니다.
- 산출물은 설정된 임시 산출물 디렉터리에 보관합니다.

읽기 전용 미디어 리뷰어에게 질문 하나에 답하게 합니다. 증거가 구별되는 깨진 상태를 눈으로 확인할 수 있게 보여 주는가?

답이 아니오이거나 불확실하면 재현은 확인되지 않은 것입니다. 더 나은 증거를 캡처하거나 `Could not reproduce`를 사용합니다.

자세한 증거는 운영 스레드가 설정된 경우 그곳에만 게시합니다. 원본 업데이트는 간결하게 유지합니다.

## 9. 재현 결과 보고

먼저 운영 상태를 업데이트합니다.

`Could not reproduce` 또는 `Blocked`인 경우 원본 스레드에는 아무것도 게시하지 않습니다. 결과는 운영 스레드나 실행 출력이 담습니다.

재현이 확인되면 원본 사전 점검을 실행하고, 요청받지 않은 원본 답글을 최대 하나만 게시합니다.

- 이슈가 재현되었다고 알립니다.
- 운영 증거 스레드가 있으면 링크합니다.
- 짧은 발견 사항을 최대 세 개까지 포함합니다.
- 트래커 이슈가 있으면 링크합니다.
- 기본적으로 담당자를 멘션하지 않습니다.

설정된 Slack 액션이 증거를 같은 원본 스레드 안에 유지하고 조직의 보존 정책이 허용할 때만 증거를 첨부합니다.

설정된 거부 대기 시간 동안 기다립니다. 사람이 설정이나 해석이 잘못되었음을 보여 주면 재현을 한 번 바로잡습니다. 유효한 거부 없이 대기 시간이 끝나기 전에는 수정 단계를 시작하지 않습니다.

## 10. 기존 수정 검증

수정 산출물이 있으면 `references/verify-existing-fix.md`를 따릅니다.

검증은 기준(baseline) 빌드에서 증상이 나타나고, 패치된 빌드에서 증상이 사라졌음을 보여야 합니다. 두 경로 모두 실제 UI를 두 번 사용합니다.

기존 수정을 편집하거나, 경쟁하는 패치를 추가하거나, 대체 PR을 열지 않습니다.

## 11. 범위가 제한된 수정 자격 확인

다음 조건이 모두 성립할 때만 수정을 시도합니다.

- 결과가 단서 없이 확인된 재현입니다.
- 미디어 리뷰가 깨진 최종 상태를 확인했습니다.
- 기존 수정 산출물이 나타나지 않았습니다.
- 거부 대기 시간 동안 수정을 맡겠다고 한 사람이 없었습니다.
- 런타임 증거가 근본 원인을 식별합니다.
- 예상되는 변경이 설정된 수정 예산과 저장소 범위에 들어맞습니다.
- 제어 어댑터가 기준 빌드와 패치된 빌드를 모두 실행할 수 있습니다.

조건 중 하나라도 실패하면 재현 보고는 유지하고 PR 없이 중단합니다.

게이트를 통과하면 운영 상태를 `Attempting bounded fix`로 업데이트합니다.

## 12. 근본 원인 분석 및 구현

코디네이터가 모든 Slack 게시, 최종 diff 리뷰, 커밋, PR을 맡습니다.

읽기 전용 워커는 다음을 할 수 있습니다.

- 코드와 히스토리 트레이스
- 테스트 제안
- 영향 범위(blast radius) 매핑
- diff 리뷰
- 미디어 리뷰

워커는 편집하거나, 외부 쓰기를 실행하거나, 상태를 게시하거나, 수정을 맡지 않습니다.

도구 격리로 해당 워커에게서 Slack 자격 증명과 모든 Slack 쓰기 액션이 제거된 경우에만, 이 단계에서 범위가 좁게 제한된 코드 편집을 위임할 수 있습니다. 그 워커의 프롬프트에도 명시적인 Slack 쓰기 금지 규칙을 반드시 넣어야 합니다. 코디네이터는 편집을 리뷰하고 필요한 테스트를 실행하거나 검증합니다. 도구 격리가 확실하지 않으면 편집은 코디네이터가 직접 합니다.

런타임 증거로 메커니즘을 확인합니다. 편집하기 전에 경쟁하는 가설들을 제거합니다.

정당화되는 가장 작은 변경으로 근본 원인을 수정합니다.

- 저렴하게 돌릴 수 있는 로컬 테스트 대상이 있으면 pstack의 `tdd` 스킬을 호출하고, 수정하기 전에 실패하는 테스트를 작성합니다.
- 경로가 비싸거나, 불명확하거나, 통합 비중이 크면 TDD를 생략한 이유를 밝힙니다.
- 관련 없는 정리는 포함하지 않습니다.
- 변경이 설정된 노력 예산이나 위험 예산을 넘어서면 중단합니다.

## 13. 수정 입증

원래의 기준 증거를 보관합니다.

패치된 빌드에서 다음을 수행합니다.

1. 같은 실제 UI 경로를 실행합니다.
2. 그 경로를 두 번 반복합니다.
3. 깨진 상태가 사라졌음을 보여 줍니다.
4. 그 자리에 기대 상태가 나타남을 보여 줍니다.
5. 수정 후 녹화와 스크린샷을 캡처합니다.
6. 기준 빌드에서 사용한 것과 같은 실제 상태 값을 교차 확인합니다.

컴파일, 단위 테스트, 코드 리뷰, 그럴듯한 diff는 수정 후 증거가 아닙니다.

집중된 테스트를 실행한 다음, 변경된 동작 주변의 영향 범위(blast radius)를 스모크 테스트합니다. 변경이 영향을 줄 수 있는 인접 상태, 입력, 권한, 플랫폼, 실패 경로를 다룹니다. 회귀가 남아 있으면 PR 없이 중단합니다.

## 14. draft PR 열기

수정 전후 증거를 확보한 뒤에만 다음을 수행합니다.

- 최종 diff에 관련 없는 변경과 비밀 정보가 없는지 리뷰합니다.
- 저장소에서 요구하는 검사를 실행합니다.
- 저장소 워크플로가 허용하면 작고 순서가 있는 커밋을 만듭니다.
- draft PR을 엽니다. 이 워크플로에서 절대 병합하거나 배포하지 않습니다.
- 트래커가 지원하는 PR 문법으로 설정된 트래커 이슈를 링크합니다.
- 설정된 공개 URL 형식, 보통 `https://github.com/{owner}/{repo}/pull/{number}`를 사용합니다.
- 재현 단계, 근본 원인, 테스트 결과, 수정 전후 증거, 영향 범위(blast radius) 점검 결과를 포함합니다.
- PR 텍스트와 모든 Slack 업데이트를 pstack의 `unslop` 스킬로 다듬습니다.

PR 생성에 실패하면 성공했다고 주장하지 않습니다. 커밋이나 브랜치 상태를 실행 출력에 남기고 운영 상태를 `Fix did not land`로 표시합니다.

성공하면 운영 상태를 `Draft pull request opened`로 표시하고, 운영 스레드에 PR 링크를 담은 간결한 답글을 하나 게시합니다. 두 번째 원본 채널 루트 메시지나 요청받지 않은 원본 답글을 만들지 않습니다.

## 15. 후속 대응 및 정리

설정된 운영 스레드를 후속 대응 대기 시간 한 번 동안 지켜봅니다.

- 직접적인 질문에는 이미 수집한 증거로 답합니다.
- 설정을 무효로 만드는 구체적인 정정이 있으면 한 번 반영하고 재현을 한 번 다시 실행합니다.
- 사람(사용자) 사이의 조율과 잡담에는 끼어들지 않습니다.
- 중단하라는 요청을 받으면 중단합니다.

항상 제어 어댑터의 정리 기능을 호출합니다. 산출물은 설정된 보존 정책이 허용하는 기간 동안만 보관합니다.
