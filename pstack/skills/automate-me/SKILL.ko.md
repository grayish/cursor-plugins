> 이 문서는 [SKILL.md](./SKILL.md)를 한국어로 번역한 문서입니다. 원본과 내용이 다르면 원본을 기준으로 합니다.

# Automate me

사용자의 작업 관례를 에이전트가 따를 스킬로 바꾸는 안내형 흐름입니다. 결과물은 사용자에게 맞춘 `-mode` 스킬 하나입니다(예: `jay-mode`, `priya-mode`).

이 스킬은 다른 세 가지를 조율합니다. 인라인 분석 단계(1단계 참고), Cursor에 내장된 `create-skill`(작성), 그리고 **unslop** 스킬(문장 규율)입니다. 이 스킬은 이들의 순서를 정할 뿐이며, 이들을 대체하지 않습니다.

## 흐름

### 0. 기존 스킬 확인

사용자 핸들과 일치하는 `.cursor/skills/**/*-mode/SKILL.md`와 `~/.cursor/skills/*-mode/SKILL.md`를 재귀적으로 찾습니다. mode 스킬은 최상위뿐 아니라 개인 카테고리 디렉터리(`.cursor/skills/<handle>/`)에 있을 수도 있습니다. 기존 스킬이 있으면 `AskQuestion`으로 의도를 확인합니다(사용자가 이미 "내 스킬을 업데이트해 줘" 같은 말을 했다면 생략합니다).

- 기존 스킬 업데이트(반복 실행 시 기본값)
- 처음부터 새로 시작(드문 경우이며, 진행하기 전에 이유를 묻습니다)

업데이트 모드에서는 나머지 흐름이 다음과 같이 바뀝니다.
- 1단계에서는 스킬이 마지막으로 수정된 이후의 기록만 분석합니다(`git log -1 --format=%cI <path>`).
- 2단계에서는 무엇을 처음부터 담을지가 아니라 무엇이 바뀌었거나 빠졌는지 묻습니다.
- 4단계에서는 기존 파일을 그 자리에서 수정합니다. 사용자가 반박하지 않은 섹션은 유지합니다. 새로운 근거가 있는 섹션은 수정합니다. 새 섹션은 진정으로 새로운 규칙이 있을 때만 추가합니다.

### 1. 사용자 기록 분석

병렬로 분산하기 전에 현재 워크스페이스의 트랜스크립트 위치를 찾습니다. 시스템 프롬프트에 워크스페이스의 `agent-transcripts/` 디렉터리가 명시되어 있습니다. 그 경로만 사용합니다. `~/.cursor/projects/*/` 전체를 glob으로 검색하지 않습니다. 그렇게 하면 워크스페이스 경계를 넘어 관련 없는 프로젝트의 비공개 대화를 읽게 됩니다.

그 범위 안에서 최근 에이전트 대화를 조사해 반복되는 패턴을 찾습니다. 기록을 여러 구간으로 나누어 여러 서브에이전트를 병렬로 실행합니다(예: 최근 2~4주를 3개 구간으로 나누어 각 구간에 충분한 자료가 있게 합니다). **poteto-mode** 스킬의 Subagents 섹션에 따라 각 서브에이전트의 추론 수준과 fast 또는 standard 속도를 작업에 맞게 고릅니다. 구간별 분석 서브에이전트는 부모가 제공한 워크스페이스 범위의 경로에서 트랜스크립트를 읽고, 아래 신호를 찾은 뒤, 발견한 패턴을 근거 위치와 함께 짧고 구조화된 목록으로 반환합니다. 기본적으로 찾아볼 만한 신호는 다음과 같습니다.

- 응답 선호(길이, 어조, 형식, "더 쉽게 설명해 줘" 같은 교정)
- 위임 습관(서브에이전트, 모델, 특화된 워크플로, 병렬 처리)
- 검증 태도("완료"가 무엇을 뜻하는지, 단위 테스트와 실제 재현 중 무엇을 쓰는지, 리뷰어)
- 코드와 문장 규율(스타일, 인용하는 원칙, 린트/포맷 도구)
- 프로세스 관례(워크트리, 커밋, PR, 리뷰/머지 도구)
- 메타 선호(작업 도중 스킬 수정, 새 스킬 제안)

신호를 격상하기 전에 구간끼리 교차 확인합니다. 2개 이상의 구간에서 보인 패턴은 신뢰도가 높습니다. 한 번만 보인 신호는 약하며 보통 버립니다.

### 2. 사용자에게 직접 질문

기록 분석으로는 아직 드러나지 않은 의도를 놓칩니다. 사용자에게 처음부터 직접 입력하도록 요청하지 말고 `AskQuestion` 도구(구조화된 객관식)를 사용합니다.

형태는 각각 4~6개 선택지가 있는 질문 한두 개이며, 카테고리 질문에는 `allow_multiple: true`를 씁니다. 넓은 질문("어떤 영역이 가장 중요한가요?")으로 시작한 뒤, 선택된 영역에 대해 구체적인 선택지로 후속 질문을 합니다. 구조화된 질문을 마친 뒤에는 자유 형식의 채팅 질문 하나로 선택지가 놓친 내용을 잡아냅니다.

질문 20개를 한꺼번에 쏟아내지 않습니다.

### 3. 결과 묶기

모은 신호를 섹션으로 묶습니다. 흔한 섹션은 다음과 같습니다(해당하는 것만 사용합니다).

- **Response style**: 길이, 어조, 형식.
- **Autonomy**: 묻지 않고 얼마나 진행할지, MCP 도구 사용.
- **Understand first**: 변경 범위를 정하거나 조사할 때 어떤 스킬을 쓸지.
- **Subagents**: 기본값, 병렬 처리, 작업별 모델, 특화된 워크플로.
- **Prose / code discipline**: 원칙, 린트 도구, 스타일 가이드.
- **Review and verify**: 재현 태도, 검증 스킬, 실제 테스트 도구.
- **Process**: git 워크트리, 커밋, PR, 리뷰/머지 도구.
- **Skills**: 스킬 작성 습관, 스킬부터 고치기, 새 스킬 제안.

**poteto-mode** 스킬이 형태를 보여 줍니다. 세분화 수준을 참고하려면 읽어 보세요. 그 내용을 복사하지 않습니다. 사용자의 규칙은 poteto-mode의 규칙과 같지 않습니다.

### 4. 스킬 초안 작성

Cursor에 내장된 `create-skill` 스킬로 스킬을 작성합니다. 배치 기준은 다음과 같습니다.

- 경로: 기존 mode 스킬의 카테고리를 유지합니다. 새 mode라면, 저장소에 해당 핸들의 개인 카테고리가 이미 자리 잡혀 있을 때 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`를 사용합니다. 그렇지 않으면 프로젝트의 `.cursor/skills/<handle>-mode/SKILL.md`를 기본값으로 사용합니다(사용자가 개인 스킬을 선호하면 `~/.cursor/skills/<handle>-mode/`를 사용합니다).
- 핸들: 사용자의 이름(first name) 또는 사용자가 고른 식별자입니다.
- Frontmatter `description`: "write code"나 "review PR" 같은 일반적인 키워드가 아니라, 사용자 이름 + `/<handle>-mode` + "work in their style"에 반응하게 합니다.
- Frontmatter 형식: `create-skill`의 YAML 규칙을 따릅니다. `description`은 하나의 YAML 스칼라로 유지합니다. 구두점이나 줄바꿈 때문에 필요하면 따옴표로 감싸거나, 들여쓴 연속 줄과 함께 `description: >-`를 사용합니다.
- Frontmatter `disable-model-invocation: true`가 기본값입니다. 사용자가 자기 mode가 매 턴 적용되기를 명시적으로 원할 때만 해제합니다.

### 5. 문장 다듬기 반복

모든 줄에 **unslop** 스킬과 `create-skill`의 작성 지침을 적용합니다.

초안을 사용자에게 보여 주고 피드백을 받습니다. 여러 번 반복할 것을 예상합니다. 과감하게 줄입니다. mode 스킬은 매뉴얼이 아닙니다.

### 6. 반영하기

main에서 분기한 워크트리에서 작업합니다. 커밋하고 PR을 엽니다. main에 직접 push하지 않습니다.

## 가드레일

- **한 대화에 과적합하지 않습니다.** 한 번 말했다가 다른 때 반대로 말한 선호는 잡음입니다. 규칙으로 만들기 전에 여러 사례를 요구합니다.
- **멋을 부리지 않습니다.** 다른 스킬의 내용을 다시 서술하거나, 비유를 만들어 내거나, 에이전트 독자를 위해 "시적인" 문장을 쓰는 것은 이득 없이 비용만 듭니다. 실무적으로 유지합니다.
- **본문에 붙여 넣지 말고 참조합니다.** 사용자가 의존하는 다른 스킬은 발췌문을 붙여 넣지 말고 경로 참조로 나타냅니다. 사용자가 다른 곳에서 관리하는 원칙 문서도 마찬가지입니다.
- **섹션을 최소한으로 유지합니다.** 사용자에게 그 영역에 대한 구체적이고 기본값이 아닌 규칙이 있을 때만 섹션을 추가합니다. "명확하게 소통하기"는 섹션이 아닙니다. "짧은 단락. 선택지를 비교할 때는 표. 항목이 진정으로 병렬일 때만 글머리 기호."는 섹션입니다.
- **관례 이름은 일반적으로 짓습니다.** 명령문에서는 작성자의 이름 대신 "the user" 또는 "the human"을 사용합니다.
- **억지로 대칭을 맞추지 않습니다.** 사용자에게 적어 둘 만한 프로세스 규칙이 없으면 Process 섹션을 통째로 생략합니다.

## 평가

`-mode` 스킬은 주관적인 결과물입니다. `create-skill` 방식의 테스트/반복 벤치마크 루프는 여기서 유용하지 않습니다. 사용자와 함께 느낌을 확인합니다. 사용자다운 글로 읽히는지, 빠뜨린 것은 없는지 확인한 뒤 배포합니다.

description 최적화 루프는 실제로 스킬의 트리거 정확도가 문제로 드러날 때만 실행합니다.

## 사용하지 않을 때

- 사용자가 작업 관례가 아니라 특정 작업용 스킬을 원하는 경우: 기록 분석 없이 `create-skill`만 사용합니다.
- 사용자가 좁은 워크플로 하나(예: "내가 커밋 메시지를 쓰는 방식")를 담고 싶어 하는 경우: 그것은 mode 스킬이 아니라 일반 스킬입니다.
