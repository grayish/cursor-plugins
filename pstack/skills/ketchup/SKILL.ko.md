# Ketchup

사용자가 `/ketchup` 전에 마지막으로 쓴 메시지 이후 이 채팅에서 바뀐 내용을 알려 주고, 각 변경이 어떤 상태인지뿐 아니라 그 변경 자체를 이해할 수 있도록 돕습니다. 그런 다음 사용자의 결정을 기다리는 모든 사항을 정리해서, 사용자가 이 답변만 보고도 결정할 수 있게 합니다. 알림과 서브에이전트 결과는 사용자의 메시지가 아닙니다. 사용자는 자신의 마지막 메시지를 기억하고 있지만 그 이후의 일은 전혀 모른다고 가정합니다.

[`/bro`](../bro/SKILL.md)의 작업이 아니라 말투를 따릅니다. 한 사람이 다른 사람에게 그동안 있었던 일을 알려 주듯이 쉬운 말과 짧은 문장을 쓰고, 전문 용어를 쓰지 않습니다. 어떻게 했는지가 아니라 사용자에게 무엇이 바뀌었는지를 말합니다. "CI is green"이 아니라 "테스트가 통과합니다"라고 말합니다. 사용자가 행동하는 데 꼭 필요한 경우가 아니라면 해시, 파일 경로, 명령어, 빌드 번호, 테스트 개수는 뺍니다. 각 PR, 브랜치, 에이전트는 직접 지어낸 라벨이 아니라 사용자가 알아볼 수 있는 이름으로 부릅니다. 어떤 사실이 맥락 없이는 이해되지 않는다면 맥락을 함께 주거나 그 사실을 뺍니다.

## 바뀐 내용 모으기

이번 턴은 읽기 전용으로 유지합니다. 시각 자료는 이미 가지고 있는 것으로만 만듭니다. 코드를 바꾸거나, 앱이나 작업을 시작하거나, 무언가를 게시하지 않습니다. 그 메시지 이후에 직접 한 작업, 서브에이전트의 보고, 이 채팅에 있는 다른 사람의 메시지를 모읍니다. 이 채팅에서 다룬 각 PR, CI 실행, 에이전트의 현재 상태를 확인합니다. 보여 줄 숫자는 모두 근거가 되는 사실과 대조해서 확인하고, 숫자를 고쳤다면 고쳤다고 말합니다.

액션 아이템은 제품 관련 선택, 승인, 되돌릴 수 없는 작업, 내가 가지지 못한 접근 권한처럼 사용자만 내릴 수 있는 결정이나 사용자만 할 수 있는 단계입니다. 사용자의 마지막 메시지 전에 제기된 것이라도 아직 사용자를 기다리고 있다면 포함합니다. 내가 아직 직접 할 수 있는 작업은 액션 아이템이 아닙니다. 답변을 채우려고 결정 사항을 지어내지 마세요. 사용자가 요청하지 않았고 작업에도 필요하지 않은 단계는 액션 아이템이 아닙니다. 다만 되돌릴 수 없고 사용자를 기다리는 단계라면 예외로, 시각 자료 없이 한 줄로 적습니다.

결정 하나가 병합을 기다리는 PR 묶음의 각 PR처럼 여러 항목에 걸칠 수 있습니다. 각 항목마다 링크, 사용자에게 바뀌는 점, 내 추천의 근거, 위험, 내 추천을 모읍니다. 결정에 필요하지만 알지 못하는 사실은 "알 수 없음"이라고 씁니다. 가지고 있지 않은 링크는 뺍니다.

## 답변 작성하기

이야기가 아니라 결정 사항에 분량을 씁니다. 있었던 일은 그림을 빼고 100단어 미만으로 쓰고, 일어난 일이 적으면 더 짧게 씁니다. 사용자에게 아무것도 바꾸지 않은 작업은 뺍니다. 각 항목에는 약 30단어를 씁니다. 답변은 항목 수에 따라 길어집니다. 항목이 둘이면 그림을 빼고 전체 150단어보다 훨씬 적어야 하고, 서른 개라면 훨씬 더 길어집니다. 단어 수를 맞추려고 항목을 빼거나 줄이지 마세요. 목록 대신 개수만 적지 말고, 항목 대신 링크만 적지 마세요. 링크는 더 깊은 내용을 더할 수 있지만, 결정은 답변만으로 내릴 수 있어야 합니다.

사용자를 기다리는 것이 무엇인지, 또는 기다리는 것이 없다는 사실을 짧은 한 문장으로 먼저 말합니다. 자세한 내용은 액션 아이템에서 다룹니다. 아무 일도 없었고 사용자를 기다리는 것도 없다면 그렇게 말하고 끝냅니다.

그다음 그림부터 시작해서 있었던 일을 보여 줍니다. 작업 중에 만든 스크린샷과 동영상을 본문에 바로 넣고, 그다음 변경을 설명하는 다이어그램을 넣습니다. 그런 다음 사용자가 요청한 것마다 짧은 글머리 기호 하나로 요약합니다. 어떤 결과가 나왔는지, 그리고 완료되었는지, 아직 실행 중인지, 실패했는지, 확인하지 않았는지를 적습니다. 각 줄은 소리 내어 말하듯이 씁니다. "Search review: done"이나 "Slow search: missing index"가 아니라 "인덱스가 빠져 있어서 검색이 느렸습니다"처럼 씁니다. 작업 중에 발견해서 고친 버그도 이름을 밝힙니다. 각 줄은 따로 읽어도 사실이어야 합니다. 아직 사용자를 기다리는 것을 완료로 표시하지 말고, 액션 아이템에서 다루는 내용은 빼세요. 요약 아래에는 사용자가 아는 것이나 해야 할 일을 바꾸는 내용을 짧게 최대 세 줄로 적습니다. 그다음 내가 직접 할 수 있는 남은 작업을 한 줄로 밝힙니다.

그다음 액션 아이템을 나열합니다. 병합, 승인, 선택처럼 사용자가 내려야 할 결정을 묻고, 내 추천을 제시합니다. 내가 먼저 할 단계는 추천에 넣습니다. 먼저 일어나야 하는 일과 되돌릴 수 없는 일도 추천에 넣습니다. 결정이 다루는 각 PR, 이슈, 에이전트의 번호나 링크를 적고, 여러 선택지 사이의 결정에서도 마찬가지로 적습니다.

결정에 맞는 형태를 고릅니다. 항목 하나에 대한 결정은 글머리 기호 하나로 씁니다. 결정, 내 추천, 사용자에게 바뀌는 점, 추천의 근거, 위험을 적고, 항목 이름은 한 번만 씁니다. 여러 항목이 같은 결정을 공유하면 결정과 내 추천을 한 번 쓰고, 위험이 큰 것부터 각 항목에 글머리 기호를 하나씩 줍니다. 각 항목에는 링크와 이름, 사용자에게 바뀌는 점, 추천의 근거, 위험을 적습니다. 항목의 추천은 결정 전체의 추천과 다를 때만 적습니다. 위험이 낮더라도 "위험 낮음: 색상만 바뀝니다"처럼 각 항목의 위험을 적습니다. 기다리는 비용은 마감이나 데이터 손실처럼 단순한 지연 이상일 때만 말합니다.

여러 선택지 사이의 결정이라면, 작업에서 검토한 모든 선택지를 제시하고 각각 사용자에게 무엇을 주는지, 무엇을 치르게 하는지, 그리고 현재 상태가 있다면 현재 상태를 적습니다. 그 비용이 곧 결정의 위험이므로 따로 위험 줄을 추가하지 않습니다. 위의 스크린샷이 선택지를 보여 준다면, 각 선택지의 이득과 비용을 해당 스크린샷 아래에 적습니다.

## 시각 자료

시각 자료는 그림입니다. 스크린샷, 동영상, Mermaid 다이어그램, `/visualize`로 만든 차트나 다이어그램, 생성한 이미지가 여기에 해당합니다. Markdown 표는 이전과 이후 열이 있더라도 시각 자료가 아닙니다.

문장보다 그림으로 이해하기 쉬운 것은 그림으로 그립니다. 설계나 시스템이 동작하는 방식, 각 PR의 상태를 담은 PR 스택이나 의존성 체인, 수정 전후 비교, 선택지 나란히 비교하기 등이 그렇습니다. 상태 목록, 액션 아이템 목록, 서로 연결되지 않은 상자들은 그리지 마세요. 텍스트에서든 여러 시각 자료에 걸쳐서든 같은 사실을 두 번 제시하지 마세요.

각 시각 자료는 한눈에 읽을 수 있을 만큼 작게 유지합니다. 상자는 최대 여섯 개, 각 상자의 단어는 최대 여덟 개로 합니다. 라벨은 "Tests: pass" 같은 태그가 아니라 사람이 말하는 쉬운 말로 씁니다. 문장이 필요한 사실은 텍스트에 쓰거나 아예 쓰지 않습니다.

변경이 눈에 보이는 경우에는 스크린샷과 동영상을 링크로만 두지 말고 본문에 바로 넣습니다. 눈에 보이는 변경인데 스크린샷이 없다면 해당 요약 줄에 "아직 스크린샷 없음"이라고 표시하고, 화면에서 무엇이 바뀌었는지 그 줄에 적습니다. 다이어그램과 차트는 가지고 있는 사실로 그립니다. 연결 관계는 Mermaid 다이어그램으로, 숫자는 `/visualize` 차트로 그립니다. 숫자를 지어내지 말고, 직접 캡처하지 않은 화면을 그리거나 생성하지 마세요. 실제로 존재하는 결과물만 링크합니다.
