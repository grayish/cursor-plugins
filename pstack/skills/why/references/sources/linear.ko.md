# Linear 티켓

## 이 소스에 담긴 내용

- 기능, 버그, 그리고 그 동기를 설명하는 이슈
- 이슈에 첨부된 프로젝트 문서(대개 PRD 또는 명세)
- 상위/하위 이슈 관계(더 큰 이니셔티브 → 구체적인 티켓)
- 이슈에 달린 댓글(설명 보충, 범위 변경, "이 작업을 하는 이유"에 대한 근거)
- 동기의 유형을 알려 주는 라벨(예: `compliance`, `customer-request`, `perf`)
- 범위 변경을 설명하는 상태 업데이트
- 첨부 파일과 연결된 GitHub PR

Linear에는 제품/비즈니스 맥락이 담겨 있는 경우가 많습니다. "고객 X가 요청했기 때문에 이 작업을 합니다"나 "이것은 3분기 컴플라이언스 이니셔티브를 위한 작업입니다" 같은 층위의 정보가 여기에 있습니다.

## 검색 방법

Linear MCP를 사용합니다.

1. **연결된 티켓부터 시작합니다.** 시작점이 되는 커밋이나 PR이 티켓 ID(예: `ENG-1234`, `[BUG-567]`)를 참조한다면 `get_issue`로 그 티켓부터 가져옵니다. 댓글을 포함해 이슈 전체를 읽습니다.
2. **키워드로 관련 이슈를 나열합니다.** 기능 이름, 핵심 심볼, 비즈니스 용어로 `list_issues` 텍스트 검색을 합니다. 여러 가지 표현으로 시도합니다.
3. **이슈 트리를 따라 올라갑니다.** 하위 이슈에 도달했다면 상위 이슈를 가져옵니다. 하위 이슈는 실행 단위의 작업입니다. "이유"는 상위 이슈에 담겨 있는 경우가 많습니다.
4. **프로젝트 문서를 읽습니다.** 이슈가 프로젝트에 속해 있다면 `get_project`를 사용해 첨부된 문서를 확인합니다. 명세와 근거는 프로젝트 수준 문서에 가장 자주 기록됩니다.
5. **라벨과 마일스톤을 확인합니다.** 라벨은 동기의 범주(customer-request, incident-followup, compliance)를 암시합니다. 마일스톤은 작업을 마감일과 연결하며, 마감일에서 동기가 드러나는 경우가 많습니다.

## 좋은 증거의 예

- 비즈니스 문제를 밝히는 이슈 설명: "고객 Acme는 SOC2 감사 때문에 X가 필요합니다"
- 결정을 기록한 댓글: "접근 방식 A는 결제 서비스를 건드려야 하므로 접근 방식 B로 결정했습니다"
- 이니셔티브처럼 제목이 붙은 상위 이슈: "Q3 Enterprise Readiness" 또는 "Reduce Payment Failures"
- 첨부된 PRD 또는 명세
- `customer:acme`, `incident-followup`, `compliance`, `perf-regression` 같은 라벨

## 흔한 함정

- **범위 변경.** PR이 참조하는 티켓이 닫혔다가 다른 범위로 다시 열렸을 수 있습니다. 전체 이력을 읽습니다.
- **형식적인 템플릿.** 일부 팀은 "Why" 섹션을 필수로 요구하지만 상투적인 문구로 채웁니다. 일반적인 문구("사용자 경험 개선")는 실제 답이 아닐 가능성이 높습니다.
- **오래된 티켓.** 오래된 티켓은 이후에 바뀐 계획을 반영하고 있는 경우가 많습니다. 날짜를 확인하고 코드가 배포된 날짜와 대조합니다.
- **중복으로 닫힌 티켓의 연쇄.** duplicate-of 관계를 따라 기준이 되는 티켓까지 거슬러 올라갑니다.
- **비공개 워크스페이스 콘텐츠.** 이슈에 접근할 수 없다면 추측하지 말고 공백으로 기록합니다.

## 반환할 내용

관련 있는 티켓마다 다음을 반환합니다.
- 티켓 ID와 제목
- 설명이나 댓글에서 인용한 문제/동기(바꿔 쓰지 않습니다. 종합하는 쪽에서 인용하려면 정확한 원문이 필요합니다)
- 라벨, 상위 이슈, 프로젝트
- 작성자, 생성 날짜, 종료 날짜
- 가능하다면 티켓 링크
