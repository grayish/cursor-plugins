# Datadog 텔레메트리

## 이 소스에 담긴 내용

Datadog에는 런타임 기록이 있습니다. 계획되거나 논의된 내용이 아니라 프로덕션에서 실제로 일어난 일을 담고 있습니다.

- **메트릭.** 팀이 계측한 카운터, 게이지, 히스토그램입니다. 메트릭이 *존재한다는 것* 자체가 누군가 그 숫자를 지켜볼 가치가 있다고 생각했다는 증거입니다.
- **모니터와 알림.** 팀이 누군가를 깨울 만하다고 판단한 조건입니다. `rate_limit_hit > 10/min`에서 발생하는 모니터는 팀이 그 임곗값을 걱정했다는 직접적인 증거입니다.
- **대시보드.** 팀이 특정 하위 시스템에서 중요하다고 여기는 항목을 골라 구성한 화면입니다.
- **APM 트레이스와 span.** 요청 단위 런타임 데이터로, "왜 이것이 느린가" / "왜 여기에 타임아웃이 있는가" 같은 질문에 사용합니다.
- **로그.** 대량의 이벤트 기록으로, 방어적 코드의 동기가 된 오류 상황을 담고 있는 경우가 많습니다.
- **인시던트.** 타임라인과 연결된 포스트모템이 있는 공식 인시던트 기록입니다.
- **노트북.** 팀의 탐색적 조사 기록으로, 가설과 분석이 함께 담겨 있는 경우가 많습니다.

## 검색 방법

Datadog MCP를 사용합니다. 넓게 시작한 다음 범위를 좁힙니다.

1. **담당 서비스를 식별합니다.**

   ```
   search_datadog_services (filter by name or team)
   search_datadog_service_dependencies (see upstream/downstream)
   ```

2. **대시보드와 모니터를 먼저 확인합니다.**

   ```
   search_datadog_dashboards (query: feature name, service name, symbol)
   search_datadog_monitors   (same queries)
   ```

   대시보드나 모니터가 대상을 다루고 있다면 그 쿼리와 감시하는 임곗값을 기록합니다. 그 임곗값이 "왜 이 값은 N으로 제한되어 있는가?"에 대한 답인 경우가 많습니다.

3. **대상 주변의 메트릭을 확인합니다.**

   ```
   search_datadog_metrics (by name pattern, e.g., the feature or symbol)
   get_datadog_metric_context (metadata: description, units, tags)
   get_datadog_metric (timeseries; "was there a spike around the PR date?")
   ```

   메트릭의 추이를 대상이 추가되거나 변경된 날짜와 연관 짓는 것은 강력한 뒷받침 증거가 됩니다. 예를 들면 "`payment_timeout` 메트릭이 2023-11-03에 급증했고, 재시도 로직은 2023-11-06에 병합되었습니다."와 같습니다.

4. **로그. 범위를 좁히고, 통째로 쏟아 내지 않습니다.**

   ```
   search_datadog_logs (raw log patterns near the target, set use_log_patterns=true)
   analyze_datadog_logs (SQL-style aggregations, only when you need counts)
   ```

   심볼, 오류 문자열, 기능 이름으로 검색합니다. **시간 범위를 지정한 쿼리를 강하게 우선합니다**(예: 변경 전후 30일).

5. **APM span과 트레이스.**

   ```
   aggregate_spans    (stats: "how often does this endpoint fail?")
   search_datadog_spans (inspect individual spans)
   get_datadog_trace  (a specific trace ID)
   ```

   타임아웃, 재시도, 느린 경로, 서비스 간 동작을 조사할 때 유용합니다.

6. **인시던트.**

   ```
   search_datadog_incidents (by title, team, date range)
   get_datadog_incident     (full detail for a specific incident)
   ```

   대상 코드가 방어적으로 보인다면 그 코드가 추가된 시기 무렵의 인시던트를 검색합니다. 타임라인에 "X에 대한 방어적 검사 추가"가 포함된 인시던트는 거의 직접적인 증거입니다.

## 이 소스에서 좋은 증거의 모습

- 쿼리와 임곗값이 코드가 강제하는 제약과 일치하는 모니터(코드는 100으로 제한하고, 모니터는 요청이 분당 100을 넘으면 알림을 보내는 경우)
- 대상 코드의 작성자가 만든 대시보드로, 위젯이 코드가 측정하거나 막으려는 대상과 대응되는 경우
- 코드가 병합되기 직전에 프로덕션에서 급증했다가 이후에 안정된 값을 보이는 메트릭
- 대상 코드, 같은 심볼, 또는 같은 오류 문자열을 언급하는 인시던트 기록
- 방어적 코드가 막았을 특정 오류 패턴을 보여 주며, 타임스탬프가 변경 이전 기간에 있는 로그

## 흔한 함정

- **상관관계는 인과관계가 아닙니다.** PR 이전의 급증과 이후의 안정화는 시사하는 바가 있을 뿐 결정적이지 않습니다. 같은 기간에 다른 변경이 반영되었을 수 있기 때문입니다. 인접한 PR을 확인합니다.
- **찾아낸 차트에 과도하게 맞추기.** 차트에는 만든 사람의 관점이 반영되어 있습니다. "retry success rate"라는 이름의 차트는 팀이 재시도 성공률을 신경 썼다는 증거이지, 그것이 특정 코드 줄이 존재하는 이유라는 증거는 아닙니다.
- **사라진 텔레메트리.** 메트릭은 이름이 바뀌거나, 삭제되거나, 보존 기간이 짧을 수 있습니다. 관련 기간의 데이터를 찾을 수 없다면 그것은 결과 없음이 아니라 공백(gap)입니다.
- **대규모 데이터의 노이즈.** 로그 검색은 서비스, 태그, 기간으로 적극적으로 좁힙니다. 원시 로그를 쏟아 내지 말고 `analyze_datadog_logs`로 집계합니다.
- **계측되었다고 해서 원인인 것은 아닙니다.** 메트릭은 누군가 무언가를 측정할 만큼 신경 썼다는 것을 보여 줄 뿐, 코드가 그것 *때문에* 추가되었다는 것을 보여 주지는 않습니다. 커밋/PR 날짜와 교차 확인합니다.

## 반환할 내용

관련된 항목마다 다음을 포함합니다.
- 유형(대시보드 / 모니터 / 메트릭 / 로그 패턴 / 트레이스 / 인시던트 / 노트북)
- 제목 또는 이름
- 링크 또는 식별자(대시보드 ID, 모니터 ID, 메트릭 이름, 인시던트 ID)
- 소유자/작성자와 생성/수정 날짜
- 질문과 관련된 구체적인 조건, 쿼리, 인용문(가능하면 원문 그대로)
- 관련성: 이 항목이 대상 코드에 대해 무엇을 시사하는지, 그리고 연관성이 얼마나 강한지
