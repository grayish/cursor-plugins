# Why

코드 뒤에 있는 동기와 의도를 조사합니다. 짝을 이루는 `how` 스킬은 코드가 무엇을 하고 어떻게 동작하는지에 답합니다. `why`는 어떤 요인이 코드를 지금 형태로 만들었는지에 답합니다.

아래의 각 서브에이전트 생성 항목은 `pstack-models.mdc` 규칙에 있는 역할 줄 하나와 기본값을 지정합니다. `model`을 그 줄의 값으로 설정하고, 규칙이나 해당 줄이 없으면 기본값으로 설정합니다. 값이 `auto`나 `inherit-parent`이면 `model`을 설정하지 않습니다. Task 도구가 슬러그를 거부하면 기본값을 사용하고 그 사실을 알립니다. 기본값까지 거부하면 오류 메시지에 나온 슬러그 중에서 같은 계열의 가장 가까운 유효한 슬러그를 사용합니다. 각 서브에이전트의 추론 수준과 빠른 속도 또는 표준 속도는 **poteto-mode** 스킬의 Subagents 섹션에 따라 작업에 맞게 고릅니다.

모든 서브에이전트는 `readonly: false`(에이전트 모드)인 `generalPurpose`로 생성합니다. **readonly/Ask 모드를 사용하지 않습니다.** 이 모드는 MCP 접근을 제거하므로 MCP 기반 조사자와 종합자의 인용 표본 확인이 동작하지 않습니다. 그렇더라도 조사자는 아무것도 작성하지 않아야 합니다.

## 작업 태도

**신중하고 조심스러우며 정확한 조사자**로 일합니다. 아는 것과 추론하는 것을 정직하게 구분합니다. 전체 확신도 체계와 표현 지침은 `references/epistemics.md`를 읽습니다. 종합자는 이를 반드시 따라야 합니다.

## 1단계. 대상과 질문 파악하기

**대상**은 보통 코드 일부, 패턴, 기능, 또는 이름이 붙은 설계 결정입니다. **질문**은 보통 설계 근거, 트레이드오프, 동기가 된 엣지 케이스, 외부 제약, 죽은 코드, 또는 광범위한 이력 조사입니다.

대상이 모호하면("왜 이런 식으로 하나요?"처럼 가리키는 대상이 분명하지 않으면) 대화 맥락(열린 파일, 최근 편집, 커서 위치, 방금 논의한 내용)을 바탕으로 가장 그럴듯한 추측을 합니다. 빗나갔을 때 사용자가 방향을 바로잡을 수 있도록 해석을 간단히 밝힌 다음 진행합니다.

## 2단계. 코드 기준점 확립하기

조사자를 생성하기 전에 시드 컨텍스트를 직접 구성합니다. 여기에는 파일 경로와 줄 범위, 핵심 심볼(함수, 클래스, 상수), 대상을 수정한 최근 커밋 몇 개, 병합 커밋에 있는 PR 번호(제목 줄의 `(#1234)` 패턴), 연결된 티켓 ID가 들어갑니다. 마지막 수정 커밋은 `git blame -L <start>,<end> <file>`로, 이름 변경을 거친 패치 포함 전체 이력은 `git log --follow -p -- <file>`로, PR 번호가 보이는 최근 커밋은 `git log --oneline -20 -- <file>`로 확인하고, PR 번호는 `git log -1 --format=%B <commit>`로 추출합니다. 그런 다음 의미 있는 커밋마다 PR 본문과 논의를 가져옵니다: `gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews`. 이 기준점은 모든 조사자와 종합자에게 전달됩니다.

## 3단계. 병렬 조사자 생성하기

**기본값은 전체 병렬 조사입니다.** 목표는 최소한의 범위 지도가 아니라 완전한 범위 지도입니다. 검색을 건너뛰지 말고, 결과가 없으면 없다는 사실을 기록합니다.

### 탐색

조사자를 생성하기 전에 Cursor 환경에서 사용 가능한 MCP 목록을 확인합니다. 사용 가능한 도구 맵이 있으면 그것을 사용합니다. 없으면 Cursor가 노출하는 `mcps/` 디렉터리에서 활성화된 MCP 서버를 확인합니다.

사용 가능한 각 MCP를 증거 범주 하나에 대응시킵니다.

1. 소스 관리 이력
2. 이슈 / 티켓 트래커
3. 장문 문서
4. 실시간 팀 채팅
5. 인프라 관측성
6. 오류 / 예외 추적
7. 제품 분석 웨어하우스

소스 관리는 git과 `gh`를 통해 항상 사용할 수 있습니다. 나머지 여섯 범주는 MCP 이름, 서버 지침, 도구 이름, 리소스 설명자를 보고 분류합니다. 한 MCP가 여러 범주에 해당할 수 있으면 주된 증거에 맞는 범주를 고릅니다. 모호한 경우는 범위 지도에 기록합니다.

대응하는 MCP가 있는 범주마다 조사자를 하나씩, 모두 한 메시지 안에서 생성하여 동시에 실행되게 합니다. 각 조사자는 정확히 하나의 도구 또는 MCP를 맡습니다. 한 에이전트에게 여러 MCP를 맡기지 않습니다. `model`은 `why investigators` 줄의 값으로 설정하며, 기본값은 `grok-4.7-xhigh-fast`입니다.

각 조사자의 프롬프트는 `references/investigator-prompt.md`를 채운 것에 다음을 더한 것입니다.
- 선택한 MCP에 해당하는 범주 플레이북 `references/sources/<source>.md` (`references/source-playbook.md`의 예시를 바탕으로 맞춘 것)
- **대상 코드가 방어적으로 보이면**(null 검사, 재시도 로직, 타임아웃 처리, 속도 제한, 기능 플래그, 송신 차단 장치, OOM 핸들러) `references/sources/incident-postmortem.md`
- 코드 기준점과 사용자의 원래 질문

### 조사자 명단: 사용 가능한 증거 범주마다 하나씩

아래 각 범주는 "왜"의 특정한 형태 하나를 드러내는 데 고유하게 적합하며, 그 형태는 "가장 잘 찾는 것" 뒤에 적혀 있습니다. 이를 통해 어떤 결과가 돌아올지 예상하고, 범주가 빈 결과를 반환했을 때 빠진 부분을 짚고, 드물게 명백히 무관한 경우에만 건너뛰기를 정당화합니다.

1. **소스 관리** (git 이력, PR용 `gh`, 코드 주석, 테스트). 유일하게 보장된 출처이므로 항상 생성합니다. 가장 잘 찾는 것: *리뷰 과정에서 남은 구현 시점의 근거*.
2. **이슈 / 티켓 트래커** (예: Linear, Jira, GitHub Issues, Plane, Shortcut MCP). 가장 잘 찾는 것: *제품 또는 비즈니스 측면의 강제 요인*. 이유가 엔지니어링 외부에 있을 때 가장 강력합니다.
3. **장문 문서** (예: Notion, Confluence, Google Docs, Coda MCP). 가장 잘 찾는 것: 코드가 되기 전에 글로 정리된 *장문의 설계 근거*.
4. **실시간 팀 채팅** (예: Slack, Discord, Microsoft Teams, Mattermost MCP). 가장 잘 찾는 것: *문서로 남지 않은 실시간 논의*. 소스 관리, 티켓, 문서 기록이 빈약할 때 특히 중요합니다.
5. **인프라 관측성** (예: Datadog, New Relic, Honeycomb, Grafana, Splunk MCP). 가장 잘 찾는 것: *코드의 동기가 된 인프라와 런타임 실제 상황*. 대상이 인프라 신호(타임아웃, 재시도, 속도 제한, 서킷 브레이커)에 반응할 때 가장 강력합니다.
6. **오류 / 예외 추적** (예: Sentry, Rollbar, Bugsnag, Airbrake MCP). 가장 잘 찾는 것: *방어 코드나 수정 코드의 동기가 된 구체적인 예외와 오류 경과*. catch 블록, null 가드, 타입 검사, 재시도를 비롯한 방어 코드에 가장 강력합니다.
7. **제품 분석 웨어하우스** (예: Databricks, Snowflake, BigQuery, ClickHouse, dbt, Redshift MCP). 가장 잘 찾는 것: *코드를 형성한 제품과 데이터의 실제 상황*. 플래그로 제어되는 코드, 실험에 따라 배포된 기능, 데이터 마이그레이션, "이 숫자는 어디서 나왔는가" 같은 질문에 가장 강력합니다.

### 조사자를 건너뛰어도 되는 경우

최종 Sources Consulted에 들어갈 **명시적인 서면 근거**가 있을 때만 건너뜁니다. 유효한 이유는 두 가지입니다.

- 이 환경에 **해당 범주의 MCP가 없는 경우**. 선택이 아니라 공백으로 표시합니다: "실시간 팀 채팅은 건너뛰었습니다. 대응하는 MCP가 없어 대화 기록을 검색할 수 없었습니다."
- **출처가 명백히 무관한 경우**. 단지 "아마 무관할 것"이라는 수준이 아니어야 하며, 기준이 높습니다: "오류 / 예외 추적은 건너뛰었습니다. 대상은 런타임 코드 경로가 없는 빌드 시점 스크립트입니다."

범위를 평가해 보니 PR 설명에 이미 완전한 답이 들어 있는 단일 커밋짜리 사소한 대상이라면, 사용 가능한 일곱 범주 검색이 모두 불필요하다는 것을 **확인한 뒤에만** 직접 답할 수 있습니다. 이 경우 그 사실을 명시적으로 밝힙니다. 이런 경우는 드물어야 합니다.

## 4단계. 종합하기

종합자 하나를 생성합니다. `model`은 `why synthesizer` 줄의 값으로 설정하며, 기본값은 `claude-opus-5-5-xhigh`입니다. 종합자는 다음을 받습니다.
1. 조사자 결과(결과가 없었던 경우와 근거를 갖고 건너뛴 범주를 포함합니다)
2. 코드 기준점
3. 사용자의 원래 질문
4. `references/epistemics.md`의 인식론 체계
5. `references/synthesizer-prompt.md`의 종합자 프롬프트 템플릿

## 5단계. 제시하기

종합자의 결과를 사용자에게 제시합니다. 명확성을 위해 가볍게 다듬거나 대화에서 얻은 맥락을 덧붙일 수는 있지만, **확신도 표현은 다시 쓰지 않습니다**.

## 출력 형식

구조는 `references/synthesizer-prompt.md`에 있는 것을 따릅니다: The Question, The Code in Question, What We Found, What We Can Reasonably Infer, Competing Hypotheses, What We Don't Know, Sources Consulted, Confidence Summary. 필요에 따라 조정해도 되지만 확신도 구분은 그대로 유지하고, Sources Consulted는 조사자마다 한 줄씩 유지합니다. 아무것도 반환하지 않았거나 건너뛴 조사자도 이유와 함께 포함합니다.

Sources Consulted 다음에는, 사용자의 `why` 질문이 이 코드를 변경하기 위한 사전 질문이라면 이력 조사 결과를 변경 계획용 Preserve / Change / Avoid / Risk 제약 조건 집합으로 변환합니다.

## 피해야 할 흔한 실패 유형

- **최신 편향**. 가장 최근 커밋이 권위 있다고 가정하는 것입니다. 현재 형태는 이전의 많은 결정이 쌓인 결과인 경우가 많습니다. 거슬러 올라가 추적합니다.
