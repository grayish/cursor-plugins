# 검증 스킬 유지하기

기능 맵은 앱이 바뀌는 순간부터 낡기 시작합니다. 이 스킬은 `/create-verification-skill`로 생성한 스킬(또는 기능 맵이 있는 모든 프로젝트 로컬 검증 스킬)을 관리하는 유지 루프입니다. 엄밀함의 단위는 모든 문장이 아니라 기능입니다. 모든 글머리 항목을 끝까지 확인하지 않더라도, 모든 기능 파일을 소스로 확인하고 모든 기능을 라이브로 실행해 봅니다.

## 결과

다음 중 하나를 고르고, 어떤 것인지 밝힙니다.

- **clean**: 모든 기능이 소스와 라이브 양쪽으로 확인되었고, 올릴 만한 변경이 없습니다. 브랜치도 PR도 만들지 않습니다.
- **changed**: 입증된 문서, 하네스, 맵 수정을 PR 하나로 올립니다.
- **blocked**: 확인을 끝내지 못했거나, 입증된 수정을 안전하게 올릴 수 없었습니다. 무엇이 막았는지 정확히 밝힙니다.

## 수정 범위

검증 스킬 자신의 디렉터리(SKILL.md, features/, 스킬이 소유한 하네스 스크립트)만 수정합니다. 실행 중에는 제품 코드를 절대 수정하지 않습니다. 맵에 적혀 있지만 앱이 더 이상 하지 않는 동작은 문서 드리프트(맵을 고칩니다)이거나 제품 회귀(보고하고, 문서로 덮어 감추지 않습니다) 중 하나입니다.

## 점검 절차

0. **대상을 찾습니다.** 유지할 검증 스킬을 찾습니다. 본문에 실행/구동 섹션과 기능 맵이 있는 프로젝트 로컬 스킬이 대상입니다(보통 `.cursor/skills/verify-*/`에 있습니다). 후보가 여러 개이면 어느 것인지 묻습니다. 후보가 없으면 대상을 지어내지 말고 멈춘 뒤 `/create-verification-skill`을 안내합니다.

1. **인덱스를 정리합니다.** 기능 맵 README를 읽고 같은 위치의 파일들을 glob으로 찾습니다. 누락되었거나, 남는, 중복된, 죽은 항목을 고칩니다. 가볍게 진행하며, 목록을 새로 생성하지 않습니다.

2. **소스 단계를 진행합니다.** 기능 파일마다 읽기 전용 서브에이전트를 하나씩 동시에 실행합니다. 각 서브에이전트는 "이 사용자 대상 기능은 어떻게 동작하는가?"를 소스로 설명하고, 문서 드리프트로 보이는 부분을 인용과 함께 표시하며, 간결한 라이브 검증 방법을 하나 반환합니다. 서브에이전트는 절대 앱을 구동하지 않으며 절대 파일을 수정하지 않습니다. 반환 형식은 기능 요약 / 소스 진입점 / 드리프트 의심 사항 또는 없음 / 검증 방법 하나입니다.

3. **결과를 맞춥니다.** 모든 기능 파일에 대해 요약이 반환되었는지 확인합니다. 겹치는 검증 방법은 가능한 한 적은 앱 상태로 합칩니다. 인용된 드리프트는 표본으로 확인하고, 문제가 없다는 주장은 다시 입증하지 않습니다. 최근 변경 사항을 훑어서 맵에서 빠진 사용자 대상 화면이나 기능을 찾습니다. 빠졌다고 판단하려면 구체적인 소스 경로가 있어야 합니다.

4. **라이브 단계를 진행합니다.** 소스에 문제가 없어 보여도 반드시 진행합니다. 모든 구동은 코디네이터가 맡습니다. 검증 스킬 자체의 실행 모델을 따릅니다. 서버와 UI는 오래 유지되는 인스턴스 하나를 순차적으로 구동하고, 짧게 끝나는 CLI는 구동할 때마다 새로 격리된 세션을 사용합니다(이 스킬이 아니라 대상 스킬의 Launch 섹션이 정합니다). 모든 기능을 최소 한 번 실행하고, 어떤 실패가 일어나든 점검 내내 다음 세 가지 불변 조건을 지킵니다. (1) 마지막으로 예상 밖의 동작을 한 이후 상태 점검을 하지 않은 인스턴스는 절대 구동하지 않습니다. 첫 구동 전에 doctor를 실행하고, 세션이 단위인 경우 새 세션마다 doctor를 실행하며, 구동이 실패한 뒤에도 다시 doctor를 실행합니다. doctor가 실패를 감지할 수 없는 경우(프로세스는 정상인데 UI 상태가 멈춘 경우)에는 잘 되기를 기대하지 말고 알려진 상태로 초기화하거나 다시 실행합니다. (2) 지금까지 수집한 증거는 모든 정리 작업 후에도 남아 있어야 하며, 이를 추정하지 말고 지정된 위치에서 확인합니다. (3) 구동이 시작한 것은 그 구동이 쓸모를 다한 뒤까지 남지 않습니다. 실패한 반복에서 남은 잔여물은 세션이 멈췄든, 종료되었든, 공유되었든 정리합니다(공유 인스턴스라면 인스턴스가 아니라 잔여물을 정리합니다). 스킬 드리프트 때문에 doctor가 실패하면 그것은 드리프트입니다. 수정 범위 안에서 고치고 한 번 다시 시도합니다(수정으로 무효가 된 것만 다시 시작하고, 그 이상은 하지 않습니다). 그래도 안 되면 점검 결과를 `blocked`로 판단합니다. 도달할 수 없는 기능은 구체적인 전제 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`로 표시합니다. 맵에 그 전제 조건이 빠져 있다면 그것은 드리프트입니다. 분류 과정에서 나온 하네스 수정은 올리기 전에 다시 라이브로 구동해 봅니다. 최종 정리는 이런 재검증까지 포함한 실행의 마지막 구동이 끝난 뒤에 하므로, 실행이 끝난 뒤에는 아무것도 남지 않습니다(증거는 스킬의 규칙에 따라 남깁니다).

5. **분류합니다.** 사용자 관점의 설명이 틀렸거나 빠졌다면 문서 드리프트이므로 고칩니다. 동작은 정상인데 하네스가 구동하지 못한다면 하네스 공백이므로 고칩니다. 하네스 수정은 생성할 때와 같은 헬퍼 규칙을 따릅니다(스크립트는 실행 가능해야 하고, 호출 방법은 스킬 본문에 문서화합니다). 앱 동작이 실제로 망가졌다면 제품 공백입니다. 사용자에게 알리도록 기록하고, 이 PR에는 넣지 않습니다.

6. **올리거나 멈춥니다.** changed라면 입증된 수정을 PR 하나로 올리되, 먼저 변경된 모든 파일을 다시 읽습니다. clean이나 blocked라면 PR을 만들지 않고, 결과와 확인 범위를 정직하게 보고합니다.

간결한 실행 노트(확인한 기능, 도달할 수 없었던 전제 조건, 확인된 드리프트, 결과)를 임시 위치에 남깁니다. 이 노트는 커밋하지 않습니다.
