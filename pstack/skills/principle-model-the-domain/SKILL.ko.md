# 도메인 모델링

실제 도메인을 조건문 곳곳에 흩어 두지 말고 데이터 구조에 담습니다. 도메인과 맞아떨어지는 구조는 유효하지 않은 상태를 아예 표현할 수 없게 만들고 분기를 없앱니다. 코드를 작성하는 시점에 이런 구조를 고르는 비용은 적습니다. 나중에 되살리려 하면 리팩터링처럼 보여서 뒤로 미뤄집니다.

다음을 활용합니다.

- 흩어진 불리언, 단계 값, 생명주기 검사 대신 상태 기계를 씁니다.
- 느슨한 매개변수나 반복되는 형태 가정 대신 타입이 있는 모델을 씁니다.
- 여러 파일에 퍼진 분기 대신 맵, 레지스트리, 조회 테이블, 판별 유니온(discriminated union)을 씁니다.
- 즉흥적인 상태 변경 대신 리듀서나 커맨드/이벤트 모델을 씁니다.
- 로드, 검증, 변환, 저장 같은 순서를 따라 모듈을 나누지 말고 하나의 도메인 지식을 중심으로 모듈을 구성합니다. 실행 순서가 곧 소유권은 아닙니다.
- 반복되는 동작, 소유권, 불변 조건을 한데 모으는 작은 모듈 경계를 둡니다.
- 접근 패턴이 요구하는 곳에는 큐, 캐시, 인덱스, 그래프, 트리, 정규화된 컬렉션을 씁니다.
- 그 밖에 맞는 구조라면 무엇이든 씁니다. 맞는 구조가 없으면 코드가 절대 허용하지 않아야 하는 것과 데이터를 읽는 방식을 먼저 정리한 뒤, 정확히 그것을 담아내는 구조를 찾습니다.

추상화를 억지로 만들지 않습니다. 현재 형태가 이미 명확하고, 국소적이며, 커질 가능성이 낮다면 평범한 코드를 선호합니다. 분기, 중복된 규칙, 유효하지 않은 상태, 생명주기 위험 중 어느 것도 없애지 못하면서 간접 참조만 늘리는 추상화는 의심합니다.

이 원칙을 건너뛰었다는 신호는 새 기능이 기존 if/else 체인에 분기를 하나 더 붙이는 경우, 또는 첫 번째 불리언과 계속 동기화해야 하는 두 번째 불리언이 생기는 경우입니다. 시간 순서에 따른 분해도 또 다른 신호입니다. 단계 이름을 붙인 모듈들은 같은 도메인 규칙을 단계마다 반복합니다.
