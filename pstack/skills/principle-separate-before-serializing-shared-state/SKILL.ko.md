# 공유 상태는 직렬화하기 전에 먼저 분리하기

동시에 실행되는 주체들이 변경 가능한 상태를 공유할 수 있다면, 먼저 그들이 정말 같은 변경 가능 객체를 필요로 하는지 질문합니다. 그렇지 않다면 공유를 없앱니다. 공유가 정말 필요하다면 직렬화를 구조적으로 강제합니다. 잠금 파일, 순차 단계, 배타적 소유권이 그 방법입니다. 지시문과 관례는 동시성 제어가 아닙니다.

**이유:** 공유 상태에 대한 동시 쓰기는 경쟁 상태를 만듭니다. 이런 문제는 간헐적으로 나타나고, 재현하기 어렵고, 디버깅 비용이 큽니다.

**패턴:**
1. **변경 가능한 공유 상태를 찾습니다**(양쪽이 모두 읽고 쓰는 파일, 양쪽이 모두 푸시하는 브랜치, 양쪽이 모두 정의하고 사용하는 API).
2. **기본값: 공유 쓰기 대상을 없앱니다.** 이 주체들에게 하나의 정식 객체가 필요한지, 아니면 서로 독립적인 사실을 기록하는 것인지 질문합니다. 각 주체에게 자기 소유의 파일, 키, 브랜치, 상태 디렉터리를 주고, 읽기/보고 경계에서만 합칩니다. 두 워커가 하나의 `state.json`에 각자 `lastX` 필드를 쓰는 것도 여전히 공유 변경입니다. `indexer-state.json`과 `metrics-state.json`으로 나누면 공유 변경이 아닙니다.
3. **공유 쓰기 대상이 하나여야 한다는 것이 실제 불변 조건일 때만 접근을 구조적으로 직렬화합니다**(잠금 파일, 순차 단계, 단일 쓰기 주체, 원자적 compare-and-swap). "잠금이 필요하다"는 생각은 기본 해답이 아니라 점검해야 할 설계상의 경고 신호로 다룹니다.
