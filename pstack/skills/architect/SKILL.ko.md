# Architect

`not implemented` 본문과 의사 코드를 사용해 타입, 함수 시그니처, 클래스 형태, 모듈 경계를 스케치합니다. 여러 모델의 관점을 종합한 다음, 선택한 스케치에 맞춰 코드를 채웁니다.

## 시작

시작하기 전에 단계마다 항목이 하나씩 있는 할 일 목록을 엽니다.

1. 그라운딩(Ground)
2. 스케치(Sketch)
3. 합의(Agree)
4. 구현(Implement)
5. 폐기(Scrap)

## Phase A: 문제 그라운딩

새 코드가 건드리는 모든 시스템에 대해 실제 멘탈 모델을 구축합니다. 관련 하위 시스템에 대해 **how** 스킬을 실행합니다. 파일 이름을 대는 것은 그라운딩이 아닙니다. `how`가 규정하는 아키텍처 설명을 만들어 냅니다. 설계가 소유권이나 계층 구조를 재정의한다면, 기존 형태에 대해 **why** 스킬도 실행하여 그 근거가 추측이 아니라 제약 조건이 되게 합니다.

둘러싼 시스템과 통합할 것이 전혀 없는, 진정한 그린필드 작업일 때만 Phase A를 건너뜁니다.

## Phase B: 스케치

설계 스케치 작업과 Phase A 그라운딩 산출물을 가지고 **arena** 스킬을 실행합니다. 각 러너의 프롬프트로 `references/runner-prompt.md`를 전달합니다.

러너는 `pstack-models.mdc` 규칙에서 `arena runners` 줄 대신 `architect runners` 줄에서 가져옵니다. 규칙이나 그 줄이 없으면 `claude-opus-5-5-xhigh`와 `grok-4.7-xhigh-fast`를 사용합니다. 별칭 항목과 거부된 항목은 **arena** 스킬 Phase A에 있는 러너 규칙을 따릅니다.

두 번 설계합니다. 첫 번째 후보가 충분해 보이더라도, 종합하기 전에 구조적으로 서로 다른 후보를 최소 두 개 요구합니다. 이것은 **exhaust-the-design-space** 원칙 스킬을 구체화한 것입니다. 한 형태 안에서 부분을 고치는 것이 아니라, 전체 형태가 다른 대안을 만듭니다.

종합하기 전에 모든 후보를 [`references/design-red-flags.md`](references/design-red-flags.md)에 비추어 선별합니다. 다음 기여자는 자신이 연 파일만 보고, 가장 가까운 예시를 복사하며, 컴파일되는 가장 짧은 경로를 택하는 에이전트라고 가정합니다. 한 파일에서 보기에 맞는 변경이 저장소 전체에서도 맞는 설계를 선호합니다.

실행 가능한 후보들을 인터페이스 깊이로 비교합니다. 더 작고 단순한 공개 표면 뒤에 더 많은 복잡성을 숨기는 설계를 선호합니다. 풍부한 인터페이스는 기능을 여러 계층에 흩뜨리지 않고 한곳에 모아 호출 체인을 짧게 유지할 수 있습니다.

Arena는 종합된 설계 패키지 하나를 반환합니다. 그 종합 결정이 근거 문서의 "Synthesis decision" 섹션을 채웁니다.

## Phase C: 합의 (선택)

기본 동작: 종합된 설계로 곧바로 구현을 진행합니다. 사람(사용자)의 확인 단계는 없습니다.

호출자가 명시적으로 요청할 때 확인 단계를 켭니다. 예를 들어 "/architect with checkpoint", "구현하기 전에 멈추고 보여 줘" 같은 요청입니다. 이 경우 종합된 설계를 제시하고 승인을 받을 때까지 멈춥니다.

어느 경우든 **foundational-thinking** 원칙 스킬의 "scaffold first" 모드처럼 종합 결과를 별도의 커밋으로 내보낼 수 있습니다. **outcome-oriented-execution** 원칙 스킬에 따라, 채워 넣는 동안 계획되고 범위가 정해진 깨짐은 괜찮습니다. 구현 전에 설계에 적대적인 압박을 가하려면 종합된 스케치에 대해 **interrogate** 스킬을 실행합니다.

사람(사용자)이 형태에 이의를 제기하면(확인 단계에서든 나중에든) 그것을 Phase A 증거로 취급합니다. 코드를 더 작성하기 전에 다시 그라운딩하고 Phase B를 다시 실행합니다.

## Phase D: 스케치에 맞춰 구현

`not implemented` 본문을 코드로, 의사 코드를 로직으로 바꿉니다. 종합된 스케치가 계약입니다. 스케치에서 벗어나는 것은 조용히 흡수할 마찰이 아니라 드러내야 할 신호입니다. 함수에 스케치가 예상하지 못한 매개변수가 필요하다면, 스케치가 틀렸는지, 요구 사항을 놓쳤는지, 구현이 지나치게 나아가고 있는지 묻습니다.

## Phase E: 아키텍처가 틀렸을 때 폐기

구현이 스케치가 흡수할 수 없는 마찰을 계속 만들어 낸다면 스케치를 버립니다. **redesign-from-first-principles** 및 **fix-root-causes** 원칙 스킬에 따라, 잘못된 설계에 수정 사항을 덧붙이지 않습니다.

신호는 개별 사례가 아니라 *패턴*입니다. 징후는 다음과 같습니다.

- 관련 없는 코드 곳곳에서 같은 형태의 우회책이 반복해서 나타납니다.
- 서로 관련 없는 여러 엣지 케이스가 모두 특수 처리 분기를 필요로 합니다.
- 타입이 컴파일되려면 탈출구(`any`, 캐스트, 실제로는 항상 설정되는 선택적 필드)가 필요합니다.
- 스케치에서는 상태가 공유되지 않는다고 했는데 "락이 필요하다"는 반사적 반응이 나옵니다.
- 호출자가 추상화를 사용하려면 그 내부 규칙을 알아야 합니다.
- 구현 전반에 걸쳐 같은 형태의 독립적인 Phase D 이탈이 두 번 이상 나타납니다.

판단력을 발휘합니다. 엣지 케이스 몇 개가 아키텍처를 폐기할 이유가 되지는 않습니다. 어떤 문제는 정당하게 복잡합니다. 데이터의 복잡성은 설계의 복잡성이 아닙니다.

폐기할 때는 다음과 같이 합니다.

1. 지금까지 만든 것에 대해 **how** 스킬을 다시 실행합니다.
2. redesign-from-first-principles에 따라, 새 제약 조건이 처음부터 전제였던 것처럼 다시 설계합니다.
3. **subtract-before-you-add** 원칙 스킬에 따라, 더하기 전에 뺍니다. 새 스케치는 커지기 전에 먼저 이전 스케치보다 작아야 합니다.
4. Phase B로 돌아가 arena를 다시 실행합니다.

## 출력

호출자 관점의 사용법을 먼저 작성하고, 그것에서 타입 스케치를 도출합니다. 작은 변경에는 새 타입과 시그니처를 담은 파일 하나를 만듭니다. 더 큰 작업에는 모듈 맵과 타입 정의를 만듭니다. 근거 문서는 `references/rationale-template.md`에 따라 구성하여 함께 내보내며, 사용법 스케치와 종합 결정을 포함합니다.
