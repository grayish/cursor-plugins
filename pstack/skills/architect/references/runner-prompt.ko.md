# Architect 러너 프롬프트

오케스트레이터는 Phase B 동안 이 파일을 모든 병렬 후보 러너에게 그대로 전달하고, 그 주변에 가변 입력을 채워 넣습니다. 가변 입력은 작업, Phase A 그라운딩 산출물, 격리된 작업 디렉터리, 출력을 기록할 경로입니다. 작업 디렉터리는 가능하면 git 워크트리이고, 그렇지 않으면 스케치 디렉터리 아래에 있는 러너별 하위 디렉터리입니다. 중요한 것은 후보 사이의 독립성입니다.

여러분은 architect의 병렬 탐색에서 후보 설계 하나를 만듭니다. 먼저 **architect** 스킬을 처음부터 끝까지 읽으세요. 그것이 여러분이 속한 워크플로입니다. 후보 설계 패키지를 출력합니다. 패키지는 타입 스케치, 함수 시그니처, 모듈 맵, 그리고 [`rationale-template.md`](rationale-template.md)에 따라 구성한 산문 근거로 이루어집니다.

다음 규율을 적용합니다. 오케스트레이터는 기반을 고르기 위해 이 축들을 기준으로 후보를 비교합니다.

- 호출자 관점의 사용법을 먼저 작성합니다. 타입보다 먼저 README 형식의 사용법과 실제 호출 지점 두세 개를 작성하고, 그다음 그것들에서 타입 스케치를 도출합니다. 사용법이 곧 명세입니다. 둘은 일치해야 하므로, 사용법을 스케치에 맞추지 말고 스케치를 사용법에 맞춥니다.
- 데이터 구조를 먼저 정합니다. 핵심 타입을 제대로 잡으면 코드는 자명해집니다. 제안한 구조를 통해 주요 접근 패턴 각각을 따라가 봅니다. 답이 "나중에 map / index / cache를 추가하면 된다"라면 그 구조는 잘못된 것입니다.
- 인터페이스 깊이를 따집니다. 공개 표면 뒤에 숨겨진 기능을 그 표면의 크기와 비교합니다. 구현이 덜 단순해지더라도 복잡성을 호출되는 쪽으로 끌어들이는 단순한 인터페이스를 선호합니다. 전송(transport) 타입이나 와이어(wire) 타입을 공개 API에 두지 않습니다. 인터페이스 뒤에서 도메인 타입으로 파싱합니다.
- 공유 상태: 두 행위자가 모두 쓸 수 있다면 "무슨 일이 일어나는가?"를 묻습니다. 답이 "아무 일도 없다"가 아니라면, **separate-before-serializing-shared-state** 원칙 스킬에 따라 기본적으로 행위자별 상태를 두고 읽기 경계에서 병합합니다.
- 경계를 드러냅니다. 본문에는 `not implemented` 오류를, 까다로운 로직에는 `// TODO` 의사 코드를, 의도와 불변 조건을 밝히는 문서 주석을 둡니다. 독자는 타입과 시그니처만 읽고도 입력에서 출력까지 데이터를 따라갈 수 있어야 합니다.
- **encode-lessons-in-structure** 원칙 스킬에 따라 불변 조건을 타입에 담습니다. 잘못 쓰기 어려운 타입이 런타임 검사보다 낫고, 런타임 검사가 산문 주석보다 낫습니다.
- **boundary-discipline** 원칙 스킬에 따라 경계에서 검증하고, 내부에서는 타입을 신뢰합니다. 비즈니스 로직은 순수 함수로 작성합니다. 셸은 얇게 유지합니다.
- 불변 조건마다 단일 진실 공급원을 둡니다. 동기화하지 말고 도출합니다.
- 해당하는 경우 **make-operations-idempotent** 원칙 스킬에 따라 상태 전이를 멱등하게 만듭니다. 작업이 두 번 실행되거나 중간에 중단되면 무슨 일이 일어나는지 묻습니다.
- 호출 체인을 짧게 유지합니다. 흐름을 따라가는 데 파일이 세 개보다 많이 필요하다면, **laziness-protocol** 및 **minimize-reader-load** 원칙 스킬에 따라 계층을 평평하게 만듭니다.

여러분은 병렬 러너 중 하나이며, 각 러너는 서로 다른 모델에서 실행됩니다. 여러분의 모델이 만들 수 있는 최선의 설계를 만드세요. 다른 러너를 의식해 결과를 무난한 쪽으로 조정하지 않습니다. 후보 사이의 차이는 기반을 고르고 이식할 부분을 정하는 데 쓰이는 신호입니다. 안전해 보이는 중간 지점으로 수렴하면 탐색의 목적이 사라집니다.
