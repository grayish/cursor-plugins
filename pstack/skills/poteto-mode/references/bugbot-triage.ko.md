# Bugbot 분류(triage)

Babysit 플레이북(`../playbooks/babysit.md`)이 Bugbot 또는 리뷰 자동화 코멘트를 처리할 때 이 참고 문서를 사용합니다. 목표는 Bugbot을 기본적으로 무시하는 것이 아닙니다. 목표는 모든 코멘트를 반드시 해야 하는 코드 변경으로 취급하지 않도록 하는 것입니다.

## 판단 기준표

조치하기 전에 각 Bugbot 스레드를 분류합니다.

- `fix`: 코멘트가 그럴듯한 정확성, 보안, 개인정보, 데이터 손실, 인증, 과금, 마이그레이션, 멱등성, 경쟁 상태, 또는 이미 출시된 동작에 관한 문제를 지적합니다. 그 코드를 소유하는 가장 아래쪽 PR에서 수정한 다음, 커밋 SHA로 답글을 달고 스레드를 resolve합니다.
- `dismiss`: 코멘트가 문서화된 저위험 노이즈 패턴에 해당하고, 현재 코드와 맥락이 그 우려에 코드 변경이 필요 없음을 증명합니다. 짧은 이유를 답글로 달고 스레드를 resolve합니다.
- `ask`: 코멘트가 새로운 유형이거나, 심각도가 높거나, 보안/개인정보/데이터와 관련되어 있거나, 모호합니다. 추측하지 말고 사용자에게 물어봅니다.

확신이 없으면 물어봅니다. 노이즈성 코드 품질 코멘트를 건너뛰는 비용은 작지만, 실제 데이터 버그나 보안 버그를 건너뛰는 비용은 작지 않습니다.

## 학습된 패턴 형식

앞으로 추가할 패턴은 다음 형태로 작성합니다.

```markdown
### <short pattern name>

- Confidence: candidate | recurring | strong
- Skip when: <conditions that must be true>
- Do not skip when: <risk boundaries>
- Example signal: <phrases or code context that identify the pattern>
- Source: <PR/comment URL or short historical note>
```

예시가 한두 개라면 `candidate`를 사용합니다. 실제로 여러 번 dismiss한 뒤에는 `recurring`을 사용합니다. `strong`은 패턴의 범위가 좁고, 반복적으로 검증되었으며, 위험이 낮을 때에만 사용합니다.

## 반복적으로 건너뛸 수 있는 후보

### 의도된 UI 또는 디자인 시스템 시각적 변경

- 신뢰도: candidate
- 건너뛰는 경우: PR 설명, 스크린샷, 디자인 리뷰, 또는 주변 코드가 시각적 변경을 명시적으로 드러내고 있고, Bugbot 코멘트가 공유된 시각적 기본값이 바뀌었다는 사실을 다시 말하는 것에 그칠 때입니다.
- 건너뛰지 않는 경우: 코멘트가 접근성, 포커스 가시성, 키보드 내비게이션, 색 대비, 또는 PR이 의도적으로 바꾸지 않은 컴포넌트 API 계약을 지적할 때입니다.
- 예시 신호: 포커스 외곽선, 버튼 크기, 간격, 공유 컴포넌트의 시각적 기본값에 관한 코멘트에 소유자가 "intentional" 또는 "intended"라고 답한 경우입니다.

### Bugbot이 볼 수 없는 상위 스택(upstack) 또는 스택 내부 사용처

- 신뢰도: candidate
- 건너뛰는 경우: Bugbot이 export, 컴포넌트, 헬퍼, 또는 파일을 사용되지 않는다고 지적했지만, 현재 사용 중인 forge의 PR 목록과 diff, 상위 스택 diff, 또는 PR 맥락을 보면 스택의 이후 PR에서 그것을 사용하고 있을 때입니다.
- 건너뛰지 않는 경우: 현재 PR이 스택의 일부가 아니거나, 해당 심볼이 공개 API이거나, 상위 스택에서 사용한다는 주장을 검증할 수 없을 때입니다.
- 예시 신호: "Exported component is never used"라는 코멘트에 사람이 "used upstack" 같은 답글을 단 경우입니다.

### 병렬 구현 중의 일시적인 중복

- 신뢰도: candidate
- 건너뛰는 경우: 삭제되거나, 교체되거나, 검증 중인 기존 경로와 새 경로를 나란히 유지하기 위해 PR이 의도적으로 소량의 코드를 중복할 때입니다.
- 건너뛰지 않는 경우: 중복된 코드가 보안, 과금, 데이터 접근, API 동작을 바꾸거나, 오래 유지되는 공유 추상화가 위험을 분명히 줄여 줄 때입니다.
- 예시 신호: "Significant duplication" 또는 "duplicated validation logic"이라는 코멘트에 소유자가 기존 경로는 삭제될 예정이라거나 중복 로직을 의도적으로 지역에 두었다고 설명한 경우입니다.

### 기존 프레임워크 또는 컴포넌트 불변 조건이 경고 내용을 이미 보장하는 경우

- 신뢰도: candidate
- 건너뛰는 경우: 지적된 우려가 현재 diff나 주변 코드에서 확인할 수 있는 공유 컴포넌트, 프레임워크 계약, 타입 불변 조건, 또는 단일 진실 공급원(single source of truth)에 의해 이미 보장될 때입니다.
- 건너뛰지 않는 경우: 불변 조건이 가정만 되어 있고 강제되지 않거나, 타이밍에 의존하거나, 값이 서로 달라질 수 있는 비동기/상태 경계를 넘을 때입니다.
- 예시 신호: 공유 popover가 이미 뷰포트 범위를 강제하는데 내부 popover에 max-height가 없다고 지적하는 코멘트, 또는 지역에서 검사한 값과 전달된 값이 같은 출처를 공유하는데 nullable 값을 지적하는 코멘트입니다.

### 소유자가 후속 작업이나 정리 연기를 선언한 경우

- 신뢰도: candidate
- 건너뛰는 경우: PR 소유자가 해당 문제를 알려진 후속 작업이라고 명시적으로 말했고, 현재 PR이 그 동작을 더 나쁘게 만들지 않으며, 코멘트가 고위험 영역에 관한 것이 아닐 때입니다.
- 건너뛰지 않는 경우: 에이전트가 소유자의 의견 없이 행동하고 있거나, 문제가 중간 또는 높은 심각도의 제품 동작이거나, 연기하면 새로운 회귀가 머지될 때입니다.
- 예시 신호: "I'll worry about that later" 또는 "we'll delete this eventually" 같은 말입니다.

### 스스로 철회했거나 오탐임을 명시한 규칙 코멘트

- 신뢰도: recurring
- 건너뛰는 경우: 코멘트 본문이나 이후의 Bugbot 답글이 해당 지적을 철회했거나, 규칙을 준수하고 있거나, 오탐(false positive)이라고 명시하고, 에이전트가 관련 규칙을 로컬에서 검증할 수 있을 때입니다.
- 건너뛰지 않는 경우: 고위험 문제에 대해 사람이 설명 없이 "false positive"라고 말한 것이 유일한 근거일 때입니다.
- 예시 신호: 파일이 이미 규칙을 준수한다고 본문에 적혀 있는 파일 이름 규칙 코멘트입니다.

## 기본적으로 물어볼 것

이전 PR에서 비슷한 코멘트를 dismiss했더라도 다음 범주는 자동으로 건너뛰지 않습니다.

- 보안, 개인정보, 인증, 과금, 데이터 보존, 학습 데이터, 권한 경계에 관한 지적입니다.
- 심각도가 높은 지적입니다.
- 마이그레이션, 스키마, 멱등성, 동시성, 시스템 간 동작에 관한 지적입니다.
- 제안된 수정이 작고, 제품 의도를 바꾸지 않으면서 위험을 분명히 줄이는 코멘트입니다.

과거 데이터를 보면 사람이 보안/데이터 흐름 코멘트를 dismiss하는 경우가 있었습니다. 이런 경우는 팀 전체의 건너뛰기 규칙이 아니라 소유자의 개별 판단으로 취급합니다.

## 최근 babysit에서 얻은 후보 학습 내용

babysit 도중이나 이후에 팀에 유용해 보이지만 아직 충분히 성숙하지 않은 후보 학습 내용을 여기에 덧붙입니다. 여러 PR에서 패턴이 확인되면 recurring 후보를 위 섹션으로 승격하는 것을 우선합니다.

### 네이티브 브라우저 동작을 수동으로 재구현한 경우

- 신뢰도: candidate
- 건너뛰는 경우: 사실상 없습니다. diff가 네이티브 브라우저 동작을 수동 구현으로 대체할 때(네이티브 sticky를 JS로 위치를 잡는 복제본으로, 네이티브 스크롤 대상 지정을 wheel/touch 이벤트 전달로, 그리기 순서에 따른 가림(occlusion)을 mask/clip-path로 바꾸는 경우), 그 코드에 대한 Bugbot의 로직 버그 지적은 일관되게 타당했습니다.
- 건너뛰지 않는 경우: 이런 코드에서 이벤트 전달의 빈틈(wheel deltaMode, 터치 팬, 가장자리에서의 스크롤 체이닝, 탭 허용 오차), mask/clip의 히트 테스트 불일치, 또는 observer와 React 상태 사이의 타이밍 경쟁에 관한 지적일 때입니다. 기본값은 fix입니다.
- 예시 신호: "masks do not affect hit-testing", "overlay blocks wheel scroll", "ignores deltaMode", "runs in the IntersectionObserver callback before React applies state" 같은 문구입니다.
- 출처: sticky 가림 처리 PR 하나에서 Bugbot이 여섯 번 실행되어 약 열여덟 개의 지적을 남겼고, 하나도 dismiss하지 않고 모두 수정했습니다.

### 계약 테스트 불일치(drift) 주장은 저렴하게 검증할 수 있으므로 테스트를 먼저 실행합니다

- 신뢰도: candidate
- 건너뛰는 경우: 검증 자체는 절대 건너뛰지 않습니다. 명령 하나면 됩니다. PR이
  프로토콜이나 문서 문장을 고정하는 계약 테스트(SKILL.md에 대한 정규식,
  문서 문구의 스냅샷)를 포함하고 있고, Bugbot이 "테스트가 더 이상 문서와
  일치하지 않는다"(또는 그 반대)고 주장하면, 분류하기 전에 PR의 최신 커밋(tip)에서
  그 테스트를 실행합니다. 실패하면 주장이 경험적으로 확인되고, 통과하면
  dismiss 답글에 쓸 구체적인 반증이 됩니다.
- 건너뛰지 않는 경우: 해당 없습니다. 이것은 dismiss 패턴이 아니라 검증을 빠르게 하는 방법입니다.
  반복 실행 시 dismiss 쪽으로 기우는 휴리스틱은 여기서 잘못 작동한다는 점에 유의합니다.
  문장을 고정하는 테스트는 바로 이전 수정 라운드가 그 문장을 고치기 때문에 불일치가 생깁니다.
- 예시 신호: 이전 수정 커밋들이 고정된 문단의 문구를 바꾼 PR에서 "Contract test omits the pre-fix wait"라는
  코멘트가 달렸고, 최신 커밋에서 테스트를 실행하자 정확히 인용된 assertion에서
  실패한 경우입니다.
- 출처: Bugbot이 여덟 번 실행된 문장 고정 PR 하나에서, 이전의 모든 실행 결과가
  수정 후 resolve되었음에도 7번째 실행의 주장은 실제였습니다.

### 같은 PR 안에서 나중에 이미 수정된 오래된 보안 리뷰 지적

- 신뢰도: candidate
- 건너뛰는 경우: 에이전트 기반 보안 리뷰(또는 비슷한 리뷰)가 authz/검증 호출이 빠졌다고 주장하지만, 현재 PR의 최신 커밋에 바로 그 게이트가 (테스트와 함께) 분명히 포함되어 있을 때입니다. 보통 리뷰가 실행된 뒤의 보안 강화 커밋에서 추가된 경우입니다.
- 건너뛰지 않는 경우: 인용된 헬퍼가 논의 중인 주체(principal)에 대해서는 아무 일도 하지 않거나, 검사가 그것이 보호해야 할 부수 효과보다 뒤에 실행되거나, 주장된 주체에 대한 커버리지가 없을 때입니다.
- 예시 신호: 최신 커밋에서 바로 그 가드가 부수 효과보다 먼저 이미 호출되고 있는데 HIGH 등급의 "missing authorization check" 지적이 달린 경우입니다.
- 출처: 보안 강화 커밋이 리뷰 실행보다 나중에 들어간 웹훅 엔드포인트 PR 하나입니다.

### 의도적으로 좁힌 오류 조건을 넓히면 실제 오류가 가려지는 경우

- 신뢰도: candidate
- 건너뛰는 경우: 지적이 좁은 오류 조건(특정
  `errno`, 오류 코드, 또는 상태 클래스)을 모든 경우를 잡는 조건으로 넓히라고 요구하는데, 그 좁은 범위가
  실제로 의미 있는 구분을 담고 있을 때입니다. 대표적인 형태는 `ENOENT`일 때에만 작동하는
  의존성 대체(fallback) 경로입니다. "바이너리가 설치되어 있지 않음"은
  "명령이 실행되었지만 실패함"과 다른 상황입니다. 0이 아닌 종료 코드마다 재시도하면
  정당한 실패(찾을 수 없음, 인증 만료, 네트워크 문제)를 대체 경로로 다시 실행하고
  대체 경로의 오류를 보고하게 되어, 진짜 오류가 가려집니다.
- 건너뛰지 않는 경우: 좁은 조건이 같은 범주의 경우를 놓칠 때(`EACCES` 같은
  다른 "바이너리 사용 불가" errno, 다른 전송 계층 실패), 처리되지 않은 경로에서
  데이터가 유실되거나 부분적인 상태가 남을 때, 또는 재시도가
  멱등적이면서 원래 오류도 여전히 드러날 때입니다.
- 예시 신호: "only retries when X fails with ENOENT … never tries the
  fallback even when a working Y exists"처럼, 실패한 작업이 아니라 누락된 의존성을 위해
  대체 경로가 존재하는 코드를 가리키는 지적입니다.
- 출처: 대체 경로가 실패한 명령이 아니라 누락된 바이너리를 위해 존재했던
  CLI 이름 변경 PR 하나입니다.
