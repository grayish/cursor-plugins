> 이 문서는 [opening-a-pr.md](./opening-a-pr.md)을 한국어로 번역한 문서입니다. 원본과 내용이 다르면 원본을 기준으로 합니다.

### Opening a PR

다른 모든 플레이북의 마지막에 호출합니다.

**워크트리.** main에서 분기한 git 워크트리에서 작업합니다. 서브에이전트는 이 워크트리를 물려받습니다. 같은 브랜치에서 여러 `Task` 호출을 실행할 때는 각각 자체 워크트리를 사용하거나, 호출 사이에 `git fetch && git reset --hard origin/<branch>`를 실행합니다. 관련 없는 작업이 섞인 지저분한 브랜치라면, 변경을 패치로 빼내고, 새 워크트리를 만들고, 패치를 적용합니다. 워크트리가 엉켜 버렸다면 main에서 리셋하고 최소한으로 다시 작업합니다.

**커밋.** 커밋은 자주 합니다. PR을 열기 전에 작고 순서가 정해진 커밋으로 리베이스합니다. 각 커밋은 앞으로 PR 하나가 됩니다. 따라서 각 커밋은 단독으로 반영할 수 있어야 하고, 변경의 흐름이 드러나도록 순서를 정해야 합니다. 수정 사항이 방금 만든 커밋에 속한다면 amend합니다. 분리할 수 있다면 새 커밋을 만듭니다. 커밋 본문에서 제목을 다시 반복하지 않습니다.

**PR.** 커밋 전에 diff에 대해 `cursor-team-kit`의 `/deslop`을 실행하고, 리뷰 전에 `/no-comments`를 실행합니다. 모든 PR 제목, 설명, 커밋 본문은 `/technical-writing`으로 작성하고(Diátaxis를 제외한 모든 계층을 적용하고, STE 어휘 규칙도 적용합니다. 즉 동작 하나에 단어 하나를 쓰고, 관사를 유지하고, 가능하면 `-ing` 형태 대신 단순한 동사를 씁니다), 그다음 `/unslop`을 적용합니다.

**제목.** Conventional Commits 형식 `type(scope): subject`를 따르고, 끝에 마침표를 붙이지 않습니다. type은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf` 등입니다. scope는 `pstack`이나 `poteto-mode`처럼 영역을 나타냅니다. subject는 짧은 명령형으로 쓰고, 변경을 담고 있는 실제 심볼이 있으면 그 이름을 씁니다. 예를 들면 `fix(pstack): retarget opening-a-pr babysit trigger`와 같습니다.

**설명.** PR 본문은 실험 노트가 아니라, diff를 가지고 있는 리뷰어를 위한 1분짜리 브리핑입니다. 본문에는 변경이 왜 존재하는지, 무엇을 제외했는지, 무엇을 망가뜨릴 수 있는지, 그리고 제대로 동작한다는 것을 어떻게 입증했는지를 적습니다. 식별자를 적게 쓰는 짧고 단순한 문장으로 쓰고, 긴 글 덩어리를 만들지 않습니다. 본문은 squash 커밋 본문이 되므로 그 커밋을 약 40줄 이내로 유지합니다. 굵은 글씨 도입부 대신 `##` 제목을 다음 순서로 사용하고, 쓸 내용이 없는 섹션은 뺍니다.

- `## Why`: 문제와 접근 방식을 1~3개의 짧은 문장으로 씁니다. SHA, 리베이스 이력, "main 기반" 같은 서두는 넣지 않습니다.
- `## What changed`: 1~3개의 짧은 글머리 기호로 씁니다. 실제 심볼이나 경로는 그것이 변경을 담고 있을 때만 이름을 씁니다. 이름 변경이나 대상 변경이라면 양쪽 이름을 모두 씁니다.
- `## Scope`: 항상 넣습니다. 무엇을 다루고 무엇을 의도적으로 제외했는지(후속 작업, 알려진 공백)를 1~3개의 짧은 항목으로 씁니다. 심볼, 경로, 파일별 설명은 넣지 않습니다.
- `## Tradeoffs`: 리뷰어가 따로 물어볼 만한, 기각한 대안만 씁니다. 실질적인 선택지가 없었다면 생략합니다.
- `## Blast Radius`: 누구 또는 무엇에 영향을 주는지, 그리고 그것이 왜 안전하거나 위험한지를 1~2개의 문장으로 씁니다. main이 실패 상태라면 그대로 두었을 때의 비용을 적습니다.
- `## Verification`: 1~3개의 글머리 기호로, 각각 실제 실행 경로와 그 결과를 씁니다. 성능 변경이라면 단위를 포함한 주요 수치 하나를 `before → after`로 적고, 나머지는 arena나 swarm 디렉터리 링크로 대신합니다. 표본 크기 방법론, swarm 상세 나열, 지표 표는 넣지 않습니다.

섹션 뒤에는 주장을 입증하는 경우 동영상이나 스크린샷을 첨부합니다. 전체 SHA, swarm이나 arena 레인 상세 나열, lever 보정에 관한 긴 설명, 파일별 체크리스트, "CLEAN" 판정은 본문이 아니라 링크한 산출물에 넣습니다.

**Forge.** 첫 PR 작업 전에 forge를 결정하고, 생성, 편집, 조회, 감시, 병합에 그 선택을 계속 사용합니다. 기본값은 GitHub CLI(`gh`)입니다. `command -v origin`이 성공하고 Origin이 저장소를 확인할 수 있으면 `origin pr ...`를 우선 사용합니다. Origin이 없거나 저장소를 확인할 수 없으면 `gh`를 계속 사용하고 그 대체 사실을 기록합니다. Graphite(`gt`)를 요구하지 않습니다.

**내장 PR 도구.** 실행 환경이 내장 PR 도구를 제공하면 PR 생성, 편집, 대상 변경, ready 표시는 forge CLI가 아니라 반드시 그 도구로 합니다. CLI로 만든 PR은 그 도구가 추적하는 정보를 놓칩니다. 도구가 다루지 않는 작업에는, 그리고 실행 환경에 그런 도구가 없을 때는 모든 PR 작업에 결정된 forge를 사용합니다.

**크기와 스택.** 큰 PR 하나보다 좁은 PR 다섯 개를 선호합니다. 스택은 베이스 브랜치의 연결입니다. 루트 PR은 trunk를 대상으로 합니다. 각 하위 브랜치는 상위 브랜치의 정확한 끝 커밋 위로 리베이스하고, 그 PR은 상위 브랜치를 대상으로 합니다. 상위 브랜치가 병합되면 `playbooks/shipping.md` 4단계에 따라 하위 브랜치를 trunk 위로 옮깁니다. 내장 PR 도구가 없으면 결정된 forge에 따라 `origin pr create --status open --base <parent-branch>` 또는 `gh pr create --base <parent-branch>`로 하위 PR을 만들고, `origin pr edit <pr> --base <parent-branch>` 또는 `gh pr edit <pr> --base <parent-branch>`로 대상을 변경합니다. 독립적인 작업일 때만 trunk에서 브랜치를 만듭니다. 스택에서 상당한 작업을 하기 전에 trunk 위로 리베이스합니다.

**Ready 상태.** 모든 PR은 draft가 아니라 ready 상태로 엽니다. 내장 PR 도구는 기본값이 draft일 수 있으므로, 그 도구로 생성할 때마다 `draft: false`를 설정합니다. Origin을 쓴다면 `--status open`을 전달합니다. `gh`를 쓴다면 `--draft`를 생략합니다. 그래도 PR이 draft로 열리면, PR 도구로 ready 표시를 하거나 결정된 forge에 따라 `origin pr ready <number>` 또는 `gh pr ready <number>`를 실행합니다. PR 상태를 언급하기 전에 `origin pr view <number>` 또는 `gh pr view <number>`를 실행합니다.

**Babysit.** PR을 연다고 babysit이 시작되지는 않습니다. URL을 게시하고 계속 빌드합니다. 먼저 현재 단계나 스택을 끝냅니다. 스택 전체가 만들어진 뒤 사용자가 요청할 때만 별도의 babysit 단계를 실행합니다. 새 PR마다 babysit을 하면 빌드가 멈추고, 이후 작업 단계에서 다시 시작될 커밋에 검사를 낭비하게 됩니다. 피드백이 의도에서 벗어나면 반박합니다.

PR을 여는 서브에이전트는 `interrogate`, `/deslop`, `/no-comments`를 실행하고 URL을 게시합니다. 그 서브에이전트는 Autopilot-full 또는 Autopilot-stack 담당자가 아닌 한 babysit 없이 상위 에이전트로 돌아갑니다. 그런 담당자의 브리프는 babysit 루프를 맡기며, 이 브리프가 바로 `playbooks/babysit.md`가 기다리는 요청입니다. 그 담당자는 코드 준비 완료 보고 뒤에 루프를 시작하고, 자신의 플레이북에 따라 merge-ready 또는 STACK-READY를 보고하며, 스택 전체가 만들어질 때까지 babysit을 미루라는 이 문서와 `playbooks/babysit.md`의 규칙에서 예외입니다.
