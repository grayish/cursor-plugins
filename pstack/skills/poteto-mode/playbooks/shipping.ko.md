### 배포(Shipping)

**머지되는 결과는 당신이 책임집니다. 각 PR을 독립적으로 검증하고, 맨 아래부터 이어지는 검증된 구간만 머지한 뒤, 스택에는 더 이상 손대지 않습니다.**

1. **포지(forge)를 결정한 다음, 각 PR이 머지되기 전에 독립적으로 검증합니다.** 기본값은 GitHub CLI(`gh`)입니다. `command -v origin`이 성공하고 Origin이 저장소를 확인할 수 있으면 모든 PR 작업에 `origin pr`를 사용합니다. 그렇지 않으면 `gh`를 계속 사용하고 대체 경로를 사용했다는 사실을 기록합니다. Graphite(`gt`)를 필수로 요구하지 않습니다. PR마다 검증자를 하나씩 두며, 각 검증자는 Cursor 클라우드 에이전트입니다. 검증자는 알맞은 control 스킬(예: `cursor-team-kit`의 `control-ui` 또는 `control-cli`)로 사용자가 쓰는 방식 그대로 변경 사항을 실행하고, 부모와 head를 비교한 뒤, 해당 PR에 `PASS`, `PASS+NOTES`, `FAIL` 중 하나를 게시합니다. 코드를 작성하지 않은 에이전트가 낸 판정만 인정합니다. 작성자는 자신이 만들려고 의도한 것을 확인하기 때문입니다. CI 통과와 봇의 승인 리뷰는 판정이 아닙니다. 둘 다 사용자처럼 변경 사항을 실행하지 않기 때문입니다.
2. **맨 아래에서 시작해 연속으로 검증된 구간만 머지합니다.** 아직 머지되지 않은 가장 아래 PR부터 위로 올라가다가 `PASS`나 `PASS+NOTES`가 없는 첫 PR에서 멈춥니다. 그 아래에 있는 PR들이 머지할 구간이고, 그중 맨 위 PR이 상한선입니다. 검증되지 않은 PR 위에 있는 검증된 PR은 기다립니다. 아래 코드 없이는 머지될 수 없기 때문입니다. 브랜치가 그 코드를 포함하지도 않고 필요로 하지도 않는 PR은 trunk 위로 옮겨 단독으로 머지할 수 있습니다. 다만 먼저 새 판정을 받아야 합니다. 이전 판정은 그 코드가 아래에 있는 상태에서 실행되었고, trunk에는 그 코드가 없기 때문입니다.
3. **판정이 여전히 현재 코드를 설명하는지 다시 확인합니다.** 판정은 하나의 패치를 대상으로 하며, 체인 리베이스는 어떤 검사도 실패시키지 않으면서 그 위의 모든 PR을 새 SHA로 옮깁니다. 이전 판정을 신뢰하기 전에 판정 시점 SHA와 현재 head의 `git patch-id`를 비교합니다. 패치가 테스트, 문서, lint 설정에서만 다르다면, 레인이 실행한 대상이 노이즈를 제외하고 두 SHA에서 똑같이 빌드되는 경우 그 레인의 결과는 유효합니다. 노이즈란 판정 시점 SHA를 두 번 빌드했을 때에도 나타나는 차이, 또는 빌드에 포함된 커밋 SHA를 말합니다. 읽는 사람이 판단을 확인할 수 있도록 노이즈의 종류별로 해당 파일을 함께 보고합니다. 변경 자체는 여전히 새로운 검사와 리뷰를 받습니다. 이전 판정은 그 변경을 본 적이 없기 때문입니다. dev 서버처럼 빌드 산출물이 없는 레인은 이것을 보여 줄 수 없으므로 다시 실행하고, 그 밖에 달라진 부분도 다시 검증합니다.
4. **아래에서 위로, 한 번에 PR 하나씩 머지합니다.** 항상 구간에서 아직 머지되지 않은 가장 아래 PR을 `origin pr merge <pr>` 또는 `gh pr merge <pr> --squash`로 머지합니다. Origin에서는 기본 명령이 지정한 PR 아래의 모든 PR까지 함께 머지하고, GitHub에서는 base가 아직 부모 브랜치인 PR이 trunk가 아니라 그 브랜치로 머지됩니다. 결과는 PR을 다시 조회해서 확인합니다(`origin pr view <pr>` 또는 `gh pr view <pr> --json state,mergedAt,baseRefName`). 머지 큐가 PR을 대기열에 넣기만 했어도 머지 명령이 성공을 보고할 수 있고, 요청된 auto-merge는 머지가 아니기 때문입니다. 머지된 PR은 상태가 merged이고 base가 부모 브랜치가 아니라 trunk로 표시됩니다. `--auto`(Origin의 merge-when-ready 또는 GitHub auto-merge)는 판정이 현재 head를 대상으로 하는 PR에만 설정합니다. auto-merge는 준비된 head가 무엇이든 그대로 머지하기 때문입니다. 머지가 완료되면, base가 머지된 브랜치였던 PR의 base를 trunk로 바꾸고(`origin pr edit <pr> --base <trunk>` 또는 `gh pr edit <pr> --base <trunk>`), 그 패치를 머지 결과 위로 옮긴 다음 `--force-with-lease`로 푸시합니다. 판정은 커밋이 아니라 패치를 대상으로 하므로, 판정이 유효한지는 3단계의 patch-id 규칙으로 결정합니다. 검사가 통과하고 판정이 유효하면 그 PR을 머지합니다.
5. **머지가 진행되는 동안 스택에 손대지 않습니다.** 브랜치나 base에 가하는 변경은 4단계에서 다음 PR을 옮기는 것뿐입니다. 머지는 판정이 있든 없든 그 순간 브랜치와 base에 담긴 내용을 그대로 반영하기 때문입니다. GitHub에서는 `playbooks/babysit.md`의 queued watcher(`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`)를 `/loop` 아래에서 실행해 상한선에서 `COMPLETE`를 보고할 때까지 구간을 지켜봅니다. Origin에서는 `origin pr checks <pr> --watch`가 반환될 때마다 `origin pr view <pr> --checks`로 현재 PR을 다시 조회하고, 상한선 PR이 merged로 표시될 때까지 반복합니다. 부모가 머지될 때 base가 trunk로 바뀌는 것은 예상된 동작이며 고쳐야 할 손상이 아닙니다. 머지가 멈추면 무언가를 바꾸기 전에 원인부터 파악합니다.
6. **상한선에서 멈춥니다.** 구간을 늘리려면 새 판정이 필요하므로, 이는 1단계부터 새로 시작하는 작업입니다.

**응답:** 검증된 구간과 그 상한선, 각 PR의 판정과 그 판정을 낸 주체, 머지된 내용과 이를 확인한 방법, 그리고 다음 빈틈을 메우려면 무엇이 필요한지를 보고합니다.
