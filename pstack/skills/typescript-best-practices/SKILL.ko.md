# TypeScript 모범 사례

먼저 **type-system-discipline** 원칙 스킬을 적용합니다.

| 규칙 | 요약 |
|------|---------|
| 판별 유니언(Discriminated unions) | `kind` 리터럴 판별자로 변형을 모델링하여 불가능한 상태를 표현할 수 없게 합니다. 선택적 필드를 모아 둔 객체를 쓰지 않습니다. |
| 브랜드 타입(Branded types) | 원시 타입에 `& { readonly __brand: "X" }`로 브랜드를 붙여 서로 섞이지 않게 합니다. 경계에서 한 번만 검증합니다. 브랜드는 실제로 검증하는 타입 가드(`input is AgentId`)에서만 얻으며, `as`로 만들지 않습니다. |
| 구성적 모델링(Constructive modeling) | 잘못된 값을 아예 만들 수 없는 형태로 타입을 설계합니다. 비어 있지 않은 배열에는 `[T, ...T[]]`, 짝수 길이에는 `[T, T][]`, 범위에는 `start`와 `duration`을 사용합니다. 런타임 가드도 아니고, refinement type을 바라는 것도 아닙니다. |
| 가장 단순한 전체 타입(Simplest total type) | 모든 연산이 전체 함수(total)로 유지되는 동안에는 `T[]`를 그대로 둡니다. 느슨한 타입 때문에 `!`, 캐스트, "절대 일어나지 않아야 하는" throw가 필요해지는 곳에서만 `NonEmpty<T>`로 강화합니다. |
| `any`보다 `unknown` | 외부 데이터는 `unknown`입니다. |
| 가드보다 스키마 먼저 | 속성을 하나씩 확인하는 타입 가드를 직접 작성하기 전에, 저장소의 런타임 스키마 라이브러리를 사용하고 `z.infer`처럼 스키마에서 타입을 추론합니다. |
| `as` 캐스트 금지 | 모든 `as`는 언젠가 터질 런타임 크래시입니다. 검증한 뒤에만 캐스트합니다. |
| 좁히기(narrowing) 우선순위 | 판별자 switch > `in` 연산자 > `typeof`/`instanceof` > 사용자 정의 타입 가드 > `as` 순서입니다. |
| 타입 가드 | 주장하는 내용을 반드시 검증해야 합니다. 거짓말하는 가드는 `as`보다 나쁩니다. 안전하다고 말하는 이름 뒤에 버그가 숨기 때문입니다. 이름은 `isX` 또는 `hasX`로 짓습니다. |
| 완전성 검사(Exhaustiveness) | default 분기에 `const _exhaustive: never = x;`를 인라인으로 넣어 새 변형이 추가되면 컴파일러가 오류를 내도록 합니다. |
| `as`보다 `satisfies` | 리터럴 타입을 넓히지 않고 값을 검증합니다. |
| 경계 검증 | 데이터가 들어오는 지점에서 이름 있는 도메인 타입으로 파싱합니다. `Record<string, unknown>`(어떻게 표기하든)은 그 파싱 지점에서 끝나야 합니다. 내부에서는 타입을 신뢰합니다. **boundary-discipline** 원칙 스킬을 참고합니다. |
| 스키마에서 파생한 타입 | 새 인터페이스를 선언하기 전에 `Pick`/`Omit`/`Parameters`/`ReturnType`/`Awaited`/`typeof`를 먼저 활용합니다. |
| 객체 인자 | 위치 인자 대신 객체를 전달하여 인자 순서가 코드 자체로 드러나게 합니다. 핫 패스(프레임마다 실행되는 렌더링, 토크나이저, 파서)에서는 적용하지 않습니다. |
| 실제 테스트 | 실행할 수 있는 것은 모킹하지 않습니다. 누수/disposable 검사를 포함한 프레임워크의 실제 테스트 기본 요소를 우선 사용하고, UI는 실행 중인 빌드에서 검증합니다. 로컬에서 실행할 수 없는 것만 모킹합니다. |
| 구조화된 텔레메트리 | id만으로 디버깅할 수 있을 만큼 맥락을 담은 구조화된 로거 진단을 우선 사용합니다. 배포되는 코드에는 `console.log`를 두지 않습니다. |

예시는 `references/patterns.md`에 있습니다.
