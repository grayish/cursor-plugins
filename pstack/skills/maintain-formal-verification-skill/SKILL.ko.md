# 형식 검증 스킬 유지하기

형식 검사는 자신이 기술하는 대상의 속성을 증명합니다. 코드가 바뀌었는데 검증이 바뀌지 않으면, 검사는 더 이상 존재하지 않는 코드를 기술하면서도 계속 통과할 수 있습니다. 이런 통과는 증명처럼 보이기 때문에 가장 위험합니다. 이 스킬은 `/create-formal-verification-skill`이 생성한 검증 스킬, 또는 이름이 지정된 코드에 대해 모델 체커, 증명기, 코드 수준 검증기를 실행하는 모든 프로젝트 로컬 스킬을 관리하는 유지 루프입니다. 프로젝트 로컬 스킬은 에이전트가 그 스킬을 사용하면서 만드는 변경을 처리합니다. 이 스킬은 그 스킬을 거치지 않은 변경을 처리합니다. 병합, 스킬 없이 한 수정, 여러 커밋에 걸쳐 쌓인 드리프트가 여기에 해당합니다.

## 결과

각 검사에 결과 하나를 정하고, 어떤 결과인지 밝힙니다.

- **in sync**: 마지막 동기화 이후 검사가 기술하는 내용을 바꾸는 변경이 없고, 검사가 통과합니다.
- **updated**: 코드가 바뀌었고, 검증이 이제 새 코드를 기술하며, 검사가 통과합니다.
- **bug**: 검증이 현재 코드를 기술하고 있고, 코드가 속성을 위반합니다. 이것은 코드에 대한 발견이며, 드리프트가 아닙니다.
- **blocked**: 검사를 다시 코드와 일치시킬 수 없었거나 실행할 수 없었습니다. 정확한 이유를 밝힙니다.

검사는 updated이면서 동시에 bug일 수 있습니다. 업데이트로 검증이 다시 코드를 기술하게 된 다음, 그 코드에서 속성이 실패하는 경우입니다.

## 수정 범위

검증만 수정합니다. 모델, 하네스, 속성 파일, 그리고 검증 스킬 자체가 여기에 해당합니다. 사용자가 요청하지 않는 한 실행 중에 제품 코드를 수정하지 않습니다. 현재 코드에서 속성이 실패하면, 통과시키려고 속성이나 모델을 약하게 만들지 않습니다. 실패를 보고합니다.

## 진행 단계

1. **검사를 찾습니다.** 검증 스킬에는 정해진 이름이 없으므로, 하는 일로 찾습니다. 이름이 지정된 코드에 대해 모델 체커, 증명기, 또는 다른 검증기를 실행하는 프로젝트 스킬을 찾습니다. 찾은 스킬을 각각 읽거나, 사용자가 지정한 스킬을 읽습니다. 각 검사마다 속성, 검사가 다루는 코드, 범위(bound)와 가정, 검사를 실행하는 명령어, 그리고 검사가 코드를 기술한다고 마지막으로 확인된 커밋을 모읍니다. 검증 스킬이 없다면 멈추고 `/create-formal-verification-skill`을 안내합니다. 스킬에 동기화 커밋이 기록되어 있지 않다면 검증 파일을 마지막으로 바꾼 커밋을 사용하고, 그렇게 했다고 밝힙니다.

2. **있는 그대로 실행합니다.** 아무것도 바꾸기 전에 각 검사를 한 번 실행하고 결과를 기록합니다. 여기서 통과했다고 해서 코드가 올바르다는 뜻은 아닙니다. 예전 기술이 여전히 성립한다는 뜻일 뿐입니다. 여기서 실패하면 드리프트일 수도 있고 버그일 수도 있습니다. 5단계 전까지는 어느 쪽인지 판단하지 않습니다.

3. **검사 대상 코드의 모든 변경을 읽습니다.** 동기화 커밋부터 현재 커밋까지 검사 대상 파일의 diff를 보고, 각 커밋 메시지를 읽습니다. 옮겨진 코드도 찾습니다. 검사 대상 함수가 이름이 바뀌거나, 쪼개지거나, 다른 파일로 옮겨졌더라도 여전히 검사 대상 코드입니다. 검사가 보호하는 상태를 건드리는 새 코드도 찾습니다. 같은 필드에 값을 쓰는 새 함수가 그 예입니다. 각 변경이 다음 중 어디에 해당하는지 판단합니다.
   - **영향 없음.** 서식, 주석, 검증이 다루지 않는 코드 경로처럼, 변경이 검증이 기술하는 어떤 것도 바꾸지 않습니다. 이 판단은 커밋 메시지가 아니라 모델이나 하네스와 대조해서 확인합니다.
   - **검증이 더 이상 코드를 기술하지 않습니다.** 하나의 나눌 수 없는 동작이던 단계가 이제 둘이 되었거나, 분기가 추가되거나 제거되었거나, 검사가 옮겨졌거나, 새 경로가 보호 대상 상태에 도달하거나, 값의 범위가 달라졌습니다. 모델이나 하네스를 바꿔야 합니다.
   - **약속이 의도적으로 바뀌었습니다.** 변경이 코드가 약속하는 내용을 바꾸고, 변경 안의 증거가 이것이 의도된 것임을 말해 줍니다. 문서 주석, 테스트, 변경 로그, 커밋 메시지가 그런 증거입니다. 속성을 바꿔야 하며, 그 증거를 인용해야 합니다.
   - **약속이 깨졌을 수 있습니다.** 코드가 바뀌었는데 약속이 바뀌었다는 증거가 없습니다. 이후에 나오는 실패는 버그 후보로 다룹니다.

4. **결과가 아니라 코드를 보고 업데이트합니다.** 바뀐 각 부분이 다시 리뷰어가 열어 볼 수 있는 코드를 가리키도록 모델이나 하네스를 바꾸고, 코드에서 하나의 나눌 수 없는 단계는 검증에서도 하나의 단계로 유지합니다. 다시 실행하기 전에 코드를 보고 업데이트를 작성하고, 검사를 통과시키는 방향으로 업데이트를 맞추지 않습니다. 속성은 약속이 의도적으로 바뀐 경우에만 바꿉니다. 예전 문구, 새 문구, 그리고 증거를 기록합니다. 변경 때문에 범위(bound)가 틀리게 되지 않는 한 범위는 그대로 둡니다. 범위를 줄여야 한다면 보고서에 그렇게 밝힙니다.

5. **다시 실행하고 각 결과를 판단합니다.**
   - **통과:** 검사가 이제 실패할 수 없게 된 기술 위에서 통과하고 있을 수도 있습니다. 새 검사를 제거하거나 새 단계의 순서를 바꾸는 것처럼, 속성이 막으려는 방식으로 새 코드를 망가뜨리고, 검사가 이를 잡아내는지 확인합니다. 그런 다음 망가뜨린 부분을 되돌립니다.
   - **실패:** 반례를 실제 코드에 대해 한 단계씩 재현합니다. 어떤 단계가 코드에서 일어날 수 없다면 검증이 틀린 것입니다. 검증을 고치고, 무엇이 틀렸는지 밝힙니다. 모든 단계가 일어날 수 있다면 버그입니다. 버그를 도입한 커밋을 밝히고, 반례를 코드 자체의 용어로 일련의 단계로 설명하고, 피해를 한 문장으로 말합니다. 실제 코드에 대한 간단한 테스트나 재현으로 버그가 드러난다면 증거로 보고서에 추가합니다. 그것을 제품 코드에 커밋하지는 않습니다.

6. **검증 스킬을 업데이트합니다.** 각 검사가 다루는 코드, 명령어, 범위(bound), 가정, 동기화 커밋을 업데이트합니다. 동기화 커밋은 확인한 커밋으로 설정합니다. blocked인 검사의 동기화 커밋은 옮기지 않고, 보고서에 그렇게 밝힙니다. 그런 다음 다음 에이전트가 하듯이 검증 스킬을 한 번 따라 해서, 그 단계들이 여전히 실행되는지 확인합니다.

## 보고

각 검사마다 사용자에게 다음을 알립니다.

- 결과, 그리고 읽은 커밋
- 검증에서 바뀐 내용과 그 이유: 각 변경마다 코드의 형태가 바뀌었는지, 또는 약속이 의도적으로 바뀌었는지(증거 포함) 짧게 밝힌 이유
- 다시 실행한 결과, 그리고 업데이트한 검사가 여전히 실패할 수 있음을 보이기 위해 사용한 망가뜨리기
- 각 버그를 쉬운 말로: 코드의 용어로 쓴 단계별 반례, 피해, 그리고 버그를 도입한 커밋
- 검증이 여전히 다루지 않는 부분(다뤄야 하지만 다루지 않는 새 코드 포함)

어떤 실패가 검증의 드리프트였고 어떤 실패가 코드의 버그였는지 분명하게 말합니다. 업데이트 전에는 통과했고 업데이트 후에는 실패하는 검사라면, 예전 통과는 낡은 기술에 대한 통과였다고 말합니다.

검증 업데이트는 제품 수정과 분리해서 별도의 변경으로 만듭니다.
