# 검증 스킬 만들기

진지한 프로젝트라면 실제 앱을 조작해 동작을 입증하는 스크립트화된 방법이 반드시 필요합니다. 앱을 실행하고, 사용자가 하듯이 기능을 사용해 보고, 증거를 수집하는 방법입니다. 이 스킬은 그 방법을 저장소에 맞춘 프로젝트 로컬 스킬(`.cursor/skills/verify-<app>/`)로 생성합니다. 생성 결과물은 사람이 아니라 다음 에이전트를 위해 작성합니다. 이 결과물은 앱을 한 번도 본 적 없는 에이전트가 작업 도중에 사전 맥락 없이 읽게 됩니다.

## 1. 사용자가 아니라 저장소를 인터뷰합니다

다음 질문에는 코드베이스를 보고 답하고, 직접 관찰할 수 없는 내용만 사용자에게 묻습니다.

- **표면(Surface):** 사용자가 실제로 다루는 것은 무엇인가요? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리 중 무엇인가요? 저장소에 여러 개가 있을 수 있습니다. 주된 것 하나를 고르고 나머지는 기록해 둡니다.
- **실행(Run):** 앱을 로컬에서 어떻게 시작하나요? 저장소가 직접 문서화한 개발 명령(package 스크립트, Makefile, README 빠른 시작)을 우선합니다. 포트, 환경 변수, 시드 데이터, 인증 방식을 기록합니다.
- **조작(Drive):** 에이전트가 프로그래밍 방식으로 앱과 상호작용하려면 어떻게 해야 하나요? 기존 하네스를 먼저 찾습니다. Playwright/Cypress 명세, expect 스크립트, PTY 헬퍼, curl로 호출할 수 있는 엔드포인트, 디버그 포트 등이 해당합니다. 그런 것이 없을 때만 일반적인 방법을 고릅니다. 웹과 Electron에는 브라우저/CDP를, CLI/TUI에는 tmux/PTY 하네스를, 서비스에는 일반 HTTP를 사용합니다.
- **관찰(Observe):** 어떤 증거를 수집할 수 있나요? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태 등이 있습니다.
- **격리(Isolate):** 인스턴스 두 개를 나란히 실행할 수 있나요(포트, 데이터 디렉터리, 프로필)? 실행할 수 없다면 생성된 스킬에 그 사실을 명시합니다. 공유 인스턴스를 이중으로 조작하기를 거부하는 편이 사용자 세션을 망가뜨리는 것보다 낫습니다.

체크아웃한 코드가 그대로는 빌드되거나 시작되지 않는다면, 스킬을 생성하기 전에 먼저 그 문제를 고치거나 정확하게 보고합니다. 망가진 기반 위에서 작성한 스킬은 잘못된 절차를 가르칩니다. 관련 없는 자산이 없어서 시작이 막히는 경우(API가 전혀 제공하지 않는 정적 디렉터리, 샘플 설정 등)에는 생성된 스킬이 그 자산을 만들 수 있습니다. 다만 검증용 임시 구조물임을 분명히 표시하고 정리 단계에서 제거합니다.

## 2. 스킬을 생성합니다

`.cursor/skills/verify-<app>/SKILL.md`를 작성합니다. YAML frontmatter(`name: verify-<app>`과, 앱과 표면과 언제 이 스킬을 사용할지를 밝히는 `description`)를 포함해야 합니다. frontmatter가 없으면 스킬이 등록되지 않습니다. 그리고 다음 섹션을 작성하되, 각 섹션은 인터뷰에서 실제로 알아낸 내용에 근거해야 합니다(자리 표시자를 남기지 않습니다).

- **실행(Launch):** 검증을 위해 앱을 시작하는 정확한 명령과, 준비가 되었는지 판단하는 방법(로그 한 줄, 프롬프트 등)을 적습니다. 실행 단계는 마이그레이션과 시드 데이터를 포함해 빈 데이터 디렉터리에서 시작해 사용 가능한 상태까지 도달해야 합니다. 준비되었다는 것은 프로세스가 응답한다는 뜻이 아니라 사용할 수 있다는 뜻입니다. 데이터베이스 상태 확인은 초기화 스크립트가 아직 실행 중일 때도 통과할 수 있습니다. 종료 절차도 포함합니다. 짧게 실행되는 CLI나 TUI에는 계속 띄워 둘 서버가 없습니다. 이 경우 실행이란 바이너리를 한 번 빌드(또는 의존성을 설치)한 뒤, 매번 조작할 때마다 격리된 별도의 PTY나 tmux 세션에서 시작하는 것을 뜻합니다.
- **진단(Doctor):** "이 인스턴스를 조작할 가치가 있는가?"에 답하는 읽기 전용 확인 한 가지를 적습니다. 프로세스가 실행 중인지, 버전/빌드가 맞는지, 포트를 우리가 점유하고 있는지, 인증이 유효한지를 확인합니다. 에이전트는 무언가 이상해 보일 때마다 이 확인을 먼저 실행합니다.
- **조작(Drive):** 예시가 아니라 이 저장소의 실제 선택자/명령을 사용한 하네스 방법을 적습니다. 좌표나 탭 순서보다 안정적인 식별자(ARIA 레이블, data 속성, 프롬프트 문자열, 라우트 경로)를 우선합니다.
- **증거(Evidence):** 입증을 위해 무엇을 수집하고 어디에 저장하는지 적습니다. 입증 기준을 명시합니다. 내부 setter나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로를 사용합니다. 최종 화면만이 아니라 동작과 그 결과 상태를 함께 수집합니다. 눈에 보이는 것과 더불어 부수 효과(작성된 파일, 삽입된 행, 전송된 메시지)도 검증합니다. mock은 프로덕션 경계가 이미 외부 시스템을 격리하는 곳에서만 사용합니다. 안전한 경로가 dry-run이나 테스트 모드라면, 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰(파일, 네트워크, git ref)해서 검증합니다. 어떤 dry-run은 여전히 네트워크에 접근하거나 브라우저를 엽니다.
- **정리(Cleanup):** 실행 중에 만든 인스턴스를 종료하는 방법을 적습니다. 프로세스 이름으로 종료하지 않습니다. 직접 시작한 것만 종료합니다. 정리 단계는 인스턴스와 임시 상태를 제거하지만 증거는 절대 제거하지 않습니다. 입증 결과물은 스킬이 지정한 위치에 남아 종료 후에도 보존됩니다.
- **헬퍼(Helpers):** 스킬에 포함된 스크립트는 모두 실행 가능해야 하고, 호출 방법이 스킬 본문에 나와 있어야 합니다. 읽는 사람이 역공학으로 알아내야 하는 헬퍼는 헬퍼가 아닙니다.

## 3. 기능 맵의 초안을 만듭니다

`.cursor/skills/verify-<app>/features/README.md`와 함께, 파악할 수 있는 사용자 대상 기능마다 파일을 하나씩 만듭니다(처음에는 라우트, 명령, 메뉴, 문서에서 찾은 상위 3~5개를 목표로 합니다). [`references/feature-map-example/`](references/feature-map-example/)에 있는 형식을 따라, README 색인 하나와 기능별 파일 하나씩을 둡니다. 각 파일은 사용자 관점에서 다음 질문에 답합니다. 이 기능은 무엇인지, 어떻게 접근하는지, 하네스로 어떻게 조작하는지, 그리고 어떤 관찰 가능한 최종 상태가 기능이 동작함을 입증하는지입니다. H2 제목 네 개는 `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`입니다. 어떤 사용자 여정에 필요한 사전 조건이 시드 데이터에 없다면, 그 여정은 실패를 보고하고 이유를 해당 기능의 `Gotchas`에 적습니다. 통과시키려고 여정을 약화하지 않습니다. 이 맵은 저장소에서 관리하는 검증 기준 자료입니다. 맵에 다른 진입점이 나열되어 있는데 편리한 진입점 하나만 조작했다면 그 입증은 불완전합니다.

## 4. 넘겨주기 전에 생성된 스킬을 입증합니다

스킬 자체의 지시를 처음부터 끝까지 한 번 실행합니다. 실행, 진단, 맵에 있는 기능 하나 조작(하나면 충분합니다. 맵은 이후 실행에서 나머지를 다루기 위해 존재합니다), 증거 수집, 정리 순서입니다. 정리 후에도 증거가 지정된 위치에 여전히 있는지 확인합니다. 정리 단계가 입증 결과물을 지워 버리면 이 단계는 실패입니다. 실패한 부분을 고치고, 실패한 반복마다 생성된 정리 절차도 실행해서 망가진 시도가 프로세스와 포트를 남겨 두지 않게 합니다. 한 번도 실행해 보지 않은 생성 스킬은 결과물이 아니라 초안입니다. 실제 대상 대신 대체 환경(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택)에서 입증했다면, 대체 환경이 수행했지만 실제 대상에서는 수행되지 않을 설정 단계를 모두 나열합니다. 그 단계들은 실제 대상에서 실행해 확인하기 전까지 검증되지 않은 상태로 남습니다.

## 5. 유지 관리 루프를 안내합니다

앱이 바뀌어도 맵을 정확하게 유지할 수 있도록 사용자에게 `/maintain-verification-skill`을 안내합니다. 실행 주기는 사용자가 물어볼 때만 제안합니다.
