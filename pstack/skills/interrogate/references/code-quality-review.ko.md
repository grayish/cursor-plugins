# 코드 품질 리뷰

각 리뷰어는 루브릭에 더해 이 코드 품질 관점을 적용합니다. 이것은 구현 품질, 유지보수성, 추상화 품질, 코드베이스 건강에 초점을 둔 엄격한 기준입니다.

무엇보다 코드 구조에 대해 야심차게 접근하세요. 국소적인 정리 거리를 찾는 데 그치지 않습니다. 동작은 유지하면서 구현을 극적으로 더 단순하고, 작고, 직접적이고, 우아하게 만드는 재구성, 즉 "code judo" 수를 적극적으로 찾으세요.

## 핵심 프롬프트

다음 기본 프롬프트에서 시작합니다.

> 현재 브랜치의 변경 사항에 대해 깊이 있는 코드 품질 감사를 수행하세요.
> 동작에 영향을 주지 않으면서 코드 품질을 의미 있게 개선할 수 있도록 변경 사항을 어떻게 구조화하고 구현할지 다시 생각하세요.
> 추상화와 모듈성을 개선하고, 스파게티 코드를 줄이고, 간결성과 가독성을 높이도록 노력하세요.
> 야심차게 접근하세요. 코드베이스 일부를 재구성하는 것을 포함해 구현을 개선할 명확한 길이 있다면 그렇게 하세요.
> 매우 철저하고 엄밀하게 하세요. 실행하기 전에 두 번 확인하세요(measure twice, cut once).

## 차원

각 차원은 한 번씩만 서술합니다. 관련 있는 차원을 적용하세요.

0. **구조적 단순화에 대해 야심차게 접근합니다.** "이건 조금 더 깔끔해질 수 있겠네"에서 멈추지 마세요. 브랜치, 헬퍼, 모드, 조건문, 계층 전체를 사라지게 만드는 관점 전환을 찾으세요. "code judo" 수가 대개 존재한다고 가정하세요. 그런 수는 기존 아키텍처를 더 효과적으로 활용하고 변경을 극적으로 단순하게 만듭니다. 복잡성을 재배치하는 대신 삭제할 수 있다면 그 방향으로 강하게 밀어붙이세요.

1. **PR이 1천 줄 미만인 파일을 1천 줄 넘게 만드는 것을 매우 강한 이유 없이 허용하지 않습니다.** 이것을 강한 악취(smell)로 취급하세요. 헬퍼, 하위 컴포넌트, 모듈로 추출하는 쪽을 선호하세요. diff가 그 기준을 넘으면 코드를 먼저 분해해야 하는지 물으세요. 설득력 있는 구조적 이유가 있고 결과 파일이 명확하게 정리된 상태로 유지되는 경우에만 예외로 합니다.

2. **기존 코드에서 스파게티처럼 얽히며 커지는 것을 허용하지 않습니다.** 새로 추가된 임시방편 조건문, 여기저기 흩어진 특수 사례, 관련 없는 흐름에 끼워 넣은 일회성 분기를 의심하세요. "이상한 곳에 들어간 이상한 if 문"을 스타일 지적이 아니라 설계 문제로 취급하세요. 기존 경로를 얽히게 만드는 대신 로직을 전용 헬퍼, 상태 머신, 모듈로 옮기는 쪽을 선호하세요.

3. **동작하는 코드를 그냥 받아들이기보다 설계를 정리하는 쪽으로 기웁니다.** 동작을 그대로 유지하면서 구조를 의미 있게 깔끔하게 만들 수 있다면 더 깔끔한 버전을 요구하세요. 같은 복잡성을 여기저기 퍼뜨리는 리팩터링보다 움직이는 부품을 없애는 단순화를 선호하세요.

4. **꼼수나 마법 같은 코드보다 직접적이고 평범하며 유지보수하기 쉬운 코드를 선호합니다.** 깨지기 쉽거나, 임시방편이거나, "마법 같은" 동작을 문제로 취급하세요. 단순한 데이터 형태 가정을 숨기는 범용 메커니즘을 의심하세요. 명확성을 얻지 못하면서 간접 단계만 더하는 얇은 추상화, 항등 래퍼, 단순 전달 헬퍼를 지적하세요.

5. **유지보수성에 영향을 줄 때는 타입과 경계의 깔끔함을 요구합니다.** 더 명확한 타입 경계가 가능한데도 불필요한 선택적 값(optional), `unknown`, `any`, 캐스트가 많은 코드가 있다면 문제를 제기하세요. 형태가 느슨한 임시 객체보다 명시적인 타입 모델을 선호하세요. 어떤 분기가 불명확한 불변 조건을 덮기 위해 조용한 폴백(fallback)에 의존한다면 그 경계를 명시적으로 만들어야 하는지 물으세요.

6. **로직은 정식(canonical) 계층에 두고 기존 헬퍼를 재사용합니다.** 기능 로직이 공유 경로로 새어 나가거나 구현 세부 사항이 API를 통해 새어 나가는 경우를 지적하세요. 맞춤형 일회성 코드보다 기존의 정식 유틸리티를 선호하세요. 어긋남을 당연하게 받아들이지 말고 코드를 올바른 패키지, 서비스, 모듈로 옮기도록 요구하세요.

7. **더 깔끔한 구조가 명백할 때는 불필요한 순차적 오케스트레이션과 원자적이지 않은 업데이트를 설계 악취로 취급합니다.** 독립적인 작업이 이유 없이 직렬로 실행된다면 병렬로 실행해야 하는지 물으세요. 관련된 업데이트들이 상태를 반쯤 적용된 채로 남길 수 있다면 더 원자적인 구조를 요구하세요. 미세 최적화에 지나치게 집중하지는 않되, 코드를 더 깨지기 쉽게 만드는 피할 수 있는 오케스트레이션 복잡성은 지적하세요.

## 출력 기대 사항

구조적인 코드 품질 회귀와 놓친 단순화를 가장 먼저 다루고, 그다음 스파게티와 분기 복잡성, 그다음 경계, 타입, 파일 크기 문제, 그다음 더 작은 모듈성과 가독성 문제를 다룹니다.

## 승인 기준

동작이 올바른 것처럼 보인다는 이유만으로 승인하지 않습니다. 작성자가 정당화하지 못하는 한 다음을 사실상 차단 사유로 취급합니다. PR이 code-judo 수로 삭제할 수 있는 부수적인 복잡성을 많이 유지하는 경우입니다. 1000줄 미만인 파일을 1000줄 넘게 만드는 경우입니다. 기존 흐름을 얽히게 만드는 임시방편 분기를 추가하는 경우입니다. 기능 검사를 공유 코드 곳곳에 흩뿌리는 경우입니다. 불필요한 추상화, 래퍼, 캐스트가 많은 계약을 추가하거나, 명확한 정식 위치가 있는데도 기존 헬퍼를 중복하거나 로직을 잘못된 계층에 두는 경우입니다. 이런 조건에 해당하지 않으면 명시적이고 실행 가능한 피드백을 남기고 더 깔끔한 분해를 요구하세요.

## 리뷰 어조

품질에 대해 직접적이고 진지하며 까다롭게 대하세요. 무례하게 굴지는 않되, 주요 유지보수성 문제를 가벼운 제안으로 누그러뜨리지 마세요. 코드가 코드베이스를 더 지저분하게 만들고 있다면 그렇다고 말하세요. 구현이 명백하고 극적인 단순화를 놓쳤다면 그것도 말하세요. 진짜 문제가 구조적인데 "이름을 바꾸는 게 좋겠어요" 정도로 만족하지 마세요.
