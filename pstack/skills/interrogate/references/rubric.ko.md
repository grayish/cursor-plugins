# 리뷰 기준표

관련 있는 관점을 골라 리뷰합니다. 모든 관점이 모든 변경에 적용되지는 않습니다.

## 정확성

코드가 의도한 동작을 실제로 수행하는지 확인합니다.

- 엣지 케이스: 빈 입력, nil/undefined, 경계값, 동시 접근
- 오류 처리: 오류를 잡는지, 전파하는지, 아니면 조용히 삼키는지
- off-by-one, 타입 강제 변환, 정수 오버플로, 문자열 인코딩
- 상태 관리: 경쟁 조건, 오래된 클로저, 댕글링 참조
- 정상 경로와 실패 경로가 모두 동작하는지
- 멱등성: 이 작업이 두 번 실행되거나 이전 실행이 중간에 중단되었다면 어떻게 되는지 확인합니다. 답이 "남아 있는 상태에 따라 다르다"라면 상태를 맞추는 조정 단계가 빠져 있는 것입니다.
- 동시성: 여러 주체가 같은 가변 상태(파일, 브랜치, 공유 데이터)를 건드릴 수 있다면, 접근이 구조적으로(락, 순차 단계, 배타적 소유권) 직렬화되어 있는지, 아니면 지켜지지 않을 관례에 기대고 있는지 확인합니다.

잠재적 버그를 발견하면 실행 경로를 추적합니다. "이 값이 nil일 수 있다"라고 지적하는 데서 그치지 않고, 그 값을 nil로 만드는 호출 체인을 보여 줍니다.

## 근본 원인과 증상

코드가 실제 문제를 고치는지, 아니면 증상만 덮는지 확인합니다.

이 질문에 답하려면 변경된 파일 밖을 살펴봐야 하는 경우가 많습니다. 주변 코드(호출하는 쪽, 호출되는 쪽, 타입 정의, 인접 모듈)를 읽고 변경이 놓인 아키텍처를 이해합니다. 변경이 올바른 계층을 다루는지 판단하기 전에, 사용할 수 있는 도구(Read, Grep, Glob)로 호출 체인을 따라가고 타입을 읽고 코드가 존재하는 이유를 이해합니다.

- 더 깊은 불변 조건 위반을 가리는 가드 절
- 깨진 계약을 숨기는 재시도 로직
- 모델링 오류를 묵살하는 타입 캐스트
- 우회책: 왜 필요한지, 제대로 고치면 어떤 모습일지 확인합니다
- 사실은 모듈 B의 계약을 고쳐야 하는데 모듈 A에서 한 수정
- 구조가 더 나은 곳에 쓰인 지시문: 수정 내용이 "X를 하지 마세요"라는 주석이거나 누군가 기억해야 하는 관례라면, 잘못된 동작을 불가능하게 만드는 타입 제약, 린트 규칙, 런타임 검사로 바꿀 수 있는지 묻습니다

## 구조적 무결성

코드가 속한 시스템에 잘 맞는지 확인합니다.

- 경계 규율: 검증이 시스템 경계에 있는지, 아니면 비즈니스 로직 곳곳에 흩어져 있는지 확인합니다. 데이터가 시스템에 들어오는 지점에서 한 번 검증하고, 내부에서는 그 데이터를 신뢰합니다.
- 추상화 수준: 코드가 상위 수준의 조율과 하위 수준의 세부 사항을 섞고 있는지 확인합니다.
- 결합도: 이 변경이 향후 변경을 어렵게 만들 의존성을 들여오는지 확인합니다.
- 데이터 모델 적합성: 데이터 구조가 실제 접근 패턴과 맞는지 확인합니다.
- 덧붙임과 통합: 새 요구 사항을 처음부터 알았다면 코드가 이런 모습이었을지, 아니면 변경이 기존 설계에 덧댄 것처럼 느껴지는지 확인합니다.
- 레거시 이중 경로: 변경이 새 API를 들여오면서 옛 API도 살려 두는지 확인합니다. 외부 소비자가 없다면 같은 작업 단위에서 호출하는 쪽을 옮기고 옛 경로를 삭제합니다. 영구적으로 남게 될 호환성 계층을 두지 않습니다.

단순한 코드에 추상화가 없다고 감점하지 않습니다. 섣부른 추상화는 중복보다 나쁩니다.

## 검증

코드를 읽고 이 코드가 동작한다는 것을 알 수 있는지 확인합니다.

- 테스트가 있는지, 테스트가 동작을 검사하는지 아니면 구현 세부 사항을 검사하는지 확인합니다.
- 회귀를 잡아낼 단언이나 불변 조건이 있는지 확인합니다.
- 버그 수정이라면 그 버그에 대한 테스트가 있는지 확인합니다.
- 통합 경계를 건드린다면 전체 경로를 테스트하는지 확인합니다.
- 대리 지표가 아니라 실제 대상을 확인합니다. 코드가 실제 값을 읽지 않고 파일 mtime이나 캐시된 상태로 활성 여부를 확인한다면, 그것은 검증 공백입니다.
- 위임된 작업이나 비동기 작업이라면, 코드가 실제 산출물을 검증하는지, 아니면 자체 보고와 요약을 그대로 신뢰하는지 확인합니다.

## 복잡도 예산

코드가 달성하는 일에 비해 복잡도가 정당한지 확인합니다.

- 정확성이나 명확성을 잃지 않고 더 단순해질 수 있는 코드
- 호출 지점이 하나뿐인 추상화
- 아직 존재하지 않는 경우를 위한 설정이나 매개변수화
- 죽은 코드, 사용하지 않는 import, 흔적만 남은 매개변수
- 과잉 설계: 현재 호출하는 쪽이 없는 "만약을 위한" 코드 경로
- 더 이상 필요 없는 전환기 안정성을 위해 살려 둔 낡은 호환성 경로. 마이그레이션이 끝났다면 임시 구조물을 삭제합니다
- 사용자 경험이 복잡도를 정당화하는지 확인합니다. 모든 기능, 컨트롤, 옵션은 존재할 이유가 있어야 합니다. 반쯤 완성된 기능은 아예 없는 기능보다 나쁩니다.

더 단순한 쪽이 틀리지 않는 한, 더 단순한 쪽이 낫습니다.

## 보안

보안 관련 발견 사항마다 코드 안에서 입력 경로를 추적해 보여 줍니다.

- 정제 없이 위험한 싱크(SQL, shell, eval, innerHTML)로 흘러가는 사용자 입력
- 새 엔드포인트의 인증/인가 공백
- 코드, 로그, 오류 메시지에 들어 있는 비밀 정보
- 보안상 중요한 경로의 TOCTOU(time-of-check-time-of-use, 확인 시점과 사용 시점 사이의 경쟁)
