# Interrogate

설정된 모델마다 리뷰어를 하나씩 띄워 코드 변경을 적대적으로 리뷰하게 합니다. 적대적 신호는 할당된 페르소나가 아니라 모델의 다양성에서 나옵니다. 결과물은 종합된 판정입니다. 변경 사항을 자동으로 적용하지 마세요.

## 1단계, 범위

맥락에서 무엇을 리뷰할지 파악합니다.

- 사용자가 특정 파일이나 diff를 가리키면 그것을 사용합니다.
- 기능 브랜치에 있다면 전체 변경 집합을 얻기 위해 `git diff main...HEAD`(또는 적절한 기준 브랜치)를 실행합니다.
- 사용자 메시지가 최근 작업을 언급하면 관련 파일을 모읍니다.

diff나 파일 내용을, 리뷰어가 코드를 이해하는 데 필요한 주변 맥락 파일과 함께 묶습니다.

## 2단계, 의도

리뷰어를 띄우기 전에 사용자 메시지, 커밋 메시지, PR 설명(있는 경우), 코드를 바탕으로 의도를 명확한 한 단락으로 정리합니다. 의도가 확실하지 않으면 진행하기 전에 사용자에게 묻습니다.

## 3단계, 리뷰어 띄우기

Task 도구로 모든 리뷰어를 한 메시지 안에서 실행합니다. `~/.cursor/rules/pstack-models.mdc`의 `interrogate reviewers` 줄에 있는 항목마다 하나씩 띄우고, 항목 수에 맞추어 Reviewer A, B 같은 식으로 이름을 붙입니다. 규칙 파일이나 그 줄이 없으면 표의 기본값을 사용합니다.

| 서브에이전트 | 기본 모델 |
|----------|---------------|
| Reviewer A | `claude-opus-5-5-xhigh` |
| Reviewer B | `grok-4.7-xhigh-fast` |

각 리뷰어에는 `subagent_type: generalPurpose`, `readonly: true`를 지정하고, `model`은 설정된 항목으로, 설정된 줄이 없으면 표의 기본값으로 지정합니다. `auto` 또는 `inherit-parent` 항목이면 `model`을 생략해 그 리뷰어가 부모 모델로 실행되게 합니다.

Task 도구가 설정된 항목을 거부하면, 그 리뷰어를 해당 계열의 표 기본값으로 실행하고 그 사실을 알립니다. 계열은 접두사로 구분합니다. `claude-*`가 한 계열이고, `grok-*`는 `cursor-grok-*`, `composer-*`와 같은 계열입니다. 거부된 `composer-*` 항목은 Reviewer B의 기본값으로 실행합니다. 맞는 계열이 없으면 Reviewer A의 기본값을 사용합니다. 표 기본값이 거부되면, 오류 메시지에 나온 유효한 슬러그 가운데 가장 가까운 것(같은 계열과 같은 추론 단계를 우선합니다)으로 띄우고, 기본값 표를 갱신하는 PR을 따로 엽니다. 슬러그 문제 때문에 리뷰를 멈추지 마세요. 별칭 항목을 거부된 슬러그로 취급하거나 별칭 항목에 두 대체 방식 중 어느 것도 적용하지 마세요.

`references/reviewer-prompt.md`를 읽고, 모든 리뷰어에게 같은 템플릿을 채워 줍니다. 템플릿에는 정리한 의도, diff 또는 파일 내용, `references/rubric.md`의 기준표, `references/code-quality-review.md`의 코드 품질 관점을 넣습니다. 각 서브에이전트의 추론 수준과 빠른 속도 또는 표준 속도는 **poteto-mode** 스킬의 Subagents 섹션에 따라 작업에 맞게 고릅니다.

## 4단계, 종합

결과가 돌아오는 대로 하나로 통합된 그림을 만듭니다. 모든 리뷰어의 발견 사항을 파싱합니다. 같은 문제를 다르게 표현한 발견 사항은 합치고, 각 문제를 어느 모델이 제기했는지 기록합니다. 두 개 이상의 모델이 독립적으로 제기한 발견 사항이 가장 강한 신호입니다. 한 모델만 제기한 발견 사항도 읽되, 그에 맞게 비중을 낮춥니다. 의견이 갈린 부분도 기록합니다. 한 모델이 어떤 점을 지적하고 다른 모델이 명시적으로 반대 의견을 냈다면, 그것은 판정에 참고할 맥락입니다.

## 5단계, 리드 판단

여러분은 중립적인 집계자가 아니라 실용적인 시니어 엔지니어로서 리드 리뷰어 역할을 맡습니다. 전체 판단 틀은 `references/lead-judgment.md`를 읽어 확인합니다. 모든 발견 사항을 네 가지 분류 중 하나에 넣고, 그 사항을 제기한 모델과 한 줄짜리 근거를 함께 적습니다.

- **Act on**. 실제 목표를 고려할 때 정확성, 보안, 유지보수성에 영향을 주는 실제 문제입니다. 실제 PR이라면 머지를 막을 수준입니다.
- **Consider**. 타당하지만 지금 해결하는 비용보다 중요한지 확신할 수 없는 사항입니다. 사용자가 살펴볼 가치가 있습니다.
- **Noted**. 기술적으로는 타당하지만 조치할 수 없는 사항입니다. 상황에 따라 달라지거나, 섣부른 최적화이거나, 현재 단계에서는 영향이 작은 경우입니다.
- **Dismissed**. 틀렸거나, 사소한 트집이거나, 맥락을 놓친 사항입니다. 짧은 이유를 함께 적습니다.
