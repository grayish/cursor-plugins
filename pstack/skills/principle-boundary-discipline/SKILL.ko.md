# 경계 규율

검증, 타입 좁히기, 오류 처리는 시스템 경계에 둡니다. 내부 코드는 무조건 신뢰합니다. 비즈니스 로직은 순수 함수에 둡니다. 바깥 껍데기(shell)는 얇고 기계적으로 유지합니다.

**이유:** 여기저기 흩어진 검증은 코드를 어지럽히고, 중복되며, 안전하다는 착각을 줍니다. 로직을 프레임워크 연결 코드 밖에 두어야 프레임워크 없이도 테스트할 수 있습니다.

**패턴:**
- **경계에서는** (CLI 인자, 설정 파일, 외부 API, 네트워크 프로토콜): 검증하고, 오류를 반환하고, 방어적으로 처리합니다.
- **시스템 내부에서는:** 타입이 있는 데이터를 사용하고, 오류를 전파하며, 다시 검증하지 않습니다. 타입을 신뢰합니다.
- **경계를 넘을 때는:** 경계 내부의 표현이 아니라 도메인 개념을 노출합니다. 범용 메커니즘은 안쪽에 두고, 특수 목적의 정책은 가장자리에 둡니다.

**적용 사례:**

검증과 오류 처리:
- 설정은 비즈니스 로직 안이 아니라 파싱 시점(경계)에 검증합니다
- 원시 데이터는 경계에서 도메인 타입으로 파싱합니다
- 전송, 저장소, 프레임워크, 와이어(wire) 타입을 공개 인터페이스를 통해 다시 내보내지 않습니다
- 경계에서 이미 검증했다면 호출 체인 깊은 곳에서 중복된 nil 검사를 하지 않습니다

코드 구성:
- 비즈니스 로직은 프레임워크 의존성이 없는 순수 함수에 둡니다
- 파싱 함수는 원시 바이트를 타입이 있는 상태로 바꾸는 순수 변환으로 만듭니다
- 프롬프트 구성은 구조화된 상태를 받아 문자열을 내보내는 방식으로 만듭니다
- 점수 계산과 평가는 상태를 결과로 바꾸는 순수 변환으로 만듭니다

**판별 질문:**
- "이 데이터가 지금 시스템 경계를 넘고 있는가?" 그렇지 않다면 검증은 중복입니다.
- "이것을 바깥 껍데기가 호출만 하면 되는 순수 함수로 만들 수 있는가?" 그렇다면 추출합니다.
