# Figure it out

작업에 맞는 플레이북이 없으면 플레이북을 설계합니다. 코드보다 먼저 나와야 하는 결과물은 워크플로 자체입니다. 즉, 작업에 맞게 엄밀함의 수준을 조절하고, 과학적 방법을 실행하며, 사람(사용자)이 자리를 비웠다가 돌아와 감사할 수 있는 결정 기록을 남기는 일련의 단계입니다.

## 시작

할 일 목록을 열고, 첫 항목으로 **poteto-mode** 스킬의 Principles 섹션 읽기를 넣습니다. 그런 다음 아래 단계들을 할 일로 추가합니다.

## Phase A: 틀 잡기

먼저 근거를 파악하고, 그다음에 확정합니다. 다음을 말할 수 있기 전에는 실행을 시작하지 않습니다.

- 반증 가능한 조건으로 표현한 완료의 정의(**prove-it-works** 원칙 스킬)
- 정량화한 범위: 대략적인 작업 단위와 노력, 그리고 근거 파악 과정에서 드러난 차단 요소
- 높은 쪽으로 기울인 엄밀함 수준: 되돌릴 수 없는 결정과 영향 범위(blast radius)가 큰 작업에는 더 높은 수준을 적용합니다. 되돌릴 수 있고 위험이 낮은 단계에는 더 낮은 수준을 적용합니다. 엄밀함이란 "더 열심히 하기"가 아니라 관문(gate)과 산출물을 뜻합니다.

긴 실행을 확정하기 전에 틀과 트레이드오프를 제시합니다. 되돌릴 수 있는 작업은 계속 진행하지만(**never-block-on-the-human** 원칙 스킬), 몇 시간짜리 실행이라면 확인 지점을 한 번 둘 만합니다.

## Phase B: 워크플로 설계

작업을 원자적이고 독립적으로 반영할 수 있는 단위로 나눕니다. 가장 위험한 미지수부터 먼저 처리하도록 순서를 정합니다. 기반 구조와 검증이 기능보다 먼저 옵니다(**foundational-thinking** 원칙 스킬).

- 작업보다 먼저 검증 하네스를 만들고, 변경 전 상태에서 기준값을 수집해 두어서 확인 결과를 "이전 값 대 새 값"으로 읽을 수 있게 합니다.
- 되돌릴 수 없는 설계 결정에는 **architect** 스킬을 실행합니다(이 스킬은 **arena**를 실행합니다). 형태가 이미 구체적인 기계적 작업에는 생략합니다. 이미 정해진 설계에 arena를 한 번 더 돌리는 것은 과잉 설계입니다(**laziness-protocol** 원칙 스킬).
- 무엇을 병렬로 분산할지 결정합니다. 경계가 분명한 부분 사이에서만 병렬화하고, 각 작업자에게 별도의 워크트리나 브랜치를 줍니다(**separate-before-serializing-shared-state** 원칙 스킬). 지나치게 분산하지 않습니다. **poteto-mode** 스킬의 Subagents 섹션에 따라, 작업에 맞게 각 서브에이전트의 추론 수준과 fast 또는 standard 속도를 고릅니다.
- 설계한 단계 목록을 기록합니다. 사람(사용자)이 리뷰하는 것은 그 목록입니다.

그런 다음 설계를 실행합니다. 설계의 단계들을 할 일 목록의 Phase C와 Phase D 항목 사이에 구체적인 항목으로 추가합니다. 각 단계를 Phase C의 루프 규율에 따라 실행하고, 전체 기록을 마지막에 몰아서 남기지 말고 각 단계가 반영될 때마다 한 행씩 Phase D 로그를 함께 작성합니다.

## Phase C: 루프 실행

각 단위는 하나의 실험입니다. 가설을 세우고, 가장 작은 변경을 가하고, 실제 산출물을 대상으로 완료 조건에 비추어 측정하고, 진전이 있으면 유지하고 없으면 되돌립니다. **sequence-verifiable-units** 원칙 스킬을 적용해, 확인을 마지막에 몰아서 하지 말고 각 단위를 검증한 뒤에 다음 단위를 시작합니다.

- 자체 보고가 아니라 산출물을 직접 살펴서 검증합니다. 무언가가 너무 쉽게 통과하면 시스템보다 관찰 방법을 먼저 의심합니다.
- 위임한 작업에는 판정자를 붙입니다. 작업자가 관문을 편법으로 통과하면 초기화하고 계약을 강화합니다. 관문 자체가 잘못되었다면 우회하지 말고 별도의 변경으로 관문을 고칩니다.
- 판정은 VERIFIED, NOT VERIFIED, INCONCLUSIVE 중 하나입니다. INCONCLUSIVE는 통과가 아닙니다. 부정적인 결과를 숨기지 않습니다.

## Phase D: 감사 기록 유지

**show-me-your-work** 스킬로 실행 과정을 기록합니다. figure-it-out의 작업은 대개 충분히 규모가 크므로, 리뷰어가 PR에서 읽을 수 있도록 기록을 커밋합니다. 사람(사용자)이 돌아와서 작업을 신뢰할 수 있게 해 주는 것은 이 기록과 diff입니다.

## Phase E: 검증 후 넘겨주기

하네스만이 아니라 실제 제품에서 전체 결과를 Phase A의 완료 조건에 비추어 확인합니다. 반복되는 수정 사항은 관문, lint 규칙, 확인 절차, 스크립트로 구조화합니다(**encode-lessons-in-structure** 원칙 스킬).

**답변:** 설계한 플레이북, 엄밀함 수준과 그 이유, 결정 기록의 경로, 완료 조건에 비추어 검증된 내용, 아직 해결되지 않은 내용을 알립니다.
