# 타입 시스템 규율

불가능한 상태, 맞지 않는 원시 타입, 처리되지 않은 변형을 컴파일러가 거부하도록 만듭니다. 핸들러를 늘리기보다 오류와 특수 사례가 애초에 존재하지 않도록 정의하는 편을 선호합니다. TypeScript 문법은 `typescript-best-practices` 스킬을 참고하세요.

- **의미 있는 원시 타입에 브랜드를 붙입니다.** `UserId`와 `OrderId`는 내부적으로 문자열이지만 서로 바꿔 쓸 수 있어서는 안 됩니다. TypeScript의 브랜드 교차 타입이나 다른 언어의 newtype처럼 각각에 고유한 타입을 부여합니다. 생성 시점에 한 번 검증하고, 이후에는 타입을 신뢰합니다. 두 인자가 같은 원시 타입을 공유하지만 의미가 다르다면 브랜드를 붙입니다.
- **외부 데이터는 파싱하기 전까지 타입이 없습니다.** RPC 페이로드, JSON, IPC 메시지, CLI 인자, 설정 파일, 환경 변수, 데이터베이스 행이 여기에 해당합니다. 모든 경계에 비정형 입력을 타입이 있는 모델로 바꾸는 파싱 함수를 둡니다. 검증을 어디에 둘지는 **boundary-discipline** 원칙 스킬이 알려 줍니다.
- **권위 있는 스키마에서 타입을 도출합니다.** protocol buffer, OpenAPI 명세, GraphQL 스키마, 데이터베이스 마이그레이션, 디자인 토큰 파일 등 다른 파일이 어떤 형태를 소유하고 있다면, 병렬 타입을 손으로 만들지 말고 그 파일에서 도출합니다. **encode-lessons-in-structure** 원칙 스킬을 참고하세요.
