# 결과를 검증하고 PR 열기

"컴파일된다"는 증거가 아닙니다. [Prove It Works 원칙](../../skills/principle-prove-it-works/SKILL.md)은 에이전트가 성공을 보고하기 전에 실제 산출물을 확인하게 만들고, 여러분이 할 일은 그 "실제 산출물"을 확인 가능한 상태로 만드는 것입니다. 이 페이지에서는 완료 조건을 명시하는 방법, 측정한 수치를 점검하는 방법, 앱을 위한 검증 스킬을 생성하는 방법, 테스트가 거의 닿지 않는 속성을 형식 검증하는 방법, PR을 여는 방법, 그리고 PR을 머지까지 끌고 가는 방법을 다룹니다.

대부분의 에이전트 작업에서 검증은 가장 느린 단계입니다. 보통 사람(사용자)을 기다려야 하는 단계이기 때문입니다. 에이전트가 검증을 직접 할 수 있게 만들면 여러분이 병목이 되지 않습니다. 검증을 건너뛰면 에이전트를 더 많이 돌려도 리뷰해야 할 미확인 작업만 늘어납니다.

![시제품 비행기가 실제 시험 코스를 비행하는 동안 그녀는 스톱워치로 시간을 재고, 로봇들은 비행을 촬영하며 체크리스트를 확인합니다. 터미널에는 verify: pass, evidence: captured라고 표시되어 있습니다.](./images/verification.jpg)

## 완료 조건을 미리 명시하기

완료가 무엇을 뜻하는지 첫 프롬프트에 적습니다. 표현은 상황에 맞게 자유롭게 하면 됩니다.

```text
/poteto-mode 이 명령에 json 출력을 추가해줘. 텍스트 출력은 바이트 단위로 동일하게 유지되고, json은 파싱되어야 하고, 둘 다 샘플 프로젝트에 대해 실행해야 해. 증거를 보여줘.
```

이제 에이전트에게는 막연히 만족시켜야 할 기분이 아니라 실행할 수 있는 확인 항목 세 가지가 생깁니다. 응답이 돌아오면 그 안에는 정확한 명령어와 출력이 담겨 있어야 합니다. 확인을 실행할 수 없었다면 좋은 응답은 "inconclusive(결론 없음)"라고 말합니다. 증거 없이 자신만만한 응답은 경고 신호입니다.

변경 종류에 맞는 확인을 고릅니다.

- CLI 변경은 실제 명령을 실행합니다.
- UI 변경은 실행 중인 앱에서 바뀐 흐름을 직접 따라가 봅니다. 참조 화면과 픽셀 단위로 일치해야 할 때는 [Visual parity 플레이북](../../skills/poteto-mode/playbooks/visual-parity.md)이 눈으로 판단하는 대신 고정된 기준 스크린샷과 비교해 차이를 찾습니다.
- 파서나 마이그레이션은 저장해 둔 입력을 다시 재생합니다.
- 성능 변경은 변경 전후 프로파일을 비교합니다.
- 스토리지 변경은 기록한 값을 다시 읽어 봅니다.

증거는 여러분이 직접 살펴볼 수 있는 산출물 형태로 요청합니다. 실패하는 테스트와 그다음 통과하는 테스트, 변경 전후 영상, 트레이스, 스크린샷 같은 것입니다. 수정이 이미 머지되었다면 main에서 같은 확인을 다시 요청합니다. 산출물은 그럴듯한 설명보다 낫습니다. 전체 실행을 다시 돌려 보지 않고도 산출물을 근거로 따져 물을 수 있기 때문입니다.

완전히 믿기 어려운 작은 diff에는 [`/blast-radius`](../../skills/blast-radius/SKILL.md)가 그 변경이 다른 곳에서 무엇을 망가뜨릴 수 있는지 찾아냅니다. 이 스킬은 변경을 안전하게 만드는 단 하나의 사실을 찾고, 그 사실을 논증이 아니라 코드를 실행해서 증명합니다.

## `/benchmark-checklist`로 측정한 수치 점검하기

변경 전후 수치는 실수로 틀리기 가장 쉬운 증거입니다. 캐시가 데워져 있었거나, 한쪽만 디버그 빌드였거나, 작업이 측정 구간 안에서 실제로 실행되지 않았다면, 각각의 경우 모두 그럴듯한 속도 향상이 나올 수 있습니다. 수치를 보고하거나 그 수치에 따라 행동하기 전에 다음을 입력합니다.

```text
/benchmark-checklist pr에 넣기 전에 export 속도 향상을 점검해줘
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)는 일곱 가지 질문을 던지고, 각 질문마다 실행에서 얻은 증거를 요구합니다.

1. 무엇이 이 수치를 제한하며, 왜 두 배가 아닌가?
2. 모든 쪽이 프로덕션과 같은 방식으로 튜닝된 상태로 실행되었는가?
3. 결과가 디스크 대역폭이나 코어 수 같은 물리적 한계를 넘어서는가?
4. 오류가 나거나 잘못된 출력을 반환한 것이 있는가?
5. 번갈아 실행했을 때 중앙값과 범위를 갖고 재현되는가?
6. 사용자가 기다리는 경로에서 처음부터 끝까지 봤을 때 의미가 있는가?
7. 작업이 실제로 측정 구간 안에서 일어났는가?

판정은 빨라짐, 느려짐, 측정 가능한 차이 없음, 결론 없음 중 하나로 나오며, 실행 횟수, 범위, 제한 요인이 함께 제시됩니다. 제한 요인을 지목하지 못하거나 한쪽이 튜닝되지 않은 상태로 실행되었다면 결론 없음이라고 말합니다. `/poteto-mode`는 이미 Perf issue 플레이북과 Hillclimb 플레이북 안에서 이 체크리스트를 실행합니다. 따라서 그 플레이북 밖에서 무언가를 측정했을 때나 다른 사람의 수치가 너무 좋아 보일 때 직접 입력하면 됩니다. 이 스킬은 [Explain the Number 원칙](../../skills/principle-explain-the-number/SKILL.md)을 실제로 작동하는 형태로 만든 것입니다.

## 프로젝트 검증 스킬 만들기

위의 UI 항목에는 실제 요구 사항이 숨어 있습니다. 에이전트에게는 앱을 조작할 스크립트화된 방법이 필요합니다. 프로젝트에 이미 그런 방법이 있다면 좋습니다. 없다면 다음을 실행합니다.

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)은 여러분이 아니라 저장소를 인터뷰합니다. 사용자가 무엇을 만지는지, 앱이 로컬에서 어떻게 실행되는지, 무엇으로 앱을 조작할 수 있는지(먼저 기존 하네스를 찾고, 없으면 브라우저와 CDP, PTY, 또는 일반 HTTP), 어떤 증거가 동작을 증명하는지, 두 인스턴스를 나란히 실행할 수 있는지를 파악합니다. 여러분에게는 코드로 답할 수 없는 것만 묻습니다.

이 스킬은 `.cursor/skills/verify-<app>/`를 작성합니다. 여기에는 정확한 Launch, Doctor, Drive, Evidence, Cleanup 섹션을 갖춘 에이전트용 지침, 함께 제공하는 스크립트를 위한 Helpers 섹션, 그리고 앱이 무엇을 하는지와 각 기능이 작동함을 증명하는 결과가 무엇인지를 색인한 `features/` 아래의 기능 맵이 들어갑니다. 이 스킬에는 README 색인과 필수 H2 네 개를 사용하는 기능별 파일로 구성된 [기능 맵 예시](../../skills/create-verification-skill/references/feature-map-example/)가 함께 들어 있습니다. 생성기는 스킬을 넘겨주기 전에 처음부터 끝까지 한 번 증명합니다. 실행하고, doctor 검사를 하고, 기능 하나를 조작하고, 증거를 수집하고, 정리한 다음, 정리 후에도 증거가 남아 있는지 확인합니다. 이 증명이 실패하면 출력을 사용하지 않습니다.

그 뒤로는 "앱에서 검증해"가 이 저장소에서 어떤 에이전트든 별도의 설정 대화 없이 실행할 수 있는 단계가 됩니다. 증거를 특정 형태로 받고 싶을 때는 프롬프트에 스킬 이름을 적습니다.

```text
/poteto-mode 일괄 보관(bulk-archive) 액션을 만들어줘. /verify-<app>을 사용해서 변경 사항을 검증하고 증거로 영상과 스크린샷을 보여줘.
```

```text
/poteto-mode /verify-<app>으로 이걸 재현해줘. main에서 재현되면 고치고 증거로 영상을 보여줘.
```

검증 스킬이 작동하면 [`/swarm`](../../skills/swarm/SKILL.md)이 전체 검증 과정을 기능 맵 항목별로 나누고 결과를 취합할 수 있습니다. 검증자 스웜은 충분히 큰 표본으로 성능 향상을 확인하거나, PR이 배포되기 전에 앱을 퍼징해 회귀를 찾을 수도 있습니다.

검증 스킬은 일회용이 아니라 인프라로 다룹니다. 커밋해 두면 팀의 모든 사람과 모든 에이전트가 같은 방식으로 앱을 조작합니다. 그다음 [레버를 만듭니다](../../skills/principle-build-the-lever/SKILL.md). 에이전트가 앱을 클릭해 보기 위해 일회용 스크립트를 계속 작성한다면, 스킬이 대신 호출할 작은 제어용 CLI를 요청합니다. 그러면 에이전트가 쓰는 토큰이 줄고 모든 실행이 반복 가능해집니다. 에이전트가 잘 사용하는 CLI에는 다음과 같은 특징이 있습니다.

- 얇은 명령 여러 개가 아니라, 각각 실제 작업을 하는 조합 가능한 명령 몇 개
- 파괴적인 작업 모두에 있는 `--dry-run` 옵션
- 기능을 한꺼번에 드러내지 않고 점진적으로 드러내는 하위 명령
- 대신 무엇을 해야 하는지 알려 주는 오류 메시지
- 풍부한 `--help` 텍스트
- JSON 같은 기계가 읽을 수 있는 출력

이왕 하는 김에 개발 환경 설정도 반복 가능하게 만듭니다. 시드 데이터, 테스트 사용자, 그리고 매번 같은 방식으로 환경을 띄우는 명령 하나를 준비합니다.

## 검증 스킬을 정확하게 유지하기

앱은 바뀌고, 기능 맵은 낡습니다. 다음을 최소 하루에 한 번 실행합니다. 아무도 기억할 필요가 없도록 예약된 자동화에서 실행하는 것이 가장 좋습니다.

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)은 생성된 스킬을 감사합니다. 먼저 기능마다 읽기 전용 소스 리더 하나씩을 병렬로 돌리고, 그다음 매핑된 모든 기능을 조작하는 라이브 패스를 한 번 실행합니다. 결과는 세 가지 중 정확히 하나로 끝납니다. `clean`은 전체가 커버되었고 배포할 것이 없다는 뜻입니다. `changed`는 검증된 수정 사항을 담은 PR 하나가 있다는 뜻이며, 이 수정은 검증 스킬 자체의 디렉터리 안으로 한정됩니다. `blocked`는 무엇이 막고 있는지를 밝힙니다. 이 스킬은 제품 코드를 절대 수정하지 않습니다. 라이브 패스에서 제품 회귀를 발견하면 문서 수정으로 감추지 않고 회귀를 보고합니다.

## 형식 검증 스킬로 속성 증명하기

검증 스킬은 여러분이 조작하는 경로를 증명합니다. 어떤 버그는 아무도 조작하지 않는 경로에 숨어 있습니다. 겹쳐서 실행되는 두 번의 재시도, 쓰기 도중에 만료되는 락, 순서가 뒤바뀌어 도착하는 상태 변경 같은 경우입니다. 테스트는 이런 경우에 거의 닿지 않습니다. 이런 버그가 큰 비용을 낳는 코드에는 다음을 실행합니다.

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)은 코드에서 대상을 고릅니다. 대상은 코드가 지키겠다고 약속하는 것 중에서, 깨지면 사용자에게 피해가 가고 그것을 깨뜨리는 경우에 테스트가 거의 닿지 않는 것입니다. 이 스킬은 검증하기 가장 쉬운 대상이 아니라 가장 강한 대상을 고릅니다. 특정 영역이나 버그에서 시작하고 싶다면 이름을 지정합니다.

```text
/create-formal-verification-skill 작업 lease와 재시도 로직. 하나의 작업이 동시에 두 번 실행되면 절대 안 돼.
```

질문이 도구를 결정합니다. 이벤트가 잘못된 순서로 일어날 수 있는지를 묻는다면 설계를 작게 모델링한 뒤 모델 체커로 확인하는 것이 적합하며, 언어와 상관없이 TLA+가 기본 선택입니다. 코드가 모든 입력에 대해 올바르게 동작하는지를 묻는다면 코드 위에서 직접 실행되는 검증기가 적합합니다. 여러분의 언어에서 실행되는 검증기가 없다면 에이전트는 그 사실을 알리고, 함수를 손으로 모델링하는 대신 생성된 입력으로 실제 코드를 테스트합니다. 모든 크기에서 성립해야 하는 속성에는 증명이 필요할 수 있습니다. 에이전트는 어떤 도구를 골랐는지와 그 이유를 알려 줍니다.

이 스킬은 속성 하나를 검증하고, 일부러 망가뜨린 코드 변형에서 그 속성이 실패하는 모습을 보여 줍니다. 실패하는 모습을 한 번도 본 적 없는 검사는 아무것도 증명하지 못하기 때문입니다. 현재 코드가 이미 속성을 깨뜨리고 있다면 여러분의 코드 용어로 된 짧은 단계 목록 형태의 반례를 받게 됩니다. 속성은 명시된 그대로 유지되므로 발견 사항도 발견 사항으로 남습니다. 여러분이 요청하지 않는 한 제품 코드는 바뀌지 않습니다.

이 스킬은 프로젝트 로컬 스킬을 작성합니다. 이 스킬은 다음 에이전트에게 변경이 검증된 코드를 건드리는지, 명령 하나로 검사를 실행하는 방법, 그리고 실제 버그와 모델링 오류를 구별하는 방법을 알려 줍니다. 생성기는 스킬을 넘겨주기 전에 속성을 깨뜨리는 임시 변경에 대해 그 스킬을 한 번 따라 해 보며, 검사는 이를 잡아내야 합니다. 인계 내용에는 무엇을 어떤 도구와 범위(bound)로 검증했는지, 검사가 무엇을 발견했는지, 무엇을 다루지 않는지가 담깁니다. 통과는 시스템 전체가 아니라 모델이나 범위만을 보장합니다.

이 스킬은 각 검사가 어떤 코드를 다루는지와, 검사가 그 코드와 마지막으로 일치했던 커밋도 기록합니다. 스킬을 거치지 않은 머지나 리팩터링이 일어나면, 이미 사라진 코드에 대한 설명을 기준으로 검사가 계속 통과하는 상태가 될 수 있습니다. 그런 일이 있은 뒤에는 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)을 실행합니다. 이 스킬은 코드를 바탕으로 검증을 갱신하고, 다시 실행하고, 갱신된 각 검사가 여전히 실패할 수 있음을 보여 준 다음, 각 실패가 검증 쪽의 어긋남인지 코드의 버그인지를 알려 줍니다.

## PR 열기

```text
/poteto-mode pr을 열어줘. 작고 순서가 있는 커밋으로, 설명에는 증거를 넣어줘.
```

[Opening a PR 플레이북](../../skills/poteto-mode/playbooks/opening-a-pr.md)은 워크트리에서 작업하며, 작업을 작고 순서 있는 커밋들로 리베이스하고, diff를 정리하고, 글에서 슬롭(slop)을 걷어 낸 뒤 PR 링크를 반환합니다. 범위가 좁은 PR 다섯 개가 비대한 PR 하나보다 낫고, 스택으로 쌓은 후속 PR이 계속 커지는 브랜치보다 낫습니다.

## Babysit으로 PR을 머지 가능한 상태까지 끌고 가기

PR은 열리자마자 차단 요인이 쌓이기 시작합니다. 검사가 실패하고, 리뷰어가 코멘트를 달고, 트렁크가 앞서 나갑니다. 이런 번거로운 일은 [Babysit 플레이북](../../skills/poteto-mode/playbooks/babysit.md)에 넘깁니다.

```text
/poteto-mode 이 pr을 돌봐줘. 전부 통과(green)시켜줘.
```

Babysit은 GitHub용 번들 감시기나, 사용할 수 있으면 Origin CLI로 PR을 지켜보면서 차단 요인을 순서대로 처리합니다. 충돌을 먼저, 그다음 리뷰 스레드, 그다음 CI를 처리합니다. 알려진 수정은 모두 한 번의 푸시로 묶기 때문에 검사가 수정마다 다시 시작되지 않고 한 번만 다시 시작됩니다. 코멘트 분류는 회의적인 태도로 진행합니다. 사람과 봇 모두 실제로 의미 있는 지적과 잡음을 같은 목록에 올리기 때문입니다. 실제 발견 사항은 수정하고, 잡음은 반박 근거를 스레드에 남긴 뒤 무시합니다. 상태만 알고 싶을 때는 더 작게 요청하면 Babysit이 루프를 시작하지 않고 답합니다.

```text
/poteto-mode pr 123 상태 확인해줘. 남은 거 있어?
```

Babysit은 머지 가능한 상태에서 멈춥니다. 모든 것이 통과(green) 상태여도 절대 머지하지 않습니다. 머지는 별개의 결정이기 때문입니다.

## Shipping으로 스택 반영(land)하기

통과(green)는 안전과 같은 말이 아닙니다. 반영할 준비가 되면 그렇게 말합니다.

```text
/poteto-mode 스택을 반영(land)해줘.
```

[Shipping 플레이북](../../skills/poteto-mode/playbooks/shipping.md)은 무엇이든 머지 대기 상태로 걸기(arm) 전에 각 PR을 독립적으로 검증합니다. PR마다 새로운 에이전트 하나가 동작을 라이브로 증명하며, 변경을 판정하는 에이전트는 절대 그 변경을 작성한 에이전트가 아닙니다. 그런 다음 Shipping은 맨 아래부터 연속으로 검증된 PR들만 반영합니다. 기본적으로 GitHub를 통해, Origin CLI를 사용할 수 있으면 Origin을 통해 한 번에 PR 하나씩 반영하고, 연쇄를 끊는 첫 번째 PR을 보고합니다. 검증되지 않은 PR 위에 있는 검증된 PR은 기다립니다. 그 PR을 머지하면 검증되지 않은 틈이 아래로 함께 딸려 들어오기 때문입니다.
