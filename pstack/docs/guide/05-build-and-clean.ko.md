# 변경 사항을 구현하고 diff를 정리하기

> 이 문서는 [05-build-and-clean.md](./05-build-and-clean.md)을 한국어로 번역한 문서입니다. 원본과 내용이 다르면 원본을 기준으로 합니다.

구현 플레이북들은 하나의 작업 규율을 공유합니다. 관찰한 내용을 말하고, 증거를 요구하는 일은 플레이북에 맡깁니다. 이 페이지는 흔한 구현 작업마다 프롬프트에 무엇을 넣어야 하는지 보여 주고, 이어서 diff를 리뷰하기 쉽게 유지하는 정리 습관을 설명합니다.

## 각 구현 플레이북에 아는 내용을 담아 프롬프트하기

버그 프롬프트는 증상을 밝히고 재현을 먼저 요청합니다.

```text
/poteto-mode 이 명령이 재시도 후에 레코드를 두 개 내보내. 먼저 재현하고, 그다음에 고치고 검증해.
```

기능 프롬프트는 동작과 함께 바뀌면 안 되는 것을 밝힙니다.

```text
/poteto-mode --json 플래그를 추가해. 텍스트 출력은 바이트 단위로 동일하게 유지해. 두 형식 모두 검증해.
```

리팩터링 프롬프트는 구조를 옮기기 전에 동작을 고정합니다.

```text
/poteto-mode 파싱을 하나의 모듈로 옮겨. 동작 변경은 전혀 없어야 해. 먼저 현재 출력을 기록하고, 옮긴 뒤에 바뀌지 않았음을 증명해.
```

성능 프롬프트는 인상이 아니라 측정값을 밝힙니다.

```text
/poteto-mode 이 fixture에서 시작에 1.8초가 걸려. 트레이스를 뜨고, 측정된 원인을 고치고, 전후 결과를 보여 줘.
```

이 프롬프트들은 각각 해당 플레이북([버그 수정](../../skills/poteto-mode/playbooks/bug-fix.md), [기능](../../skills/poteto-mode/playbooks/feature.md), [리팩터링](../../skills/poteto-mode/playbooks/refactoring.md), [성능 문제](../../skills/poteto-mode/playbooks/perf-issue.md))으로 라우팅되고, 플레이북은 여러분이 입력하지 않은 단계를 채워 줍니다. 즉, 고치기 전에 재현하고, 구현하기 전에 데이터 형태를 정하고, 구조를 바꾸기 전에 동작을 고정하고, 최적화하기 전에 프로파일링합니다.

하나의 수치를 꾸준히 개선하려면 [Hillclimb 플레이북](../../skills/poteto-mode/playbooks/hillclimb.md)이 있습니다. 지표, 목표치, 최소 시도 횟수를 주면, 이 플레이북은 고정된 측정 하네스로 한 번에 가설 하나씩 반복합니다. 개선된 결과는 유지하고 나머지는 모두 되돌립니다.

두 성능 플레이북은 모두 자신이 얻은 수치에 [`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)를 실행합니다. Perf issue 플레이북은 기준선과 그 이후의 모든 수치를 점검하고, Hillclimb 플레이북은 하네스를 고정하기 전에 하네스를 점검합니다. 이 스킬을 직접 입력해야 하는 경우는 [검증하고 배포하기](./06-verify-and-ship.md#vet-a-measured-number-with-benchmark-checklist)에서 설명합니다.

때로는 수정하기 전에 원인부터 알고 싶을 때가 있습니다. 메모리 누수, 유휴 상태의 CPU 과점유, 화면 깨짐처럼 지금 나타나는 증상이라면 [Runtime forensics 플레이북](../../skills/poteto-mode/playbooks/runtime-forensics.md)이 실행 중인 프로세스를 계측합니다. 이미 수집한 프로파일이 있다면 [Trace forensics 플레이북](../../skills/poteto-mode/playbooks/trace-forensics.md)이 그 산출물을 읽고 가장 많은 시간을 쓰는 프레임을 소스에 대응시킵니다. 두 플레이북 모두 수정이 아니라 진단을 돌려줍니다.

```text
/poteto-mode 느린 시작 과정에서 뜬 cpuprofile이야. 시간이 어디에 쓰이는지, 어떤 소스 줄이 그 시간을 차지하는지 알려 줘. 아직 고치지는 마.
```

## `/tdd`로 실패하는 테스트를 먼저 작성하기

버그를 로컬에서 저렴하게 테스트할 방법이 있다면, 프롬프트 전체가 두 단어로 충분할 수 있습니다.

```text
/tdd 구현해
```

맥락이 있으면 이것으로 충분합니다. [`/tdd`](../../skills/tdd/SKILL.md)는 의도한 이유로 실패하는 가장 작은 테스트를 작성하고, 이어서 수정을 작성한 다음, 테스트를 다시 실행합니다. 테스트에 광범위한 하네스 설정이나 깨지기 쉬운 mock이 필요하다면, 스킬은 그렇다고 알리고 대신 가장 가까운 실행 가능한 검사를 사용합니다. 실제 명령이 더 강한 증거가 되는 상황에서 테스트를 억지로 만들지 마세요.

## TypeScript 규칙은 이름으로 불러오기

[`typescript-best-practices`](../../skills/typescript-best-practices/SKILL.md)는 타입 시스템 원칙을 구체적인 규칙으로 바꿉니다. 판별 유니온(discriminated union), 경계에서의 `unknown`, 모든 경우를 다루는 variant 처리, 스키마에서 파생한 타입 등이 그 예입니다. 이 스킬은 자동으로 로드되지 않으므로, 작업이 `.ts`나 `.tsx` 파일을 건드릴 때는 `/typescript-best-practices`를 입력하세요.

## 커밋하기 전에 정리하기

[PR 열기 플레이북](../../skills/poteto-mode/playbooks/opening-a-pr.md)은 각 커밋 전에 diff에 `/deslop`을 실행하고, PR 설명과 커밋 본문에는 [`/unslop`](../../skills/unslop/SKILL.md)을 적용합니다. `/deslop`은 pstack이 아니라 `cursor-team-kit` 플러그인에 포함되어 있습니다. 이 스킬이 없다면 같은 결과를 평범한 말로 요청하세요. 즉, 동작을 설명하기만 하는 주석, 근거 없는 가드, 쓰이지 않는 호환성 경로, 관련 없는 수정을 제거해 달라고 요청합니다.

문장에 대해서는 `/unslop`이 대상과 여러분이 가진 추가 규칙을 받습니다.

```text
/unslop readme 변경 사항, 엠대시 쓰지 마
```

여러분만의 줄임말이 생길 것입니다. 이 스킬은 `unslop that, tighten it`처럼 짧은 프롬프트에서도 의도를 잘 읽어 냅니다.

## `/no-comments`로 주석 걷어 내기

주석은 별도의 점검이 필요하며, 그 점검은 주석을 작성한 에이전트가 해서는 안 됩니다. 작성자는 여러분이 자기 주석을 옹호하듯 자기 주석을 옹호합니다. 그러므로 리뷰 전에 주석을 작성하지 않은 새로운 리뷰어에게 맡기세요.

```text
/no-comments 이 diff
```

[`/no-comments`](../../skills/no-comments/SKILL.md)는 [Comment Sicko](../../agents/comment-sicko.md)를 생성합니다. Comment Sicko는 짧은 유지 목록을 가진 읽기 전용 리뷰어이며, 유지 목록에는 라이선스 헤더, 공개 API의 문서 주석, 코드로 설명할 수 없는 내용을 설명하는 링크, 여러분이 바꿀 수 없는 외부 의존성 때문에 강제된 동작이 있습니다. 나머지는 모두 제거됩니다. 여러분 자신의 코드에 있는 의외의 부분은 이런 예외를 받지 못합니다. 그런 주석은 리팩터링 표시로 돌아오고, `/no-comments`는 받아들인 표시를 근본 원인에서 고칩니다. 주석이 "제거하지 마세요" 같은 제약을 주장하면, 스킬은 그 주장을 타입, 테스트, 또는 lint로 표현하자고 제안합니다. 어느 쪽이든 주석은 제거됩니다.

역할 분담을 분명히 구분해 둘 가치가 있습니다. `/deslop`은 코드에서 슬롭(slop)을 걷어 내고, `/unslop`은 문장에서 슬롭을 걷어 내며, `/no-comments`는 주석을 그것을 작성하지 않은 리뷰어에게 넘깁니다.

**주의할 점:** 정리는 선택적인 마무리 작업이 아닙니다. 동작을 설명하기만 하는 주석과 방어적인 불필요 코드가 있는 diff는 리뷰어에게 미완성으로 보이고, 그런 여분의 코드는 다음 버그가 숨는 곳이 됩니다. diff가 부풀려진 것처럼 느껴지면, 리뷰에서 지적받은 뒤가 아니라 커밋하기 전에 `deslop it`이라고 말하세요.
