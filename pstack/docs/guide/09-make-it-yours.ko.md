# 나만의 방식으로 만들기

> 이 문서는 [09-make-it-yours.md](./09-make-it-yours.md)를 한국어로 번역한 문서입니다. 원본과 내용이 다르면 원본을 기준으로 합니다.

poteto-mode는 한 사람의 스타일입니다. 그 밑에 있는 플레이북, 라우팅, 모델 역할은 여러분의 스타일과도 똑같이 잘 동작합니다. 이 페이지는 개인 모드를 생성하는 방법, 세션에서 얻은 교훈을 기록하는 방법, 에이전트가 같은 실수를 반복하지 않도록 저장소를 고치는 방법, 특정 목적의 스킬을 작성하는 방법, 그리고 스킬 변경을 신뢰하기 전에 테스트하는 방법을 다룹니다.

생각보다 작게 시작하세요. 첫날부터 많은 스킬이 필요하지 않으며, 이 플러그인 전체가 필요한 것도 아닙니다. 평범하게 프롬프트를 작성하고, 에이전트가 어디서 실패하는지 지켜보고, 같은 실패가 두 번 나타나면 스킬이나 검사를 추가하세요.

## `/automate-me`로 나만의 모드 생성하기

```text
/automate-me
```

여러분이 자신의 스타일을 설명할 필요는 없습니다. [`/automate-me`](../../skills/automate-me/SKILL.md)가 여러분의 기록에서 스타일을 읽어 내기 때문입니다. 이 스킬은 활성 워크스페이스의 최근 대화 기록에서 답변, 위임, 검증, 코드, 글, 작업 과정을 어떻게 선호하는지에 관한 반복되는 선호를 찾아낸 다음, 어떤 패턴이 정말 여러분의 것인지 묻습니다. 그리고 Cursor에 내장된 `create-skill` 흐름으로 `.cursor/skills/<your-name>-mode/SKILL.md` 초안을 작성하고, 초안을 [`/unslop`](../../skills/unslop/SKILL.md)으로 다듬은 뒤, 워크트리에서 PR을 열어 다른 변경과 마찬가지로 리뷰할 수 있게 합니다.

습관이 달라질 때마다 다시 실행하세요.

```text
/automate-me 마지막으로 수정한 이후의 모든 내용으로 내 모드 스킬을 업데이트해 줘
```

업데이트 모드는 스킬이 마지막으로 바뀐 이후의 기록만 분석합니다. 여러분이 반박하지 않은 규칙은 유지하고, 새로운 근거가 있는 규칙은 수정하며, 새로운 패턴에 대해서만 섹션을 추가합니다.

## `/reflect`로 세션의 교훈 기록하기

무언가를 배운 작업을 마친 직후에 다음을 실행합니다.

```text
/reflect 너무 오래 걸렸어. 다음 실행에서 반복하지 않도록 이번에 배운 것을 기록해 줘.
```

[`/reflect`](../../skills/reflect/SKILL.md)는 대화 기록을 세 명의 리뷰어에게 병렬로 보내고, 이어서 종합 담당이 제안을 `Accepted`, `Rejected`, `Backlog`로 분류한 다음, 스킬을 변경하기 전에 여러분의 승인을 기다립니다. 앞으로의 결정을 바꿀 제안만 승인하세요. 이상했던 세션 하나는 일화일 뿐이며, 규칙이 될 수 없습니다.

## `/correct`로 환경 고치기

에이전트의 같은 실수를 계속해서 바로잡고 있다면, 해결책은 다음 프롬프트가 아니라 저장소에 있어야 합니다. 선택지를 얼마나 확실하게 유지되는지에 따라 순위를 매기면 다음과 같습니다.

1. 아키텍처나 더 나은 자료 구조로 실수 자체를 불가능하게 만듭니다.
2. 타입으로 막거나, 오류 메시지가 해결 방법을 알려 주는 린트 또는 CI 검사로 막습니다.
3. 테스트로 잡아냅니다.
4. 문서나 에이전트 규칙으로 적어 둡니다. 에이전트가 규칙을 건너뛰어도 아무것도 실패하지 않으므로, 이 방법이 마지막입니다.

사람이 하는 리뷰는 목록에 없습니다. 모든 PR에서 같은 실수를 잡아내야 하는 리뷰어가 바로 이 방법이 해결하려는 문제입니다. [`/correct`](../../skills/correct/SKILL.md)가 이 작업을 수행합니다.

```text
/correct 에이전트들이 리포지토리 계층을 거치지 않고 데이터베이스 클라이언트를 직접 호출하는 일이 계속 생겨
```

이 스킬은 최근 커밋, 되돌린 커밋(revert), 리뷰 코멘트, 우회 방법을 설명하는 코멘트를 읽은 다음, 실수를 유형별로 묶습니다. 어떤 유형이 두 번 발생하면 하나의 유형으로 인정합니다. 가장 자주 발생하는 유형부터, 효과가 있는 가장 높은 수준에서, 유형마다 커밋 하나씩으로 고치고, 새로 추가한 각 검사가 과거에 실제로 있었던 실수에서 실패하는지 증명합니다. 또한 에이전트 지침 파일에 각 규칙과 그 규칙을 강제하는 수단을 짝지은 표를 유지하므로, 아무것도 강제하지 않는 규칙은 반복되는 실수로 드러납니다. 답변에는 각 유형과 그 근거, 선택한 수준, 그리고 더 높은 수준이 통하지 않은 이유가 나열됩니다.

인자 없이 실행하면 기록에서 유형을 스스로 찾아냅니다. `/reflect`와 `/correct`는 작업을 나누어 맡습니다. `/reflect`는 한 세션을 바탕으로 스킬을 개선합니다. `/correct`는 저장소를 바꾸어 어떤 실수 유형이 다시 발생하지 못하게 합니다. 해결책이 새로운 경계라면 `/architect`와 함께 사용하세요. [여러 프로젝트를 병렬로 실행하기](./07-overnight.md#run-many-projects-in-parallel)에는 저장소 전체에 걸쳐 두 가지를 모두 수행하는 프롬프트가 있습니다.

## 특정 목적의 스킬 작성하기

기록하고 싶은 워크플로를 이미 알고 있다면 다음과 같이 합니다.

```text
/poteto-mode 이 저장소에서 데이터베이스 마이그레이션을 검증하는 스킬을 작성해 줘
```

스킬 작성은 [스킬 작성 또는 수정 플레이북](../../skills/poteto-mode/playbooks/authoring-a-skill.md)에 해당합니다. 이 플레이북은 Cursor에 내장된 `create-skill`을 거치고, frontmatter와 링크를 검증하며, Opening a PR 플레이북을 통해 결과를 내보냅니다. 에이전트가 읽는 글은 사람이 읽는 글보다 기준이 더 높습니다. 도움이 되지 않는 문장이 앞으로 어떤 에이전트가 따를 지시가 되기 때문입니다. `SKILL.md`를 자유롭게 작성하지 말고, 플레이북이 그 기준을 지키게 하세요.

두 가지 특수한 경우에는 별도의 생성기가 있습니다. 앱을 조작해 동작을 증명해야 하는 스킬은 검증 스킬이므로, 대신 [`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)과 [`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)을 사용하세요. 모델 체커, 증명, 또는 다른 검증기로 코드의 속성을 확인하는 스킬은 형식 검증 스킬이므로, [`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)과 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)을 사용하세요. [검증하고 내보내기](./06-verify-and-ship.md#prove-a-property-with-a-formal-verification-skill)에서 두 종류를 모두 다룹니다.

## `/technical-writing`으로 기준에 맞게 문서 작성하기

여러분이 내보내는 글은 스킬만이 아닙니다. 문서, RFC, readme, PR 설명, 커밋 메시지에는 다음을 사용합니다.

```text
/technical-writing readme 변경 사항을 리뷰해 줘
```

[`/technical-writing`](../../skills/technical-writing/SKILL.md)은 여러 계층으로 이루어진 기준을 적용합니다. 이 스킬의 목표는 피곤한 엔지니어도 처음 읽을 때 이해할 수 있는 글입니다. 먼저 문서의 유형(튜토리얼, 하우투, 레퍼런스, 설명)을 정한 다음, 문장 단위로 작업합니다. 누가 무엇을 하는지 분명히 하고, 한 문장에는 하나의 생각만 담으며, 두 가지로 읽힐 수 있는 문장은 남기지 않습니다. 여러분이나 에이전트가 방금 작성한 글을 리뷰할 때 사용하거나, 문서를 요청할 때 처음부터 이 스킬의 이름을 언급하세요.

## 스킬 변경을 블라인드로 테스트하기

스킬 수정은 앞으로의 모든 세션에 영향을 미치므로, 실험으로 보고 그에 맞게 테스트하세요. 다른 사람의 스킬을 도입할 때도 마찬가지입니다. 스킬을 계속 쓰기 전에, 그 스킬이 여러분의 작업에서 에이전트를 더 낫게 만드는지 확인하세요.

```text
/poteto-mode 이 스킬 변경에 대해 eval 플레이북을 실행해 줘. 두 변형 모두 같은 작업을 주고, 후보들은 블라인드 상태를 유지해.
```

스킬이 계속 기대에 못 미치고 그 스킬이 무엇을 해야 하는지 알고 있다면, 하나의 작업에서 변경과 테스트를 함께 진행하세요.

```text
/poteto-mode 누락된 마이그레이션을 지적하도록 리뷰 스킬을 업데이트하고, 그 변경을 eval로 평가해 줘.
```

처음부터 평가(eval)를 요청하면 수정이 정직하게 유지됩니다. 나빴던 세션 하나를 바탕으로 작성한 수정은 그 세션에 과적합되기 쉽고, 수정이 거듭되면 스킬이 원래 방향에서 벗어납니다. 평가(eval)는 이렇게 벗어난 부분을 배포 전에 잡아냅니다.

[Eval 플레이북](../../skills/poteto-mode/playbooks/eval.md)은 관찰자 효과라는 하나의 실패 유형을 중심으로 설계되었습니다. 자신이 평가받고 있다는 것을 아는 에이전트는 다르게 행동합니다. 그래서 후보 에이전트들은 정제된 디렉터리에서 자연스러워 보이는 작업을 받으며, "eval"이나 "candidate"라는 단어를 접하지 않고, 서로의 존재도 알지 못합니다. 한 명의 심사자가 중립적인 레이블 아래에서 모든 출력을 채점하며, 참조 체인을 따라갔는지는 각 후보가 주장하는 내용이 아니라 실제로 읽은 파일을 바탕으로 채점합니다.

판정을 받아들이기 전에 모든 출력을 직접 읽어 보세요. 심사자와 의견이 다르다면, 자신의 판단을 의심하기 전에 채점 기준을 먼저 의심하세요.

## `/make-bot-ui`로 봇 UI 만들기

특정 상황에서 쓰는 스킬 하나는 Grok Bot 사용자를 위한 것입니다. [`/make-bot-ui`](../../skills/make-bot-ui/SKILL.md)는 버튼을 누르면 웹훅 루틴을 통해 봇을 깨우는 작은 페이지를 만듭니다. 예를 들어 리뷰 대기열을 스와이프하면서, 스와이프할 때마다 봇이 해당 항목을 처리하도록 요청할 수 있습니다. 여러분의 컴퓨터에서 실행되는 서버가 웹훅의 발신자 키를 보관하므로, 키는 브라우저나 대화에 전달되지 않습니다. 이 스킬은 페이지를 Tailscale에 공개하는 방법도 다룹니다.

**주의할 점:** 스킬이 오작동한다는 이유로 작업 도중에 스킬을 수정하지 마세요. 별도의 PR에서 고치고 작업은 계속 진행하세요. 기능 작업과 뒤섞여 배포된 스킬 수정은 리뷰에서 드러나지 않고, 평가할 수도 없습니다.
